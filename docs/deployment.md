# 배포 (B-63)

> **되돌릴 수 있는 것은 이미지뿐이다.** 이 문서의 나머지는 전부 그 사실에서 나온다.

관련: `docs/git-workflow.md`(브랜치 흐름 · §8.2 `main` 은 릴리스 후보다) · `docs/invariants-and-security.md`(S-2, S-8, S-11) · `README.md`(로컬 실행)

---

## 1. 무엇이 배포되는가

| 산출물 | 자리 | 내용 |
|---|---|---|
| 애플리케이션 이미지 | `ghcr.io/<owner>/<repo>:<커밋 SHA>` | `Dockerfile` 이 만든다 |
| 설정 | 이미지 안 `/app/config/application.yml` | **플레이스홀더뿐이다** — `application.yml.template` 그대로 |
| 값 | 런타임 환경변수 | 이미지에 들어가지 않는다 (S-2) |

**이미지에 값이 없다는 것은 확인된 사실이다.** `Release` 워크플로가 매 빌드에서
① 시크릿으로 분류되는 파일이 없는지, ② 설정이 템플릿과 **바이트 단위로 같은지**,
③ 값을 주지 않으면 부팅이 **실패하는지**를 확인한다. 셋 중 하나라도 어긋나면 게시되지 않는다.

**이동 가능한 태그를 만들지 않는다.** `latest` 가 없다 — 롤백은 *"이전 SHA 로 되돌린다"* 여야 하고,
움직이는 태그가 있으면 무엇으로 되돌리는지가 흐려진다.

### `image` 를 필수 status check 로 등록하지 않는다

`Release` 워크플로의 `image` 잡은 **경로 필터가 걸린 PR 에서만** 돈다 — `Dockerfile` ·
`.dockerignore` · 빌드 스크립트 · 설정 템플릿이 바뀔 때다. 필수 체크로 등록하면 **그 파일들을
건드리지 않은 PR 이 영원히 대기**한다. 돌지 않은 체크는 통과하지도 실패하지도 않기 때문이다.

필수 체크는 `CI` 의 세 잡(`build` · `test` · `gitleaks`)뿐이다 (`docs/branch-protection.md`).

## 2. 마이그레이션 순서

### 마이그레이션은 앱 기동이 수행한다

`DataSourceConfiguration` 이 스토어마다 `StoreMigration` 을 `initMethod = "migrate"` 로 등록한다.
**별도의 마이그레이션 단계가 없다** — 새 이미지가 뜨는 순간 그 이미지가 가진 마이그레이션이 돈다.

네 스토어(`identity` · `catalog` · `play` · `promptlog`)는 **각자의 계정으로, 각자의 경로를,
각자의 `flyway_schema_history` 에** 기록한다 (§5.3). 스토어 사이에 순서 의존이 없다 — 스키마 간
FK 가 없기 때문이다. 있었다면 배포는 스토어 순서를 아는 절차가 됐을 것이다.

### 그래서 무중단 배포의 제약이 마이그레이션의 제약이 된다

무중단 배포에서는 **구 버전과 신 버전이 겹쳐 돈다.** 신 버전이 뜨면서 스키마를 바꾸고, 그 순간
구 버전은 아직 트래픽을 받고 있다. 따라서 **모든 마이그레이션은 구 버전과도 호환되어야 한다.**

**한 번에 하나씩 늘리고, 다음 배포에서 줄인다** (expand → contract).

| 하려는 일 | 이번 배포 | 다음 배포 |
|---|---|---|
| 컬럼 추가 | `NULL` 허용 또는 `DEFAULT` 와 함께 추가 | 코드가 채우기 시작한 뒤 `NOT NULL` |
| 컬럼 삭제 | 코드에서 읽기를 멈춘다 | 컬럼을 지운다 |
| 컬럼 이름 변경 | 새 컬럼 추가 + 양쪽 쓰기 | 옛 컬럼 삭제 |
| 값 제약 강화 | 위반 행을 먼저 정리 | 제약 추가 |

**금지되는 것 — 한 배포에서 추가와 동시에 `NOT NULL` 을 거는 것.** 구 버전은 그 컬럼을 모르므로
INSERT 에 넣지 않는다. 겹쳐 도는 몇 초 동안 구 버전의 모든 쓰기가 실패한다.

> `V7__user_purge.sql`(B-61)이 그 예다 — `player_ref` 의 `NOT NULL` 을 **푸는** 방향이라
> 구 버전과 호환된다. 반대 방향이었다면 두 배포로 나눴어야 한다.

### 번호 규칙

파일명은 `V<번호>__<snake_case>.sql` 이고 **번호는 스토어별로 독립**이다 (그 스토어의 마지막 번호 + 1).
`outOfOrder=false` + `validateOnMigrate=true` 이므로 같은 스토어에 같은 번호가 둘이면
**두 번째가 머지된 뒤부터 기동이 막힌다.** 증상은 애플리케이션 오류처럼 보이지만 원인은 번호다.

**이미 머지된 마이그레이션을 고치지 않는다** — 체크섬이 어긋난다.

## 3. 무중단 배포 절차

전제 — 인스턴스가 둘 이상이고, 앞단이 `readiness` 프로브를 본다.
B-48 이 `management.endpoint.health.probes.enabled` 를 켜 두었다.

| | 경로 | 무엇을 판정하는가 |
|---|---|---|
| readiness | `/actuator/health/readiness` | 트래픽을 받아도 되는가 |
| liveness | `/actuator/health/liveness` | 재시작이 필요한가 |

0. **`service_config` 에 두 키를 먼저 넣는다.** 없으면 **그 화면들이 500 이다.**

   | 키 | 없으면 무엇이 막히는가 |
   |---|---|
   | `ai.notice` | **랜딩 · 라이브러리 · 작품 상세** (세 화면 모두 고지 문구를 싣는다) 그리고 **`GET /consents`** — `ai_notice` 동의의 판본이 이 값에서 나온다 |
   | `consent.terms` | **`GET /consents`.** 가입 화면이 약관 판본을 얻지 못한다 |

   - 설계대로다 (§13-27, §13-51). 사전 고지는 §11 의 의무이고 R11.1 이 하드코딩을 금지하므로,
     **문구 없이 그 화면을 내보내지 않는 것**이 유일한 방법이었다. 약관 판본도 같은 판단이다 —
     기본 판본을 지어내면 **검증되지 않은 판본이 동의 이력에 남는다** (R10.2).
   - `service_config` 에는 **시드가 없다** (S-11 — 운영 문구와 약관 주소를 공개 레포의
     마이그레이션에 넣지 않는다). 그래서 이 단계는 배포마다 확인하는 것이 아니라
     **환경마다 한 번** 하는 일이다.
   - **첫 배포에서 이것을 빠뜨리면 장애로 보인다.** 절차서에 있어야 하는 이유가 그것이다.
   - **`GET /consents` 는 둘 다 있어야 뜬다.** `consent.terms` 만 넣으면 여전히 500 이다 —
     그 응답의 `ai_notice` 판본이 고지에서 오기 때문이다 (§13-51). 넣는 순서는 상관없다.

   값의 모양을 **정의하는** 곳은 각각 `CatalogAiNoticeQuery` · `CatalogConsentTermsQuery` 이고,
   필드별 필수 여부는 §13-51 의 표가 든다. 아래는 그 정의를 **투입 문장의 모양으로** 옮긴 것이다 —
   판단이 필요하면 §13-51 을 본다.

   **넣는 모양** — `catalog` 스키마의 `service_config` 에 한 행씩 쓴다. **아래 `<...>` 는 전부
   자리표시자다.** 실제 판본과 주소는 여기에도, 마이그레이션에도 적지 않는다 (S-11).

   ```sql
   -- catalog 스키마. 이미 있으면 갱신한다 — 약관 개정이 이 문장을 다시 부른다.
   INSERT INTO service_config (config_key, config_value, updated_at)
   VALUES ('consent.terms', '{
     "tos":     {"version": "<v1.0>", "documentUrl": "<약관 절대 URL>"},
     "privacy": {"version": "<v1.0>", "documentUrl": "<처리방침 절대 URL>"}
   }'::jsonb, NOW())
   ON CONFLICT (config_key) DO UPDATE
      SET config_value = EXCLUDED.config_value, updated_at = NOW();
   ```

   - **판본은 `v<major>.<minor>`** 다 (§13-51). 두 종류는 각자 세므로 서로 달라도 된다.
   - **`documentUrl` 은 절대 URL** 이다 — 웹과 앱이 같은 값을 그대로 링크로 건다. 생략하면
     응답의 그 필드가 `null` 이 되고, 화면은 링크 없는 약관 항목을 그린다.
   - **`ai_notice` · `age` 를 이 JSON 에 적지 않는다.** 적어도 읽지 않는다 (§13-51, §13-24).
   - `ai.notice` 도 같은 표에 같은 방식으로 들어간다 — 모양은 `CatalogAiNoticeQuery` 가 정한다.
   - **넣은 뒤 `GET /api/v1/consents` 가 200 인지 확인한다.** 어긋난 값은 조용히 통과하지 않고
     500 `INTERNAL_ERROR` 로 떨어진다 (§13-51) — **이 한 번의 호출이 투입 검증의 전부**다.

   > **판본을 넣은 뒤 약관을 개정하면 판본도 함께 올린다.** 문구만 바꾸고 판본을 두면
   > **동의 이력이 옛 판본을 가리킨 채 새 문구에 동의한 것**이 되고, 그것이 이슈 #261 이
   > 고치려던 상태다.

0-1. **이미지 저장소를 먼저 설정한다** (#315, §13-65). `app.image-storage.*` 다섯 값이 없으면
   **작품 만들기의 이미지 업로드가 500 이고, 다섯 중 하나만 빠지면 부팅이 멈춘다.** 값 자체는
   저장소 벤더가 주며 이 레포에 없다 (S-11).

   > **버킷은 비공개여야 한다.** 공개 읽기가 열려 있으면 키를 아는 사람이 **검수 전 이미지**를
   > 볼 수 있고, 그것은 코드가 막을 수 있는 자리가 아니다 (I-8). 서버는 영구 공개 URL 을
   > 만들지 않는다 — 그 보장은 버킷이 비공개라는 전제 위에서만 성립한다.

1. **태그를 단다.** `v*` 태그가 `Release` 워크플로를 부르고, 검증을 통과한 이미지가 게시된다.
2. **새 이미지를 한 인스턴스에 올린다.** 그 인스턴스가 기동하며 마이그레이션을 수행한다.
   - 여러 인스턴스가 동시에 떠도 Flyway 가 잠금을 잡는다 — 하나가 수행하고 나머지는 기다린다.
3. **readiness 가 올라올 때까지 기다린 뒤** 다음 인스턴스로 넘어간다.
   - 기다리지 않고 넘기면 **두 인스턴스가 동시에 준비되지 않은 상태**가 되고, 그것은 무중단이 아니다.
4. 모든 인스턴스가 교체될 때까지 반복한다.

**배치는 배포와 무관하다.** `RetentionBatch` 는 Redis 잠금으로 단일 실행을 보장하므로
(`batch:retention`), 겹쳐 도는 동안 두 번 돌지 않는다.

## 4. 롤백

### Flyway 는 되돌리지 않는다

`StoreMigration` 이 `cleanDisabled(true)` 로 만들어진다. **`undo` 도 쓰지 않는다** — 되돌리는
스크립트는 검증된 적 없는 코드이고, 그것을 장애 중에 처음 실행하게 된다.

### 되돌릴 수 있는 것은 이미지뿐이다

```
이전 커밋 SHA 의 이미지로 교체한다
```

**이것이 성립하려면 §2 의 expand-contract 를 지켰어야 한다.** 지켰다면 새 스키마는 구 버전과
호환되므로, 구 이미지가 새 스키마 위에서 그대로 돈다.

### 스키마를 되돌려야 하는 상황이라면

그것은 **롤백이 아니라 새 배포다.** 되돌리는 마이그레이션을 새 번호로 작성하고, 같은 절차로
배포한다. 이력은 앞으로만 간다 — 그것이 `flyway_schema_history` 가 진실인 이유다.

### 되돌릴 수 없는 것

| 무엇 | 왜 |
|---|---|
| 파기 배치가 지운 데이터 | 지운 것이 목적이었다 (R12.4, S-10). 백업에서만 복구된다 |
| 탈퇴 | 되돌리는 경로를 두지 않기로 했다 (B-62) |
| 유출된 자격 증명 | **삭제가 아니라 로테이션이다** (§7.1). 이미지·로그·git 이력 어디에도 남지 않게 하는 것이 아니라, **그 값을 무효로 만든다** |

## 5. 초기 스테이징 구조 (2026-08-29, 이슈 #234)

**한 대다.** 무중단 교체에 필요한 것은 인스턴스 둘이지 클러스터가 아니다 — 그 둘은 한 호스트
안의 두 프로세스여도 성립한다. Kubernetes 로 넓히지 않는다: 지금 필요한 것을 넘는 운영 표면은
그 자체가 장애 원인이 되고, **아직 한 번도 배포해 본 적이 없는 상태**에서 늘릴 이유가 없다.

```
                    ┌─────────────────────────────┐
   인터넷  ───────► │  Reverse Proxy              │
                    │   (blue ⇄ green 전환)       │
                    └──────┬───────────────┬──────┘
                           │               │
                    ┌──────▼─────┐  ┌──────▼─────┐
                    │ app: blue  │  │ app: green │   ← GHCR 이미지 (커밋 SHA)
                    └──────┬─────┘  └──────┬─────┘
                           └───────┬───────┘
                            ┌──────▼──────┐ ┌──────────┐
                            │ PostgreSQL  │ │  Redis   │
                            └─────────────┘ └──────────┘
                              단일 staging host
```

| | |
|---|---|
| 이미지 | **GHCR** — 내장 `GITHUB_TOKEN` 으로 게시한다. 새 자격 증명을 만들지 않는 것이 선택 이유였고 그대로 유지한다 |
| 앱 | **Spring Boot Blue/Green.** 새 SHA 를 놀고 있는 쪽에 올리고, `readiness` 가 올라오면 프록시를 전환한다 |
| 되돌리기 | 프록시를 **이전 쪽으로 되돌린다.** 구 인스턴스를 내리지 않은 동안은 이것이 §4 의 이미지 교체보다 빠르다 |
| 데이터 | **PostgreSQL** 하나 · **Redis** 하나. 스토어 넷은 그 안의 스키마 넷이다 (§5.3 — 인스턴스 분리는 승격 사항이지 지금의 요구가 아니다) |

**실제 호스트·클라우드·주소·계정 체계·시크릿은 여기에 적지 않는다** (S-11). 값이 정해지면
레포 밖 설정에 들어간다.

### 전달 헤더는 신뢰된 프록시에서 온 것만 신뢰한다

프록시 뒤에서 `getRemoteAddr()` 은 **프록시를 가리킨다.** S-8 의 IP 기준 한도(인증 경로 ·
신고)가 여기에 걸린다 — 모두가 같은 IP 로 보이면 그 한도는 서비스 전체에 하나가 된다.

**그렇다고 전달 헤더를 무조건 믿으면 한도가 사라진다.** 헤더는 클라이언트가 보낼 수 있는
값이고, 믿는 순간 **헤더 한 줄로 무한히 우회**할 수 있다. 관리자 IP 제한(S-4)까지 같은 헤더를
본다면 우회 대상이 한도가 아니라 접근 통제가 된다.

**그래서 신뢰 경계를 설정으로 못박는다.**

- 신뢰하는 프록시의 주소를 명시한다. **그 목록에 없는 곳에서 온 전달 헤더는 읽지 않고 버린다.**
- 앱은 인터넷에 직접 노출되지 않는다. 프록시만 앞에 둔다 — 우회 경로가 있으면 위 규칙은
  선언에 그친다.
- 값이 없으면 **비어 있음을 "전부 신뢰"로 읽지 않는다.** `ADMIN_ALLOWED_CIDR` 을 다루는 방식과
  같다 (S-4).

## 6. 이 문서가 아직 답하지 못하는 것

**스테이징 환경이 아직 없다.** §5 는 **무엇을 세울 것인가**를 정했고, 호스트·클라우드·주소는
정해지지 않았다. *"스테이징 무중단 배포 1회 성공"*(B-63 의 원래 DoD, 이슈 #224)은 환경이 준비된
뒤에 확인한다.

**릴리스가 `main` 까지 가면 nightly 가 풀린다** (이슈 #181). `.github/workflows/` 가 기본
브랜치에 없어 `schedule` 과 `workflow_dispatch` 가 발동한 적이 없다 — GitHub 은 그 둘을 **기본
브랜치의 정의로만** 실행한다. `main` 이 **릴리스 후보**를 담는 자리가 되면
(`docs/git-workflow.md` §8.2) 그 위에서 nightly 와 `Release` 워크플로가 실제로 검증된다.
`nightly.yml` 은 `ref: backend` 를 체크아웃하므로, 정의가 `main` 에 있어도 **도는 코드는
`backend`** 다.
