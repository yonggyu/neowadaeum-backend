## 13. 상위 문서 검증 결과 — 정정 · 보완 사항

> 두 상위 문서를 교차 검증한 결과다. **구현 시 이 절이 상위 문서보다 우선한다.**
> 각 항목의 **기본 채택안**을 따르되, `[결정 필요]` 표시가 있으면 PR 본문에 그 사실을 명시한다.

> **공개 범위 결정 (2026-08-22).** 이 절의 대부분은 설계 정정이라 공개해도 무해하며, 오히려 구현에 필수다. 다만 **§13-12만 내부 문서로 분리**했다. 자동 검수만으로 승인되는 공개 범위와 그 보완책은 그대로 악용 경로가 된다.
>
> **git 히스토리는 되돌릴 수 없다.** 공개 커밋에 한 번 들어간 내용은 나중에 지워도 포크·아카이브·스크래퍼에 남는다. 그래서 "일단 올리고 나중에 숨긴다"는 선택지가 없다. 새로운 `[위험]` 항목이 생기면 **커밋 전에** 공개 여부를 판단한다 (S-11).

### 13-1. `[모순]` 챕터·엔딩·캐릭터가 버전에 묶여 있지 않다 — **중대**

`backend-requirements.md` §2.3에서 `character` / `chapter_def` / `ending_def`는 전부 `story_id`를 FK로 갖는다. 그런데 R2.1은 세션이 `story_version_id`를 고정 참조하고, R8.8은 "수정은 새 버전이 되며 진행 중 세션은 기존 버전을 계속 참조한다"고 한다.

**현재 스키마로는 이 보장이 불가능하다.** 작성자가 캐릭터 성격이나 엔딩 조건을 수정하면 진행 중인 모든 세션이 즉시 영향을 받는다. 버전 고정이 `world_prompt` 하나에만 걸린다.

**채택안**: `character` / `chapter_def` / `ending_def`의 FK를 `story_version_id`로 변경한다. `story_id`는 조회 편의를 위한 비정규화 컬럼으로만 유지한다. 새 버전 발행 시 세 테이블을 복제한다.

**부수 영향**: `ending_stat`은 `(story_id, ending_no)` 기준으로 집계해야 한다. `ending_id`(버전마다 달라짐)로 집계하면 버전 발행 때마다 도달률이 리셋된다.

### 13-2. `[모순]` Recent Turns 턴 수가 5인지 8인지 불일치

- 기획서 §2.2: "최근 5턴 원문"
- 요구사항 R4.5: "최근 8턴을 초과하면 초과분을 요약에 병합"
- 요구사항 R4.7: "최근 5턴의 `{turnNo, chosenChoiceText, paragraphsDigest}`를 원문으로 전달"

R4.7은 "원문"이라고 하면서 `paragraphsDigest`(요약본)를 보낸다고 해 용어도 자기모순이다.

**채택안**: 두 값은 서로 다른 것을 가리키는 것으로 정리한다.

- **요약 병합 기준 = 8턴**: `turn_no - 8`보다 오래된 턴이 요약에 병합된다 (R4.5 유지)
- **프롬프트 포함 = 최근 5턴** (R4.7 유지)
- **6~8턴 구간은 완충지대**: 요약에 아직 병합되지 않았고 프롬프트에도 들어가지 않는다. 요약 압축이 비동기(R4.6)라 지연될 수 있으므로 이 완충이 필요하다.
- **필드 명칭 정정**: `paragraphsDigest` → 최근 5턴 중 **최근 2턴은 `paragraphs` 원문**, 3~5턴은 **압축본(`paragraphsDigest`)**. 1,500토큰 예산 안에서 원문 5턴은 들어가지 않는다.

`[결정 필요]` 완충 구간 크기(8)와 원문/압축 경계(2)는 B-46 실측 후 조정한다.

**갱신 (B-20).** 세 값은 코드 상수가 아니라 **설정**이다 — `ai.prompt.recent-turns.verbatim`(2) · `.in-prompt`(5) · `.summary-merge`(8). B-46 의 조정이 배포가 되지 않게 하기 위함이며, 셋의 순서가 뒤집히는 조합(원문 구간 > 프롬프트 구간, 프롬프트 구간 > 병합 기준)은 부팅에서 거부한다. `.summary-merge` 를 읽는 것은 요약 파이프라인(B-34)이지만 셋이 한 규칙의 세 부분이라 함께 둔다.

### 13-3. `[모순]` `disabled` 판정 근거가 존재하지 않는다 — **중대**

R5.6과 I-11은 "`disabled`는 서버가 GameState 조건으로 판정한다"고 한다. 그러나 **선택지는 AI가 매 턴 새로 생성**하며, 출력 스키마의 `choices[]`에는 `{order, text}`만 있다. 서버가 참조할 조건이 어디에도 없다. 사전 정의된 챕터·엔딩과 달리 선택지는 사전 정의되지 않는다.

**채택안 (2단계)**

- **P0**: `disabled`는 **항상 `false`**, `disabledReason`은 `null`로 반환한다. API 계약에는 필드를 유지한다(프론트 계약 안정성). 게이팅 기능 없이 출시한다.
- **P1 이후**: AI 출력 스키마에 선택적 `requires` 필드를 추가한다.
  ```json
  { "order": 3, "text": "유나에게 고백한다", "requires": { "gte": ["affinity.yuna", 50] } }
  ```
  서버는 이 조건을 **`story_version.state_schema` 화이트리스트로 검증**한 뒤(미정의 키 참조 시 조건 폐기), B-27 평가기로 판정해 `disabled`를 결정한다. **판정 주체는 여전히 서버**이므로 I-11은 유지된다.

`[결정 필요]` P1 시점에 `requires` 도입 여부.

### 13-4. `[누락]` 문서에서 참조하지만 정의되지 않은 테이블

R3.7·R9.3·R12.3·R12.4가 `ai_call_log`를 참조하고, R11.1이 `service_config`, R14.5가 `admin_audit_log`를 참조하지만 **어디에도 스키마 정의가 없다.**

**채택안** — B-11에서 아래를 정의한다.

```
ai_call_log            (promptlog 스키마)
  id, session_id(nullable), draft_id(nullable), purpose(turn|summary|safety|outline),
  provider_id, model_id, fallback_from(nullable),
  request_raw(text), response_raw(text),
  input_tokens, output_tokens, latency_ms, cost_micro,
  safety_flags(jsonb), attempt_no, created_at
  ※ player_ref를 담지 않는다. session_id로만 역추적 가능

admin_audit_log        (promptlog 스키마)
  id, admin_user_id, action, target_type, target_id,
  payload(jsonb), ip_hash, created_at

access_audit_log       (promptlog 스키마)   -- S-5
  id, admin_user_id, resource(ai_call_log|story_draft), resource_id, created_at

service_config         (catalog 스키마)
  key, value(text), updated_by, updated_at
  ※ AI 고지 문구, 세이프티 임계값 상수 등

ai_notice_impression   (identity 스키마)   -- R11.3
  id, user_id, notice_version, surface(landing|library|detail|play), shown_at
```

`genre` / `story_genre`도 컬럼이 미정의다: `genre(id, key, label, display_order)`, `story_genre(story_id, genre_id)`.

### 13-5. `[누락]` UGC 미리보기 세션의 저장 대상이 없다

R8.13은 미리보기를 `is_test_session = true` 세션으로 만든다고 하지만, 미리보기 시점에는 **`story`도 `story_version`도 아직 존재하지 않는다**(드래프트 상태). `play_session.story_id` / `story_version_id`가 NOT NULL이면 저장이 불가능하다.

**채택안**: 미리보기 시 `story`를 `review_status = 'draft'` / `visibility = 'private'`로 즉시 생성하고, 임시 `story_version`을 발행한다. 제출·승인 시 정식 버전으로 승격한다. 이 방식이면 턴 파이프라인을 그대로 재사용할 수 있고, R2.3에 의해 타인 노출도 자동 차단된다.

### 13-6. `[모순]` 세션 상태값과 API 쿼리 파라미터 불일치

`play_session.status`는 `active|completed|abandoned|expired`인데, §13.7 API는 `GET /me/sessions?status=in_progress|completed`를 쓴다. `in_progress`라는 상태는 존재하지 않는다.

**채택안**: 쿼리 파라미터를 `status=active|completed`로 정정한다. `abandoned`/`expired`는 목록에서 제외한다.

### 13-7. `[누락]` UGC 작성자 닉네임을 저장할 곳이 없다

§13.3은 `authorDisplayName`(닉네임)을 반환한다고 하지만, `user` 테이블에 닉네임 컬럼이 없고 Catalog는 `player_ref`만 갖는다. 스토어 분리 원칙상 Catalog가 Identity를 조회할 수도 없다.

**채택안**: Catalog 스키마에 `author_profile(player_ref PK, display_name, updated_at)`을 둔다. 닉네임 설정 시 Identity가 Catalog 파사드로 동기화한다. 닉네임은 회원 식별정보가 아니라 **공개 표시명**이므로 Catalog 보관이 타당하다.

### 13-8. `[모순]` `consent_log`에 고지 노출 이력을 넣는 것은 부적절

R11.3은 "사전 고지 노출 이력을 `consent_log`에 기록한다"고 하지만, `consent_log`는 `consent_type` / `agreed_at`을 갖는 **동의** 기록이다. 고지 노출은 동의가 아니라 **표시 사실**이다. 섞으면 동의 이력의 법적 증빙력이 흐려진다.

**채택안**: `ai_notice_impression` 테이블로 분리한다(§13-4). `consent_log`의 `ai_notice` 타입은 "AI 고지를 읽고 동의함"에만 쓴다.

### 13-9. `[누락]` 상태 머신·제약이 명시되지 않은 항목

| 항목 | 채택안 |
|---|---|
| `review_status` 전이 | `draft → pending → (auto_rejected \| in_review) → (approved \| rejected)`, `approved → suspended → (approved \| rejected)`. §8.3 다이어그램의 "reject"는 자동 검수 반려이므로 `auto_rejected`로 기록하고 사용자에겐 `rejected`로 표시한다 |
| `is_default` 제약 | `CREATE UNIQUE INDEX ... ON ending_def(story_version_id) WHERE is_default` |
| `is_default` + `is_secret` | 동시 true 금지. CHECK 제약 |
| 작품당 active 세션 1개 | `CREATE UNIQUE INDEX ... ON play_session(player_ref, story_id) WHERE status = 'active'` |
| `restart=true` 처리 | 기존 active 세션을 `abandoned`로 전환 후 신규 생성 |
| `choiceId` 형식 | 세션 내 유일. `{turnNo}-{order}-{shortHash}` 권장. **이전 턴의 choiceId 재사용 불가** |
| `content_report` 중복 | `UNIQUE(reporter_ref, target_type, target_id)` — 동일인 반복 신고로 자동 정지를 유발할 수 없게 한다 |
| `story_summary`·`game_state_snapshot` 롤백 | 두 테이블에 `deleted_at` 추가. R14.4가 "함께 되돌린다"를 요구하므로 soft delete가 필수다 |
| `stateChanges` 연산자 | `<numericPath>: delta`, `flags.add: []`, `flags.remove: []`, `inventory.add: []`, `inventory.remove: []`, `location`, `timeOfDay`. **이 외 키는 무시** |
| `state_schema` 템플릿 | R4.4가 "플랫폼 템플릿 중 선택"을 요구하므로 `story_version.state_template_key`(`affinity`\|`flag`\|`numeric`) 컬럼 추가 |
| `isPending`(History) | 마지막 턴이며 `chosen_choice_id IS NULL`인 경우 true |
| UGC 작성자 탈퇴 | `[결정 필요]` — 약관 확정 전까지 기본값은 **공개 UGC를 `unlisted`로 강등하고 작성자명을 "탈퇴한 사용자"로 익명화**한다. **B-62 에서 이 채택안대로 구현했다** — 지우지 않는 이유는 작품에 *플레이한 사람들의* 기록(세션·도달률)이 매달려 있기 때문이고, 검수 상태는 건드리지 않는다(승인은 작품에 대한 판정이지 작성자에 대한 판정이 아니다). 발행되지 않은 원고(`story_draft`)는 지운다. 처리는 **매핑 파기보다 먼저** 일어난다 — `author_ref` 가 곧 `player_ref` 다 |

### 13-10. `[모순]` 구현 우선순위의 의존성 역전

`backend-requirements.md` 부록 A는 Turn API를 P0에, Session/Resume API를 P1에 둔다. **Session 생성 없이 Turn을 호출할 수 없다.** §12에서는 B-17(Session)이 B-32(Turn)보다 앞서도록 정정했다.

### 13-11. `[모순]` MVP 범위와 API 명세 불일치

기획서 §9.1은 MVP 계정을 "소셜 로그인 1종(Google)"으로 한정하지만, 요구사항 §13.1에는 `/auth/email/signup`, `/auth/email/login`이 있다. 또한 `oauth_identity`에 `email_hash`만 있어 **이메일 로그인에 필요한 이메일 원본 저장 위치가 없다.**

**채택안**: MVP는 **Google OAuth만** 구현한다(B-12). 이메일 가입은 범위 밖으로 미루고, 도입 시 `user` 테이블에 암호화된 `email` + `password_hash`를 추가한다.

### 13-12. `[내부]` UGC 공개 범위별 검수 정책

이 항목의 상세는 **공개 문서에서 제외**했다. 자동 검수만으로 승인되는 공개 범위와 그에 대한 보완책(샘플링 비율·신고 임계값)이 그대로 악용 경로가 되기 때문이다 (S-11).

- 내부 문서: `docs/internal/13-12-ugc-review-policy.md` (`.gitignore` 대상, 별도 비공개 백업)
- **B-06 / B-54 / B-55 / B-57 / B-59 착수 전 반드시 참조한다.**
- 내부 문서 없이 이 작업들을 구현하면 검수 정책이 R8.6의 기본값으로만 구현된다. 그 상태로 UGC를 오픈하지 않는다.

### 13-16. `[해소]` `ending_def.condition` 과 `is_default` 의 관계 — **결정됨 (2026-08-23)**

R2.2 는 *"정확히 1개는 `is_default = true`"*, R7.7 은 *"어떤 조건도 매칭되지 않고 마지막 챕터 `max_turns` 에 도달하면 `is_default` 엔딩으로 종료"* 라고 하지만, ① 기본 엔딩이 `condition` 을 가질 수 있는지 ② 일반 엔딩이 `condition` 없이 존재할 수 있는지 **어느 쪽도 규정하지 않았다.**

②가 허용되면 그 엔딩은 R7.6 의 `ending_no` 순회에서 **항상 최초 매칭**이 되어 뒤의 엔딩을 전부 가린다.

**결정**

| # | 규칙 | 강제 위치 |
|---|---|---|
| 1 | `is_default = true` 인 엔딩은 **조건 판정에 참여하지 않는** fallback 이다 | 엔진 (S-7) |
| 2 | `is_default = false` → `condition` 을 **반드시 갖는다** | DB CHECK |
| 3 | `is_default = true` → `condition` 을 **갖지 않는다** | DB CHECK |
| 4 | 기본 엔딩은 **R7.7 의 시점에만** 선택된다 — 마지막 챕터에서 `max_turns` 에 도달했고 조건부 엔딩이 하나도 매칭되지 않았을 때 | 엔진 (S-7) |
| 5 | 엔딩 집합에 기본 엔딩은 **정확히 1개** (R2.2 유지) | `≤ 1` DB partial unique / `≥ 1` 애플리케이션 |

2·3 은 `CHECK (is_default = (condition IS NULL))` 하나로 표현된다 — `catalog/V4__ending_default_contract.sql`.

**규칙 4 를 시점 없이 읽지 않는다.** *"아무 조건도 만족하지 않으면 기본 엔딩"* 을 매 턴 적용하면 초반 턴은 어떤 조건도 만족하지 않으므로 **모든 세션이 1턴에 끝난다.** 발동 시점은 R7.7 이 규정한 그것이고, 규칙 4 는 그 시점에서의 **선택 순서**를 말한다.

**하한(`≥ 1`)은 DB 로 강제하지 않는다.** 행의 부재는 CHECK 로 볼 수 없고, 트리거로 막으면 작성 도중의 정상 상태(엔딩을 아직 안 만든 `draft`)까지 거부하게 된다. 검증 시점은 **작품이 플레이 가능한 상태로 전환될 때**다 — 그 순간이 R2.2 의 *"엔딩 없이 무한히 진행되는 세션 방지"* 가 실제로 의미를 갖는 시점이다.

**구현 위치는 `B-56` 게시 & 버전 발행이다** — *"승인 시 `story_version` 발행"* 이 곧 "플레이 가능해지는" 순간이다. 추적은 **#54**. S-7 은 폴백 부재를 만나면 실패시킨다(`EndingEngine`).

> **정정 (2026-08-23).** 이 항목의 초판은 구현 위치를 **`B-49`(작성 도구)** 라고 적었다. **틀렸다** — `B-49` 는 *블록리스트 관리*다. 저작 경로는 `B-51`(드래프트 CRUD) · `B-54`(제출·자동 검수) · `B-55`(인간 검수) · `B-56`(게시·버전 발행)으로 나뉘고, "플레이 가능한 상태로 전환"에 해당하는 것은 **`B-56`** 뿐이다.
>
> 같은 오기가 `catalog/V2__catalog_core.sql` 의 주석에도 있다. **그 파일은 머지되어 고칠 수 없다** — Flyway 체크섬은 주석까지 포함하므로 한 글자만 바꿔도 기존 DB 의 기동이 막힌다(`persistence.md`). 마이그레이션 주석이 아니라 **이 항목이 기준**이다.

### 13-17. `[해소]` 세션 시작 시 GameState 초기값 — **결정됨 (2026-08-23)**

`engineering-guide` §4.2 는 세션 시작 절차에 *"GameState 초기화 (`state_schema` 기본값)"* 을 넣는다. 그런데 **`state_schema` 에는 기본값을 선언할 자리가 없다** — R4.2 가 규정하는 것은 `min` · `max` · `maxDeltaPerTurn` 뿐이다. 가리키는 대상이 없는 문장이었다.

**결정**

| 시점 | 동작 | 구현 |
|---|---|---|
| 세션 시작 | 수치·플래그·인벤토리가 **비어 있는** GameState. `chapter = 1` · `turn = 0` | `GameState.initial()` (S-5) |
| 첫 수치 변화 | 그 수치는 **`min` 을 기준**으로 델타 상한과 범위를 적용한다 | `GameStateEngine` (S-5) |

**`state_schema` 에 초기값 필드를 만들지 않는다.** 원문에 없는 스키마를 발명하지 않는다. 작품마다 "호감도 30에서 시작" 같은 요구가 실제로 생기면 그때 B-08(Catalog 스키마)에서 필드를 더한다 — **지금 만들면 쓰이지 않는 컬럼이 하나 생기고, 그 기본값이 무엇인지가 또 미정으로 남는다.**

**`0` 을 기준으로 쓰지 않는 이유가 이 결정의 핵심이다.** `min` 이 양수인 스키마에서 `0` 은 **범위 밖 값**이다. 그리고 조건 평가는 "값이 없다"와 "0 이다"를 구분한다 — 없는 수치는 `lt` 계열에서도 `false` 다(S-6). 두 상태를 같게 만들면 **도달하면 안 되는 엔딩이 열린다.**

§4.2 의 *"`state_schema` 기본값"* 은 이 결정으로 읽는다 — 기본값은 스키마가 선언하는 값이 아니라 **스키마의 `min` 이 정하는 하한**이다.

### 13-18. `[결정 필요]` 토큰을 어떻게 세는지 정의되어 있지 않다

`backend-requirements.md` §4.3 은 레이어별 상한(1,200 / 300 / 600 / 1,500 / 200)과 입력 합계 목표 4,000 을 정하고, R4.9 는 UGC `world_prompt` + `persona_prompt` 합계를 1,000 토큰으로 하드 제한한다. **그러나 이 "토큰"을 무엇으로 세는지는 어디에도 없다.**

정하지 않으면 두 가지가 성립하지 않는다. 조립기가 축소를 시작할 시점을 알 수 없고(§4.4), 저장 시점의 UGC 길이 검증(R4.9, B-51)이 무엇을 재는지 알 수 없다.

**어려운 점은 정답이 하나가 아니라는 것이다.** 토큰화는 벤더마다 다르다 — 한 벤더의 토크나이저를 붙이면 다른 벤더에서는 틀린 값이 된다. 라이브러리 추가는 새 의존성이고(§0.1 의 착수 전 확인), 벤더 API 로 세는 것은 매 턴 네트워크 호출이다.

**기본 채택안 (B-20 에서 적용)**: **벤더 없는 보수적 근사.**

| 분류 | 계수 | 근거 |
|---|---|---|
| 한글·CJK | 1.3 토큰/글자 | 현대 BPE 에서 한글은 글자당 1 토큰 안팎이고 조사·어미에서 더 쪼개진다. **1.0 은 그 꼬리를 놓친다** |
| 그 밖의 비ASCII | 2.0 토큰/코드포인트 | 이모지·기호는 여러 조각으로 쪼개져 가장 비싸다 |
| ASCII | 0.25 토큰/글자 | 영문 BPE 의 통상값 |

그 위에 **안전 여유 1.1** 을 곱한다. 계수는 평균에 대한 추정이고 예산은 **평균이 아니라 최악에서** 지켜져야 한다.

방향을 이렇게 잡은 이유는 **틀리는 쪽을 고를 수 있기 때문**이다. 과소 추정은 예산을 넘긴 요청을 실제로 보내 Provider 오류와 비용을 낳고, 과대 추정은 컨텍스트를 조금 덜 싣는다. 되돌릴 수 없는 쪽은 전자다.

### 함께 결정된 것 (2026-08-25)

**1. 소유 모듈은 `common/support` 다** (이슈 #82, §5.4). `ai` 가 아니다 — 조립 시점의 예산 판단(§4.3)과 UGC 저장 시점의 길이 검증(R4.9, B-51)이 **같은 계산을 써야** 하기 때문이다. 둘이 다르게 세면 저장 시점에 통과한 작품이 조립 시점에 예산을 넘는다. `common/spi` 가 아닌 이유는 SPI 가 데이터를 소유한 모듈이 구현을 제공하는 계약이기 때문이며(ADR-0002, ADR-0003), 토큰 계산에는 소유할 데이터가 없다.

**2. 런타임 예산 판단은 언제나 로컬 계산이다. Provider 네이티브 카운팅에 의존하지 않는다.** 매 턴 네트워크 호출이 되고, 벤더가 둘이 되면 같은 작품이 벤더마다 다른 예산을 갖는다.

**3. 실제 토큰 수는 사후에 관측한다.** 응답의 `usage` 를 `ai_call_log` 에 기록하고(B-11, B-25), 근사와의 오차를 B-48 에서 본다. **계수를 고치는 근거는 그 관측이다** — 지금의 1.3 과 1.1 은 측정이 아니라 방향이다.

**4. 골든 파일 테스트는 고정 계산기를 쓴다.** 근사 계수를 조정했을 때 축소 시점이 달라져 골든 파일이 함께 바뀌면, "프롬프트를 바꿨다"와 "계수를 바꿨다"가 같은 diff 에서 구분되지 않는다. 골든 파일의 목적이 정확히 그 구분이다.

### 이 결정이 드러낸 것 — 플랫폼 문구의 길이가 이미 정해져 있었다

계산기를 붙이자마자 **§4.3 이 `SYSTEM` 과 `OUTPUT SPEC` 의 길이를 이미 다 써 놓았다는 사실**이 드러났다.

- `FOUNDATION` 1,200 에서 R4.9 의 UGC 하드 제한 1,000 을 빼면 **`SYSTEM` 의 몫은 200 토큰**이다.
- `INSTRUCTION` 200 은 `OUTPUT SPEC` 과 `USER ACTION` 이 나눠 쓴다.

초안은 둘 다 이 상한을 넘었다. **출력 형식을 한국어 산문으로 설명하면 예산에 들어가지 않는다** — ASCII 는 한글의 약 1/5 값이라, 같은 내용을 JSON 골격으로 보여 주는 편이 훨씬 싸다. 그렇게 고쳤고, 문구가 다시 길어지면 `PlatformPromptBudgetTests` 가 먼저 실패한다.

### 13-19. `[결정 필요]` 스키마 재요청이 25초 제한의 안인가 밖인가

`backend-requirements.md` §6.1 은 턴 파이프라인을 이렇게 나눈다.

```
 4. Provider 호출 (타임아웃 25s)
 5. 파싱 → 스키마 검증 → 실패 시 1회 재요청
```

호출과 재요청이 **나란한 단계로** 적혀 있고, §6.3 은 별도로 서버 전체 응답 예산을 **28s** 로 못박는다. 세 값이 서로를 정의하지 않는다.

**재요청이 제한 밖이면 두 번의 호출이 최대 50s 가 되어 28s 예산을 넘는다.** R3.3 의 `structuredOutput === false` 경로는 재요청이 2회이므로 최대 75s 다. 클라이언트 타임아웃(30s)은 그보다 훨씬 먼저 끊긴다 — 그 시점에 서버는 아직 두 번째 호출을 기다리는 중이고, **그 호출의 비용은 아무도 받지 못한 응답에 청구된다.**

**기본 채택안 (B-21 에서 적용)**: **재요청을 시간 제한 안쪽에 둔다.**

배선은 `AiGateway( TimeLimited( SchemaRetrying( adapter ) ) )` 이며, 재요청을 포함한 전체가 25s 를 넘는 순간 기존대로 `504 GENERATION_TIMEOUT` 이 되고 진행 중이던 호출은 취소된다 (R6.4). 세션 상태는 그대로다 — §6.1 의 7단계 이전이다 (R6.6).

이렇게 잡은 근거는 **두 값 중 하나만 상한으로 삼을 수 있기 때문**이다. 25s 를 "한 번의 호출"로 읽으면 전체 상한이 사라지고, 남는 상한은 28s 뿐인데 그것을 강제할 지점이 코드에 없다. 25s 를 "생성 전체"로 읽으면 상한이 한 곳에서 지켜지고 28s 는 그 위의 여유가 된다.

**대가는 명시해 둔다.** 첫 호출이 20s 를 쓰고 스키마를 어기면 재요청에 남는 시간은 5s 이며, 사실상 재요청이 성립하지 않는다. **그 경우 사용자는 `502` 가 아니라 `504` 를 받는다** — 원인은 스키마인데 표시는 시간 초과다. 이것을 허용하는 이유는, 반대쪽 선택이 만드는 것이 *"클라이언트가 이미 끊은 뒤에도 도는 유료 호출"* 이기 때문이다. 오분류는 로그에서 복구되지만 청구는 복구되지 않는다.

**강제 수단은 아직 배선 순서 하나다 — 이것을 값으로 바꾼다 (#87).** 지금 25s 를 지키는 것은 데코레이터의 중첩 순서이며, 순서가 뒤집히면 예산이 조용히 두 배가 된다. 그 사고는 컴파일에도 단위 테스트에도 걸리지 않는다 — 두 배선은 타입이 같고, 스키마 위반만 재요청하므로 **느리기만 한 어댑터는 양쪽에서 똑같이 `504` 를 낸다.** 지켜야 할 규칙이 있는데 지키는지 확인할 방법이 없는 상태다.

방향은 **최초 요청 시점에 deadline 을 정하고 남은 예산을 호출 경로로 전달하는 것**이다. 첫 호출이 20s 를 쓰면 재요청에는 5s 만 남고, 남은 예산이 없으면 **재요청을 걸지 않는다** — 이미 끝난 예산으로 호출을 걸어 놓고 취소하는 것보다 걸지 않는 편이 싸다. `Clock` 을 주입하면 시간을 앞으로 밀어 `sleep` 없이 검증할 수 있다 (I-15 의 결정론과 같은 성질). 위의 *"20s 를 쓰고 스키마를 어기면 `504`"* 도 그때 값으로 표현된다.

**소켓 읽기 상한은 예산에서 파생시킨다 (#97).** 어댑터가 거는 상한은 <b>예산을 침범하면 안 된다</b> — 상한이 예산보다 작거나 같으면 상한이 먼저 끊고, 시간 초과가 `504 GENERATION_TIMEOUT` 이 아니라 호출 실패 → `502 PROVIDER_ERROR` 로 나간다. **원인은 시간인데 표시는 벤더 장애가 된다.** 요구사항이 정하는 것은 그 **관계**(상한 > 예산)뿐이며 그것은 테스트로 고정돼 있다. 지금 쓰는 배수 2 는 그 관계를 만족하는 가장 단순한 값이고 **근거 있는 값이 아니다** — 정확한 값은 **B-46 실측 항목**이다. 임의로 최적화하지 않는다.

**관측이 붙으면 배분을 다시 본다.** B-48 이 스키마 위반율과 첫 호출 지연 분포를 보여 주면, 재요청에 별도 예산을 떼어 줄지(예: 첫 호출 18s / 재요청 7s) 판단할 근거가 생긴다. **예산이 값으로 표현되어야 나눠 줄 수도 있다** — #87 이 그 판단을 가능하게 만드는 구조다. B-46 의 부하 실측과 같은 자리에서 정한다.

### 함께 정한 것 — 무엇을 다시 요청하는가 (B-21)

**1. 스키마 위반만 다시 요청한다.** 시간 초과·연결 실패는 같은 요청을 다시 보내 나아지는 종류가 아니고, 시간 초과는 이미 제한을 다 쓴 뒤다.

**2. 재요청은 같은 요청을 그대로 보낸다.** *"이번엔 JSON 으로 답하라"* 같은 교정 문구를 붙이지 않는다 — 그것은 `SYSTEM` 과 `OUTPUT SPEC` 밖에서 프롬프트를 바꾸는 아홉 번째 레이어이며 I-7 이 금지하는 형태다. 형식을 못 맞춘 원인이 프롬프트에 있다면 고칠 곳은 `OUTPUT_SPEC`(B-20)이지 재요청 경로가 아니다.

**3. R5.3(문단 3~5 · 120자)은 파서의 거부 조건이 아니다.** 원문이 **"프롬프트로 강제"** 라고 주체를 지정했고 `OUTPUT_SPEC` 이 이미 그 문장을 싣는다. 서버가 여기에 더해 거부까지 하면 문단이 여섯인 정상 본문이 25초짜리 재생성을 부른다. **길이는 취향이고 구조는 계약이다** — 거부하는 것은 R5.1(본문이 배열이 아니다)뿐이다.

**4. R5.4(선택지 1~4)는 상한과 하한의 처리가 다르다.** 원문의 *"서버가 절단하거나 재요청"* 을 그대로 나눈다 — 4 초과는 **버릴 것이 있으므로 절단**(`order` 순 앞의 넷), 0 개는 버릴 것이 없으므로 **거부**한다. 선택지 0 개는 사용자가 아무것도 못 하는 화면이다.

### 13-20. `[정정]` B-11 의 복귀 조건이 의존과 모순된다

`docs/tasks.md` 가 B-11 을 두 곳에서 말하는데 **둘이 서로 맞지 않는다.**

| 위치 | 내용 |
|---|---|
| `tasks.md:42` (§12 작업 목록) | B-11 의 **의존 = `B-05-1`** |
| `tasks.md:247` (제외한 작업과 복귀 조건) | B-11 의 **복귀 조건 = "B-22 착수 시"** |

**B-05-1 은 #20 이고 선행이 성립하지 않은 상태였다.** `promptlog` 스토어에 엔티티가 생기려면 스토어별 EntityManagerFactory 4벌이 먼저 있어야 한다. 즉 *"B-22 착수 시 B-11 을 복귀한다"* 는 **실행할 수 없는 지시**였고, B-22(#91)를 실제로 착수해 확인했다.

**정정 — 실행 가능한 조건으로 다시 쓴다.**

> **B-11 복귀 조건: `#20`(B-05-1) 이 해소된 뒤.** B-22 가 붙으면 필요해지지만 그것이 착수 신호는 아니다. 실제 순서는 **`#20`(B-05-1) → `B-11` → `B-25`** 이며, `tasks.md:66` 의 B-25 의존(`B-11, B-18`)은 이 순서와 이미 맞다.

**`tasks.md` 원문을 고치지 않는다.** Source of Truth 는 이 문서가 상위 문서를 정정한다고 정했고(§0), 충돌하면 정정본이 이긴다. 계획 문서를 직접 덮어쓰면 어느 쪽이 진실인지가 다시 흐려진다.

#### 그 사이에 무엇이 없는가 — 이 정정의 실질

B-22 가 머지되면서 **실 Provider 가 붙었다.** 그런데 `ai_call_log` 가 없으므로:

- **요청·응답 원문이 어디에도 남지 않는다.** 구조화 로그만 남고 원문은 남기지 않는다 (S-3 — 애플리케이션 로그에 원문 금지, 원문은 `ai_call_log` 만 보관)
- **모델이 이상한 이야기를 써도 그 원문을 사후에 볼 수 없다.** dev 콘솔로 재현하는 수밖에 없다
- `usage` · latency · cost 가 기록되지 않아 **§13-18 이 계수 조정의 근거로 지목한 B-48 의 오차 관측**과 **§13-19 가 예산 배분 재검토의 근거로 지목한 B-46 의 지연 실측**이 아직 시작되지 않는다

**결함이 아니라 순서의 결과다.** 다만 그 사실이 문서 어디에도 없어서 읽는 사람은 *"B-22 하면 로그가 붙는다"* 로 이해하게 된다 — 그 오해를 여기서 닫는다.

### 13-21. `[보완]` 검수를 부를 자리가 Provider 인터페이스에 없다 — **B-30**

§3 의 `StoryProvider` 는 **턴 생성 · 요약 · 아웃라인** 셋에 `capabilities` 를 더한 모양이다. 그런데 R3.6 은 용도를 **넷**으로 나눈다 — 턴 생성 · 요약 · **검수** · 아웃라인. **검수를 부를 메서드가 없다.**

지금까지는 드러나지 않았다. L2 가 규칙 기반 1단(S-8)뿐이라 모델을 부를 일이 없었기 때문이다. B-30 이 R9.2 의 2단(의미 기반 분류)을 얹으면서 그 공백이 실체가 됐다.

**기본 채택안 — `classifySafety` 를 seam 에 더한다.**

대안은 어댑터 밖에 별도 판정 클라이언트를 두는 것인데, 그러면 **벤더별 HTTP·인증·모델 선택 코드가 한 벌 더 생긴다.** 어댑터는 이미 그것을 갖고 있고 용도별 모델도 이미 고른다(B-24). 판정을 그 옆에 두는 것이 복제를 만들지 않는 유일한 자리다.

**I-12 는 메서드 위치가 아니라 모델 분리가 지킨다.** 같은 어댑터가 부르더라도 판정은 `AiPurpose.SAFETY` 로 설정된 모델을 쓰며, 그 값이 없으면 **턴 생성 모델을 빌려 쓰지 않고 실패한다.** 판정 결과의 최종 권한도 모델에 없다 — 차단·재생성 결정은 서버가 `SafetyCategory` 의 정책으로 한다 (§9.2).

#### 함께 정한 것

| 지점 | 원문 | 채택 |
|---|---|---|
| 분류 결과의 형태 | "의미 기반 분류"까지만 | **카테고리 집합만.** 신뢰도·위치를 받지 않는다 — 위치가 필요한 것은 §9.2 의 마스킹 정책 하나이고 그것은 미구현이다. 쓰지 않는 값을 계약에 넣으면 구현마다 그럴듯한 숫자를 지어낸다. **(§13-46 갱신 — 마스킹이 구현된 뒤에도 이 결정은 유지된다. 마스킹은 자리를 아는 1단 탐지에만 붙는다)** |
| 판정 실패의 처리 | 규정 없음 | **차단(fail-closed).** "판정하지 못했다"는 "안전하다"가 아니다. 세이프티에서 fail-open 은 장애가 곧 검수 우회다 (ADR-0002 와 같은 성질) |
| 모르는 카테고리 이름 | 규정 없음 | **판정 실패로 본다.** 무시하면 *"무엇을 봤는지 모르는 상태"* 가 빈 집합, 즉 통과가 된다 |
| 형식 위반 시 재요청 | R5.8 · R3.3 은 **턴 출력** 스키마에 대한 것 | **재요청하지 않는다.** 판정 실패의 처리는 재요청이 아니라 차단이다 |
| 벤더 장애 시 승계 | ADR-0007 은 턴 생성만 다룸 | **승계한다.** 판정 실패가 차단이므로 벤더 하나가 죽으면 모든 턴이 막힌다 — ADR-0007 이 승계를 허용한 조건("벤더가 죽었을 때") 그 자체다. 새 결정이 아니라 같은 결정의 적용이다 |

#### 판정 호출과 예산 — **결정됨 (B-30 3/3)**

§13-19 는 *생성* 예산만 정했다. 판정이 붙으면 한 턴에 외부 호출이 최대 넷이 된다 — 생성 · 판정 · 재생성 · 판정. 각각이 25초 상한을 받으므로 **산술적으로는 §6.3 의 서버 28초를 넘을 수 있다.**

**채택 — 판정은 생성 예산 밖의 별도 호출이며, 자기 상한을 받는다.**

- 판정에만 더 짧은 상한을 새로 두지 않는다. **근거 없는 숫자를 하나 더 만드는 일**이기 때문이다 — 지연 실측은 B-46 항목이고, §13-19 가 소켓 상한 배수 2 에 대해 내린 판단과 같다
- **1단이 즉시차단이면 2단을 부르지 않는다.** 판정 호출이 실제로 몇 번 일어나는지는 정책이 줄인다 (§9.2)
- **재생성은 여전히 1회뿐**이므로 호출 수의 상한 자체는 유한하다

**남는 것은 "턴 전체를 하나의 deadline 으로 묶는 일"이며, 그것은 이 작업의 범위가 아니다.** #87 이 *생성*에 대해 한 일을 *턴 전체*에 대해 해야 하고, 그 자리는 서버 응답 예산(§6.3)을 다루는 작업이다 — **후속 이슈 #116 으로 올렸다.** 지금 지켜지는 것은 "모든 외부 호출에 상한이 있다"이며, "턴 하나가 28초를 넘지 않는다"는 아직 값으로 강제되지 않는다. 그 사실을 여기 적어 두는 이유는, 적지 않으면 §13-19 를 읽은 사람이 **28초가 이미 지켜진다고 이해하기 때문**이다.

### 13-22. `[보완]` API 계약을 파일로 확정하면서 정한 것 — **B-06**

§13 은 **엔드포인트와 응답 예시**를 준다. 요청 본문·에러 매핑·식별자 표기는 대부분 규정되어 있지 않아, 파일로 옮기는 순간 정해야 했다. 정한 것을 여기 남긴다 — 적지 않으면 다음 사람이 *"§13 에 그렇게 쓰여 있다"* 고 읽는다.

#### 계약이 구현보다 넓다 — 그것이 계약 우선의 정상 상태다

`docs/openapi.yaml` 은 §13 **전체**를 담는다. 아직 구현되지 않은 엔드포인트(§13.8 작품 만들기 · §13.9 신고 등)와 필드가 먼저 존재한다. 각 자리에 `x-implemented-by` 로 담당 작업 번호를 적었다.

**반대 방향만 결함이다** — 구현에는 있는데 계약에 없는 필드. 그것이 프론트가 모르는 필드이고 계약이 거짓말을 시작하는 지점이다. `OpenApiContractTests` 가 그 방향만 검사한다.

| `/auth/email/*` | §13.1 에 존재 | **계약에 넣지 않는다.** §13-11 채택안이 MVP 를 Google OAuth 하나로 좁혔다. 넣어 두면 "구현되지 않은 약속"이 계약에 남는다 |
| §14 관리자 | 별도 장 | **B-06 범위 밖이다.** B-06 의 완료 조건은 "**13장**의 모든 엔드포인트"다. 관리자 계약은 **B-41 착수 시** 같은 파일에 더한다 |
| 세션 종료·만료 상태에 턴 요청 | §4.3-2 가 코드를 명시하지 않음 | **`403 FORBIDDEN`.** S-9-1 구현이 이미 그렇게 하고 있고 그 근거를 PR 에 남겼다 — `TURN_CONFLICT` 는 "현재 턴으로 맞춰 주세요"라서 맞출 턴이 없는 상황에 맞지 않는다 |
| `servers` | 규정 없음 | **두지 않는다.** 상대 경로로 해석된다. 계약에 필요한 것은 경로이지 호스트가 아니며, 이 파일은 공개된다 (S-11) |

#### 계약 문서의 노출 범위

`docs/openapi.yaml` 자체는 공개 레포에 있다. 그럼에도 런타임 경로(`/openapi.yaml`, swagger-ui)는 **`dev & !prod` 에서만 연다** — 열어 둘 이유가 없는 경로는 열지 않는다. 표현식은 dev 콘솔(B-47)·인증 우회 리졸버(#34)와 같다.

springdoc 의 **런타임 자동 생성본을 계약으로 쓰지 않는다.** 생성본은 구현의 사후 기록이고, 그것을 문서로 내보내는 순간 계약이 둘이 된다. springdoc 은 `swagger-ui.url` 로 수기 파일을 가리키는 **UI** 로만 쓰며, 기본값은 꺼진 상태다(자동설정이 `matchIfMissing = true` 라 명시하지 않으면 열린다).

#### §13-12 와의 관계

검수 샘플링 비율·신고 임계값은 **API 응답 스키마에 넣지 않았다.** 값을 알면 그 아래로 관리할 수 있다 (내부 문서 §13-12, S-11).

### 13-23. `[확정]` 인증 본문 — **B-12** (§13-22 의 `[결정 필요]` 해소)

§13-22 가 인증 요청·응답 본문을 `[결정 필요]` 로 올리고 *"B-12 착수 시 확정한다"* 고 적었다. 그 시점이다.

| 지점 | 확정 |
|---|---|
| **응답** | 계약 그대로 `{ accessToken, refreshToken, tokenType: "Bearer", expiresIn }`. **`playerRef` 를 담지 않는다** — 클라이언트가 알 필요가 없고, 알 필요 없는 값은 로그·에러 리포트·분석 도구로 퍼진다 |
| **요청** | 계약대로 `{ idToken, birthDate?, consents[]? }` 를 유지한다. 다만 **B-12 의 구현은 `idToken` 만 받는다** — `birthDate` · `consents` 를 판정할 코드가 B-13 이고, 받아 두기만 하면 생년월일이 아무 검사 없이 통과한 것처럼 보인다. **B-13 이 두 필드와 그 판정을 함께 더한다** |
| **토큰 클레임** | `sub`(`playerRef`) · `iss` · `iat` · `exp` · `jti` · `token_use`. **회원 식별정보를 담지 않는다** (I-3) — JWT 는 서명될 뿐 암호화되지 않으므로 담은 것은 누구나 읽는다 |
| **토큰 수명** | 액세스 30분 / 리프레시 30일. 원문에 규정이 없다. 리프레시는 세션 만료 90일(R12.4)보다 짧게 잡았다. **설정값이며 B-46 실측 후 조정한다** |
| **리프레시 상태** | 저장소를 두지 않는다. 원문에 즉시 무효화 요구가 없고, 두면 모든 요청 경로에 조회가 하나 붙는다. 재발급은 **두 토큰을 함께 회전**시킨다. **B-62 에서 결론 — 저장소는 여전히 두지 않고, 재발급 시점에만 회원 상태를 확인한다.** 탈퇴·정지 회원은 재발급받지 못하므로 차단은 액세스 토큰의 남은 수명 안에 성립한다. 조회가 붙는 곳은 재발급뿐이라 §13 이 피하려던 비용은 그대로 피한다 |
| **알 수 없는 provider** | `400 VALIDATION_ERROR`. 계약의 `provider` enum 은 `[google]` 하나이므로(§13-11) 목록 밖의 값은 **존재하지 않는 경로가 아니라 보낼 수 없는 값**이다. 계약의 400 예시는 `CONSENT_REQUIRED` 하나지만, 그것은 가입 정보 누락의 경우다 |
| **Google ID 토큰 검증** | 서명(JWKS) · 발급자 · 대상(`aud` = client-id) · 만료 넷을 서버가 본다. 발급자는 `accounts.google.com` 과 `https://accounts.google.com` 둘 다 받는다 — 구글이 두 표기를 쓴다 |
| **이메일** | `oauth_identity.email_hash` 에 SHA-256 만 남긴다. **원문은 검증기 밖으로 나가지 않는다** (I-3, §12) |

### 13-24. `[확정]` 가입 연령 게이트와 동의 — **B-13**

§13.1 은 *"`birthDate` 또는 `consents[]` 누락 → `400 CONSENT_REQUIRED`"* 만 적는다. **무엇이 필수인지, 언제 필요한지, 나이를 어느 시간대로 재는지**는 규정되어 있지 않아 구현하면서 정해야 했다.

| 지점 | 확정 |
|---|---|
| **필수 동의 3종** | `tos` · `privacy` · `ai_notice`. §4.1 이 *"약관·개인정보·AI고지 동의 수집"* 이라고 적은 그대로다. 셋 중 하나라도 `agreed=false` 이거나 없으면 `400 CONSENT_REQUIRED` |
| **`age` 동의** | **사용자가 체크하는 항목이 아니다.** 서버가 생년월일로 판정한 사실을 스스로 기록한다 — *"만 15세 이상입니다"* 에 체크했다는 사실보다 **서버가 확인했다는 사실**이 증빙이다 (R10.2). 판본은 판정 기준을 그대로 쓴다(`age-15`) |
| **언제 필요한가** | **최초 로그인(가입)에만.** 기존 회원은 `idToken` 만 보낸다 — 로그인할 때마다 동의를 다시 받으면 동의 이력이 로그인 이력이 되고 *"언제 무엇에 동의했는가"* 가 흐려진다 |
| **만 나이 기준** | **KST.** 계약이 명시했다. 서버가 어느 시간대에 뜨든 같은 사람이 같은 날 통과해야 한다 — UTC 로 재면 한국 시각 자정~오전 9시 사이에 **생일이 하루 늦게 온다** |
| **생일 당일** | **통과한다.** 만 나이는 생일에 오르므로 그날 이미 15세다. 경계가 하루 어긋나면 그날 가입한 사람이 전부 거부된다 (§10.1-13) |
| **미성년 거부 시** | **계정을 만들지 않는다** (R10.2). `user` · `oauth_identity` · `consent_log` 어느 것도 남지 않는다 — 거부하고 계정만 남기면 나이를 확인받지 않은 회원이 존재하게 된다 |
| **검증 순서** | ID 토큰 검증 → 기존 회원 조회 → 가입 정보 → 연령. **토큰 검증이 가장 앞이다** — 인증되지 않은 요청에 일을 하지 않고, 계정 존재 여부가 응답으로 새지 않는다 |
| **누락 사유의 세분** | **하지 않는다.** 무엇이 빠졌는지 코드로 나누지 않는다 — 클라이언트는 세 항목을 함께 보여 주며, §13.1 이 *"에러는 `code` 를 반환하고 클라이언트가 문구를 매핑한다"* 고 적었다 |
| **`ip_hash`** | `SHA-256(remoteAddr)`. **원문은 컨트롤러 밖으로 나가지 않는다** (§12). 프록시 뒤에서는 `getRemoteAddr()` 이 프록시를 가리키며, 전달 헤더를 신뢰할지는 배포 구성의 문제다 (B-63) |
| **요청 본문의 필수 표시** | `birthDate` · `consents` 에 `@NotNull` 을 걸지 **않는다.** 가입인지 아닌지는 계정을 찾아 봐야 알 수 있고, 걸면 **기존 회원의 로그인이 막힌다** |

**AI 고지 노출 이력(`ai_notice_impression`)은 B-14 다.** 이 작업은 **동의**만 다룬다 — 노출은 동의가 아니다 (§13-8).

### 13-25. `[결정 필요]` 라이브러리에서 정한 것 — **B-15**

§13.2 는 응답 모양을 준다. **장르 목록 · 섹션 구성 · `isNew` 의 기준**은 규정되어 있지 않아, 화면을 만드는 순간 정해야 했다.

| 지점 | 채택 | 근거 |
|---|---|---|
| **장르 목록** | `romance` · `school` · `fantasy` · `action` · `mystery` 다섯 | §13.2 예시에 `genre:romance` 가 나오고, 기획서가 초기 서비스를 *"15세 정도의 일반 로맨스 비주얼노벨 수준 또는 그에 준하는 액션, 판타지, 자극적인 소재"* 로 적는다. **그 문장에서 읽히는 것만** 넣는다 — 목록을 넓히는 것은 기획 결정이고, 빈 섹션을 만드는 것은 그보다 나쁘다 |
| **장르 섹션의 작성자 종류** | **공식 작품만** | R13.1 이 *"두 종류를 같은 섹션에 섞지 않는다"* 고 못박는다. 장르별로 공식·사용자를 각각 두면 섹션이 장르 수의 두 배가 되고 그 화면은 정의되지 않았다. 사용자 작품은 `community` 하나로 모인다 |
| **`isNew` 기준** | 발행 후 **14일** | 라이브러리를 주 단위로 도는 사용자에게 새 작품이 최소 한 번은 새것으로 보이는 길이다. 코드 상수이며 근거가 생기면 바꾼다 |
| **정렬과 커서** | `(published_at DESC, id DESC)` 키셋 | 발행 시각만으로 정렬하면 **같은 시각의 작품들이 쪽 경계에서 겹치거나 사라진다** — 시드처럼 한 번에 넣은 데이터에서 실제로 일어난다 |
| **깨진 커서** | **처음부터** 로 본다 | 해석되지 않는 값에 500 을 내면, 커서 형식을 바꾸는 순간 진행 중인 클라이언트가 전부 깨진다 |
| **모르는 섹션 키** | **빈 섹션으로 흡수하지 않는다** | 흡수하면 오타가 *"작품이 없음"* 으로 보인다 |
| **공식 작품의 승인 조건** | 공식도 `approved` 를 요구한다 | 지금은 전부 승인 상태지만, 조건을 종류별로 다르게 두면 **공식이라는 이유로 검수를 건너뛰는 경로**가 생긴다 (I-8) |
| **조립 모듈** | **`play`** | 화면이 catalog 의 작품과 play 의 진행 중 세션을 함께 담는데, 모듈 의존은 `play → catalog :: query` 한 방향만 열려 있다 (ADR-0006). 반대로 만들려면 SPI 를 하나 더 세워야 하고 그 대가가 이 화면 하나로는 크다 |

### 13-26. `[결정 필요]` 세션 수명과 이어하기에서 정한 것 — **B-17**

§13.4 는 엔드포인트와 `sessionState` 다섯 값을 준다. **판정 순서 · 겹칠 때의 우선순위 · `canViewHistory` · 완료된 세션**은 규정되어 있지 않다.

| 지점 | 채택 | 근거 |
|---|---|---|
| **판정 순서** | `deleted` → `expired` → `story_suspended` → `version_changed` → `valid` | 여러 조건이 동시에 참일 수 있다. **사용자가 할 수 있는 일이 가장 적은 쪽**부터 본다 — 지운 세션에 *"버전이 바뀌었습니다"* 를 안내하면 사용자는 자기가 무엇을 했는지 헷갈린다 |
| **작품이 사라진 경우** | `story_suspended` | 이어갈 수 없다는 사실은 같고, *"없는 작품"* 과 *"정지된 작품"* 을 구분해 알릴 이유가 없다 (I-8 과 같은 판단) |
| **완료된 세션** | `valid` | 다섯 값에 `completed` 가 없다. 엔딩 도달 여부는 `GET /current` 의 `isEnding` 이 답하며, 그 화면은 **다시 그릴 수 있어야 한다** |
| **`canViewHistory`** | `turnNo >= 1` | 조회 자체는 B-35 지만 *"볼 것이 있는가"* 는 지금도 답할 수 있다. `false` 로 고정하면 B-35 가 붙는 날 계약이 조용히 바뀐다 |
| **`lastSceneVisual`** | 항상 `null` | 장면 이미지는 P3 다. **필드는 유지한다** — 계약이 요구하고, 나중에 채우는 것이 형태를 바꾸는 것보다 낫다 |
| **삭제의 의미** | soft delete + `status = abandoned` | `deleted_at` 만 채우면 *"작품당 active 1개"* 인덱스가 지운 세션 때문에 새 세션을 막는다 — 사용자가 보기에는 **지웠는데 다시 시작할 수 없는 상태**다 |
| **삭제의 멱등성** | 두 번 지워도 `204` | 삭제는 **상태를 맞추는 요청**이다. 두 번째 호출이 실패하면 클라이언트가 재시도할 방법이 없다 |
| **남의 세션** | `404` (계약은 `403` 도 적는다) | 존재 여부가 새면 세션 id 를 훑어 다른 사람이 무엇을 하고 있는지 알 수 있다. 턴 요청이 이미 같은 규칙이다 |
| **`GET /current` 의 세션 상태** | **상태를 보지 않는다** | 다시 그리기는 진행 중을 요구하지 않는다 — 끝난 이야기의 마지막 장면이 새로고침에서 사라지면 안 된다 |
| **`endingIndex` 계산 시점** | 조회 시점 | 턴에 남는 것은 **어떤 엔딩에 도달했는가**이고, 그것이 비시크릿 중 몇 번째인지는 **작품 버전이 정한다** (R7.11) |

### 13-27. `[결정 필요]` 고지 문구가 없을 때 랜딩은 무엇을 하는가 — **B-37**

§13.10 은 `noticeText` 를 **필수 필드**로 두고, R11.1 은 그것을 **하드코딩하지 말라**고 한다. 그런데 **설정이 비어 있을 때 무엇을 할지**는 규정되어 있지 않다.

| 후보 | 문제 |
|---|---|
| 빈 문자열 | **고지가 없는 상태가 정상으로 보인다.** §11 은 사전 고지를 의무로 규정한다 |
| 코드의 기본 문구 | **R11.1 위반.** 그 문구가 그대로 운영에 나간다 |
| **500 + 로그** ✅ | 화면이 뜨지 않는다. 대신 **운영 결함이 즉시 드러난다** |

**채택: `500 INTERNAL_ERROR` 와 `log.error`.** §11 의 의무와 R11.1 의 금지를 함께 지키는 방법은 **문구 없이 이 화면을 내보내지 않는 것**뿐이다.

**대가를 적어 둔다** — 설정하기 전에는 랜딩이 뜨지 않는다. 그것이 이 결정의 의도이며, 배포 절차(B-63)에 *"`ai.notice` 를 먼저 넣는다"* 가 들어가야 한다. 알람은 B-48 이다.

> 플레이 경로(B-14 의 노출 이력)는 반대로 **조용히 넘어간다** — 그쪽은 기록이 목적이고 이쪽은 **표시**가 목적이다. 기록을 못 남기는 것과 고지를 안 보여 주는 것은 무게가 다르다.

#### 개정 (2026-09-02, #281) — 플레이도 표시 경로가 됐다

**구분은 그대로다 — "기록이냐 표시냐".** 바뀐 것은 **플레이가 어느 쪽인가**이다.

위 단서는 플레이 경로에서 고지가 하는 일이 **노출 이력을 남기는 것뿐**이라는 전제 위에 있었다. #281 이 `TurnResponse` 에 `noticeText` 를 실으면서 그 전제가 사라졌다 — 플레이 화면의 Footer 도 문구를 상시 표시하므로, 이제 **다른 화면과 같은 규칙을 받는다.**

| 경로 | 고지가 하는 일 | 문구가 없으면 |
|---|---|---|
| 노출 이력 기록 (B-14) | 기록 | **조용히 넘어간다** — 변경 없음 |
| 턴 응답의 `noticeText` (#281) | **표시** | **500** |

**대가가 커졌다.** 전에는 설정을 빠뜨리면 둘러보기 화면만 죽었다. 이제는 **세션 시작·턴 진행·이어하기가 전부 막힌다** — 아무도 플레이할 수 없다. 그것이 이 결정의 의도이며, 배포 절차의 0번 단계(`docs/deployment.md` §3)가 그만큼 더 중요해졌다.

> `AiNoticeExposureIntegrationTests` 의 `R11_1_an_unconfigured_notice_does_not_break_play` 가 **반대를 단언하고 있었다.** #281 이 그 테스트를 `R11_1_play_does_not_start_without_a_configured_notice` 로 다시 썼다 — 문서만 고치고 테스트를 두면 둘 중 하나가 거짓말을 한다.

### 13-28. `[결정 필요]` 일일 한도를 무엇으로 세는가 — **B-38**

§15 는 *"계정당 **일일 토큰 한도**. 초과 시 `429 QUOTA_EXCEEDED`"* 를 적는다. 그런데 **토큰 수를 계정별로 셀 방법이 없다.**

`ai_call_log` 가 토큰을 갖지만 **`player_ref` 를 담지 않는다** — I-3 이 그것을 금지하고, §2.7 이 *"session_id 로만 역추적한다"* 고 적었다. 계정별 합계를 내려면 promptlog → play 를 가로지르는 조인이 필요하고, 그것은 §5.3 이 막는 것이다.

| 후보 | 문제 |
|---|---|
| `ai_call_log` 를 계정별로 집계 | **I-3 위반.** 그 표에 `player_ref` 를 넣어야 한다 |
| 턴마다 사용량을 Redis 에 적립 | 사용량을 아는 것은 `ai` 이고 `playerRef` 를 아는 것은 `play` 다. 둘을 잇는 값이 없다 (ADR-0006) |
| **일일 턴 수로 대리** ✅ | 정확하지 않다. 대신 **어떤 경계도 넘지 않는다** |

**채택: 계정당 일일 `턴 수` 한도.** 턴당 토큰이 프롬프트 예산(§4.3)으로 상한이 있으므로 **턴 수가 토큰의 상한을 규정한다** — 정확한 값이 아니라 **상한**이며, 비용 통제의 목적에는 그것으로 충분하다.

**정확한 토큰 한도가 필요해지는 시점**은 원가 관리(B-48 의 비용 대시보드)가 붙을 때다. 그때는 계정이 아니라 **세션 단위 집계**로 접근해야 한다 — `ai_call_log` 는 세션까지만 알고, 세션은 play 가 계정과 잇는다. 즉 **경계를 지키면서도 가능한 경로가 있으며, 지금 그것을 만들 이유가 없을 뿐이다.**

#### 함께 정한 것

| 지점 | 채택 |
|---|---|
| **고정 창** | 창 경계에서 최대 두 배가 통과한다. 슬라이딩 창은 값 하나가 아니라 목록이 필요하고, 여기서 막으려는 것은 **정밀한 분포가 아니라 폭주**다 |
| **하루 창** | 자정이 아니라 **24시간 고정 창**이다 — 시간대 논쟁을 만들지 않는다 |
| **판정 순서** | 일일 → 분당. 오늘 다 쓴 사용자에게 *"조금 늦춰 주세요"* 를 안내하면 그 안내대로 해도 통과하지 못한다 |
| **멱등 예약보다 앞** | 한도에 걸린 요청이 예약을 잡으면 그 키가 TTL 동안 남아 **한도가 풀린 뒤에도 같은 요청이 막힌다** |
| **`retryAfterSeconds`** | 세 종류 모두에 준다. 없으면 클라이언트가 즉시 재시도하고, 한도는 트래픽을 줄이는 것이 아니라 **실패를 늘리는 장치**가 된다 |
| **IP 는 해시로** | 키에 원문을 넣으면 **Redis 가 접속자 목록이 된다** (§12) |

### §13-29 관리자 2FA — 방식과 값 `[결정 필요]`

R14.6 은 관리자에게 2FA 를 요구한다고만 적는다. **방식·코드 수명·재사용 방지·복구 절차는 원문에 없다.** 아래는 기본 채택안이며, 원문이 다르게 정하면 그쪽이 이긴다.

#### 채택: TOTP (RFC 6238)

| 후보 | 문제 |
|---|---|
| SMS / 이메일 코드 | **전달 경로가 하나 더 생긴다.** 그 경로 자체가 공격면이고, 발송 실패가 곧 관리자 잠김이다 |
| WebAuthn | 강하지만 **기기 등록·복구 절차가 통째로 따라온다.** 관리자 수가 한 자리인 단계에서 감당할 표면이 아니다 |
| **TOTP** ✅ | 서버 밖으로 나가는 것이 없다. 인증기 앱은 이미 사람들이 갖고 있다 |

#### 함께 정한 것

| 지점 | 채택 | 이유 |
|---|---|---|
| **알고리즘·자리·주기** | HMAC-SHA1 · 6자리 · 30초 | 인증기 앱의 사실상 표준이다. 다르게 잡으면 **사용자 앱이 만드는 코드와 서버가 기대하는 코드가 어긋난다** |
| **검증 창** | 앞뒤 1스텝 (총 90초) | 0 이면 시계 오차와 입력 시간 때문에 정상 사용이 자주 실패한다. 넓힐수록 **동시에 유효한 코드가 늘어난다** |
| **재사용 방지** | 통과한 스텝을 기록하고 그 이하를 거절 | 코드는 30초 동안 같다. 어깨너머로 본 여섯 자리가 그 창 안에서 재사용된다 |
| **두 걸음 등록** | 비밀 발급 → 코드로 확정 | 한 걸음이면 QR 을 잘못 찍은 관리자가 **다음 로그인에 가서야** 그 사실을 안다. 그때는 이미 잠겼다 |
| **비밀 보관** | AES-GCM 으로 감싸 저장 | 평문이면 DB 덤프 하나가 두 번째 인증 요소를 무력화한다. 감추기만 하는 방식은 **고쳐 쓸 수 있어** 공격자가 자기 비밀을 심는다 |
| **키 분리** | 서명 키와 다른 키 | 서명 키는 위조를, 이 키는 읽히는 것을 막는다. 하나를 갈 때 다른 하나까지 갈면 그 사이 발급된 토큰이 함께 죽는다 |
| **실패 응답** | 등록 없음·확정 전·코드 불일치·재사용을 **구분하지 않는다** | 어느 단계에서 어긋났는지가 곧 단서다 (S-6) |

#### 이번 범위 밖

- **복구 코드.** 인증기를 잃은 관리자를 되돌리는 절차다. 지금은 운영에서 등록을 지우는 것으로 대신하며, 자동화가 필요해지는 시점은 관리자가 여럿이 되는 때다.
- **관리자 계정 승격 경로.** 코드에도 마이그레이션에도 없다 (S-11).

### §13-30 재생성이 하는 일 `[결정 필요]`

§14 는 `POST /admin/sessions/{id}/turns/{turnNo}/regenerate` 를 적었을 뿐, **무엇을 다시 하는지**를 규정하지 않는다. 아래는 기본 채택안이며, 원문이 다르게 정하면 그쪽이 이긴다.

#### 채택: 되돌린 뒤 같은 파이프라인으로 다시 만든다

| 후보 | 문제 |
|---|---|
| 저장된 본문만 손으로 고친다 | 다시 만드는 것이 아니다. **AI 가 무엇을 내놓는지**를 보려는 것이 재생성의 목적인데 그 목적을 달성하지 못한다 |
| 관리자용 생성 경로를 따로 둔다 | 두 곳이 서서히 갈라진다. 그러면 **디버그에서 본 것이 사용자가 겪는 것과 달라진다** |
| **되돌리기 + §4.3 파이프라인** ✅ | AI 를 다시 부른다 — 비용과 비결정성이 따라오지만, 그것이 재생성의 내용이다 |

#### 함께 정한 것

| 지점 | 채택 | 이유 |
|---|---|---|
| **선택은 그대로** | 직전 턴에 기록된 `chosenChoiceId` 를 다시 쓴다 | 재생성은 *그 선택에서 다른 본문*을 보는 것이다. 선택을 바꾸면 그것은 재생성이 아니라 **새 진행**이다 |
| **순서는 서버가 되찾는다** | 저장된 선택지 JSON 에서 `order` 를 읽는다 | I-1 — 클라이언트가 보낸 것을 신뢰하지 않는다는 규칙은 관리자 경로에서도 같다 |
| **되돌리기가 먼저** | 접고 나서 만든다 | 순서를 뒤집으면 같은 턴 번호가 둘이 되고, 그 순간 `turn_no` 는 낙관적 잠금의 키이기를 그만둔다 (I-6) |
| **선택 기록이 없으면 거절** | `INVALID_CHOICE` | 그 턴은 **아직 진행되지 않은 것**이다 — 다시 만들 대상이 아니다 |
| **결과가 같을 수 있다** | 다른 본문을 약속하지 않는다 | AI 호출은 비결정적이지만 그것은 성질이지 보장이 아니다 |
| **차단되면 되돌린 자리에 남는다** | 세이프티에 걸린 본문은 저장되지 않는다 (I-2) | 접기는 이미 끝났으므로 세션은 `turnNo - 1` 에 머문다. 관리자는 다시 시도하거나 그대로 둔다 |
| **본문을 응답에 담지 않는다** | 턴 번호·챕터·차단 여부만 | 담으면 이 경로가 *고치기*이면서 *보기*가 된다. 본문은 디버그를 다시 부른다 |

#### 이번 범위 밖

- **재생성 횟수 제한.** AI 를 부르므로 비용이 든다. 지금은 관리자 수가 한 자리이며 세 조건 뒤에 있다 — 한도가 필요해지는 시점은 관리자가 여럿이 되는 때다.

### §13-31 블록리스트 — 종류·심각도·갱신 `[결정 필요]`

§2.4 는 `blocklist_entry` 의 컬럼을 규정하지만, 그 값들이 **세이프티 판정과 어떻게 이어지는지**는 적지 않는다. `kind` 는 네 종류이고 `SafetyCategory` 는 일곱인데 둘 사이의 대응이 없다. `severity` 와 `SafetyPolicy` 도 별개의 축이다.

#### 채택 1 — 종류를 분류로 옮긴다

| `kind` | `SafetyCategory` | 이유 |
|---|---|---|
| `real_person` | `REAL_PERSON_HARM` | 그대로 대응한다 |
| `ip_title` · `character` | `IP_REPLICATION` | 작품명이든 인물명이든 **막는 이유는 하나**다 |
| `phrase` | `RATING_EXCEEDED` | 포괄 항목. 15세 등급을 넘는 표현이 여기로 온다 |

**둘을 한 값으로 합치지 않는다.** 종류는 *그것이 어떤 것인가*이고 분류는 *왜 막는가*다 — 합치면 관리 화면에서 항목을 정리할 수 없고, 반대로 판정기가 알 필요 없는 것을 알게 된다.

`phrase` 를 더 잘게 나누지 않는 이유는 **운영자가 어디에 넣을지 매번 고민하게 되기 때문**이다. 필요가 실제로 생기면 그때 늘린다.

#### 채택 2 — `warn` 은 판정으로 나가지 않는다

판정기는 걸린 항목을 **곧바로 차단**으로 다룬다. 경고 항목을 함께 내보내면 **경고가 차단이 된다.**

경고 항목의 자리는 작성 중 안내(L0 precheck, B-50)다 — 거기서는 막지 않고 알려 준다. 그래서 SPI 조회는 `severity = 'block'` 만 돌려준다.

#### 채택 3 — 스냅샷 + 수명 + 명시적 무효화

판정은 **매 턴** 일어난다. 매번 DB 를 때리면 호출 비용이 그대로 턴 지연이 된다 (ADR-0002 가 캐싱을 구현의 책임으로 둔 이유).

| 지점 | 채택 | 이유 |
|---|---|---|
| **쓰기 시 무효화** | 등록·삭제가 스냅샷을 버린다 | 등록한 항목이 다음 판정부터 걸리지 않으면, **운영자는 등록했다고 믿는데 서비스는 통과시킨다** |
| **수명 1분** | 무효화와 별개로 스냅샷이 늙는다 | 인스턴스가 여럿이면 등록을 받은 쪽만 즉시 갱신된다 — 수명이 **그 간극의 상한**이다 |
| **미리 채우지 않는다** | 무효화는 지우기만 한다 | 채우려면 쓰기 트랜잭션 안에서 읽어야 하고, 그러면 **커밋 전의 목록**이 캐시에 앉는다 |
| **실패 시 옛 스냅샷을 쓰지 않는다** | 예외를 그대로 올린다 | 못 읽는 상태에서 오래된 목록으로 통과시키는 것은 *"읽을 수 없다"* 를 *"괜찮다"* 로 바꾸는 일이다 (ADR-0002 fail-closed) |

**공유 신호(예: Redis pub/sub)로 바꾸는 시점**은 배포 형태가 정해질 때다 (B-63). 지금 넣으면 인스턴스가 하나인 채로 복잡도만 는다.

### §13-32 원고 개수 상한 `[결정 필요]`

R8.12 는 *"계정당 일일 `draftOutline` 호출 수, 미리보기 턴 수, **작품 개수 상한**을 둔다"* 고만 적고 값을 정하지 않는다.

**채택: 작성 중인 원고 10개.**

작성 중인 원고가 열 개를 넘는 상태는 **쓰고 있는 것이 아니라 쌓아 둔 것**이다. 그리고 상한이 낮은 쪽의 실수는 되돌리기 쉽다 — 지우면 자리가 난다. 반대 방향의 실수(상한이 없거나 높음)는 **한 계정이 저장소를 채우고 나서야** 드러난다.

**발행된 작품의 개수 상한은 이 값과 다르다.** 그것은 B-56(게시)의 것이며, 원고는 지우면 사라지지만 작품은 남는다 — 같은 값을 쓸 이유가 없다.

`draftOutline` 호출 수와 미리보기 턴 수는 B-60 이 정한다.

### §13-33 precheck 의 자리(span)와 상태 `[결정 필요]`

R8.2 는 응답이 **위반 위치(`span`)** 를 담는다고 적지만, 그 위치를 **어떻게 구하는지**는 정의하지 않는다. 그리고 R2.5 와 정면으로 부딪친다.

#### 문제

대조는 **정규화 값끼리** 한다 (R2.5). 그런데 밑줄은 **원문 위치**에 그어야 한다 — 공백을 지우고 유사 문자를 치환하고 자모를 분해한 뒤의 인덱스는 원문의 인덱스가 아니다.

#### 채택: 글자마다 정규화해 자리를 따라가되, **대조 값은 통짜 정규화의 것**

| 지점 | 채택 | 이유 |
|---|---|---|
| **자리 추적** | 원문 글자 하나씩 정규화해 결과 문자마다 출처 인덱스를 남긴다 | 정규화 결과의 어느 구간이 원문의 어디에서 왔는지를 그렇게만 알 수 있다 |
| **대조 값** | 언제나 `TextNormalizer.normalize(전체)` | 글자별 결과를 대조에 쓰면 **판정기와 갈라진다** — 여기서 통과한 것이 제출 뒤 검수에서 걸리면 작성 중 피드백은 **거짓 안심**이 된다 |
| **둘이 다르면** | 자리 추적을 포기하고 **필드 전체**를 가리킨다 | NFKC 는 글자를 넘어 합성할 수 있다. 밑줄이 넓어질 뿐 **놓치지는 않는다** — 반대 방향(자리는 정확한데 못 잡음)이 훨씬 나쁘다 |
| **같은 항목의 반복** | 자리마다 하나씩 남긴다 | 밑줄은 자리에 긋는 것이므로, 두 번째 등장을 빼면 **그 자리는 고쳐지지 않는다** |

#### 채택 2 — `warned` 를 지금 만들지 않는다

`safety_state` 는 세 값이지만 precheck 가 만드는 것은 `clean` 과 `blocked` 뿐이다.

경고 항목(`blocklist_entry.severity = 'warn'`)은 판정으로 나오지 않으며(§13-31), 그것을 precheck 에서만 되살리면 **두 곳이 서로 다른 목록을 보게 된다.** `warned` 를 만드는 자리는 경고 항목을 실제로 쓰기 시작할 때다.

#### 채택 3 — 저장하는 findings 에 원문도 항목도 넣지 않는다

`story_draft.safety_findings` 는 원고와 함께 보관되고 검수자가 읽는다. 거기에 걸린 항목이 남으면 **그 표가 우회 사전**이 된다 (R8.7, S-11). 남기는 것은 필드·자리·분류까지다.

### §13-34 초안 호출 상한 `[결정 필요]`

R8.12 는 *"계정당 일일 `draftOutline` 호출 수"* 상한을 두라고만 하고 값을 정하지 않는다.

**채택: 하루 20회.**

초안은 **세계관을 고쳐 가며 다시 부르는** 것이다 — 한 번 받아 그대로 쓰는 값이 아니므로 하루 몇 번으로는 부족하다. 반대로 수십 번이면 그것은 작성이 아니라 **뽑기**이며, 그 비용은 플랫폼이 부담한다 (R8.12).

**일 단위 창이다** (§13-28 과 같은 이유) — 자정이 아니라 24시간 고정 창이며 시간대 논쟁을 만들지 않는다.

미리보기 턴 수의 상한은 B-53 · B-60 이 정한다.

### §13-35 조건 템플릿 목록 `[결정 필요]`

R7.16 은 *"플랫폼이 제공하는 조건 템플릿(호감도 임계 / 플래그 보유 / 턴 수)에서 선택·조합하게 한다"* 고 적지만, 그 목록의 정확한 구성은 정하지 않는다.

**채택: 넷.** `affinity_at_least` · `has_flag` · `lacks_flag` · `turn_at_least`.

R7.16 이 든 셋에 **`lacks_flag`** 를 더한다 — *"그 일이 일어나지 않았다면"* 은 분기의 절반이며, 없으면 작성자가 플래그를 뒤집어 쓰는 우회를 만든다.

**§4.5 · §4.6 의 조건 문법 전부를 노출하지 않는다.** DSL 을 열면 두 가지가 따라온다 — 아무도 못 쓰는 화면이 되거나, 쓸 수 있는 사람이 **조건 평가기의 미정의 동작**을 찾아낸다. 필요가 실제로 생기면 그때 늘린다.

### §13-36 미리보기의 턴 상한을 어디에 두는가 `[결정 필요]`

R8.13 은 미리보기를 *"3턴 후 자동 종료"* 한다고 적지만, 그 3 을 **어디에 두는지**는 정하지 않는다.

**채택: `play_session.turn_limit` 컬럼.**

코드 상수로 두지 않은 이유는 **`is_test_session` 인 세션이 미리보기만이 아니기 때문**이다 — 관리자 디버그 세션(B-43)도 같은 플래그를 쓰며, 그쪽을 3턴에 끊으면 디버그가 되지 않는다.

| 지점 | 채택 | 이유 |
|---|---|---|
| **비어 있으면 상한 없음** | 기존 세션 전부가 그 상태다 | 마이그레이션이 기존 행을 건드리지 않는다 |
| **서버가 막는다** | 턴 경로의 가드에서 `403` | 상한을 클라이언트에 맡기면 그것은 상한이 아니라 **안내**다 |
| **세션은 살아 있다** | 상태를 바꾸지 않는다 | 기록은 계속 읽혀야 한다 — 작성자가 방금 본 것을 다시 못 보면 미리보기의 의미가 없다 |
| **상한을 응답에 알린다** | `turnLimit` | 모르면 작성자는 네 번째 턴에서 **왜 막혔는지**를 403 으로 처음 겪는다 |

### §13-37 미리보기가 만드는 작품 `[결정 필요]`

§13-5 는 미리보기 때 `story` 를 만들고 임시 버전을 발행한다고 정했다. 남은 물음 둘.

**기본 엔딩을 어디서 얻는가.** 작성자의 엔딩 목록에 기본이 없으면 세션이 끝나지 못한다 (R7.7). 마지막 항목을 기본으로 삼는 대신 **따로 하나를 더한다** — 작성자가 쓴 엔딩을 조건 없는 폴백으로 바꿔 버리면 그 엔딩은 **아무 조건에서나** 나오고, 작성자는 자기가 쓰지 않은 분기를 보게 된다.

**다시 부르면 작품이 늘어나는가.** 늘어난다 — 미리보기마다 새 작품을 발행한다. `private`·`draft` 이므로 아무에게도 보이지 않지만, **쌓이는 것은 사실**이다. 그래서 일일 횟수 상한(10회)을 함께 둔다 (R8.12). 쌓인 미리보기 작품의 파기는 **B-61** 이 가져간다 — 보관 주기 정책이 그쪽에 있다.

**얼마나 두는가** `[결정 필요]` — 원문은 이 기간을 정하지 않았다. **기본 채택안은 30일**이며 `app.retention.preview-story-days` 로 설정한다 (B-61).

- **원고가 아니라 그 사본이다.** 작성자의 원고는 `story_draft` 에 그대로 남고, 미리보기는 그것을 발행해 본 결과다 — 다시 보고 싶으면 일일 상한 안에서 다시 부르면 된다. **보관이 지켜 주는 것은 원고가 아니라 "지금 확인 중인 것"뿐이다.**
- **세션 만료 기간(90일)을 재사용하지 않는다.** 근거가 다르다 — 무활동 만료는 *사용자가 돌아올 수 있는 기간*이고 이쪽은 *아무도 열지 않는 사본이 쌓이는 기간*이다. 한 값으로 묶으면 둘 중 하나를 바꿀 때 나머지가 함께 움직인다.
- **판별은 `author_type='user'` + `private` + `draft` 다.** 제출 경로는 발행과 같은 트랜잭션에서 검수 상태를 옮기므로 이 조합으로 남는 것은 미리보기뿐이다. 파기 직전에 조건을 다시 확인한다 — 그 사이에 작성자가 제출했으면 **검수를 기다리는 작품을 지우게 된다.**
- **세션을 먼저 지운다.** 작품이 사라지면 그 위의 미리보기 세션은 읽을 수 없는 기록이 되고, 순서를 뒤집으면 그 세션을 찾을 근거도 함께 사라진다.

### §13-38 자동 검수가 미리보기 출력을 다시 보는가 `[결정 필요]`

R8.5 는 자동 검수 대상을 *"전 필드 + 챕터/엔딩 초안 + **미리보기 3턴 출력**"* 으로 적는다. 그런데 미리보기 출력은 **이미 L2 를 지났다** — 파이프라인이 만든 모든 본문이 그렇다 (I-2).

**채택: 제출 시 미리보기 출력을 다시 보지 않는다.**

| 후보 | 문제 |
|---|---|
| 미리보기 턴을 다시 검사 | 같은 텍스트를 두 번 본다. 그리고 **두 판정이 갈라질 수 있다** — L2 를 통과한 본문이 제출에서 걸리면, 그 본문은 이미 작성자에게 보여진 뒤다 |
| **보지 않는다** ✅ | L2 가 이미 막았다. 막지 못한 것은 제출 검수도 막지 못한다 — 같은 블록리스트를 본다 |

**R8.5 의 의도는 "미리보기 출력이 검수를 피해 가지 않게" 하는 것**으로 읽는다. 그 성질은 이미 성립한다 — 미리보기는 정규 파이프라인을 타므로 (B-53) 모든 턴이 L2 를 지난다.

**다시 봐야 하는 시점은 블록리스트가 갱신됐을 때**이며, 그것은 사후 재스캔(B-59)의 일이다.

### §13-39 인간 검수 통과가 여는 가시성 `[결정 필요]`

R8.6 은 `public` 이 인간 검수를 거친다고 적고, R8.8 은 승인 후 버전을 발행한다고 적는다. 그러나 **승인이 어느 가시성을 여는지**는 적지 않는다 — 검수를 기다리는 동안 작품은 `private` 이므로 (B-54), 목표 가시성을 어딘가에서 얻어야 한다.

**채택: 인간 검수 통과는 `public` 을 연다.**

인간 검수 큐에 들어오는 길이 **`public` 제출 하나뿐이기 때문**이다 (R8.6). 목표 가시성을 따로 저장하지 않고도 답이 하나로 정해진다.

| 후보 | 문제 |
|---|---|
| `story` 에 목표 가시성 컬럼을 더한다 | 지금 답이 하나인 값을 위해 컬럼과 CHECK 를 늘린다. 값이 둘 이상이 될 때 더해도 늦지 않다 |
| 검수 중에도 `visibility` 를 `public` 으로 두고 `review_status` 로만 가린다 | 두 컬럼 중 하나만 보는 조회가 하나라도 생기면 **검수 중인 작품이 새어 나온다** (I-8) |
| **승인은 `public` 을 연다** ✅ | 큐에 오는 경로가 하나이므로 성립한다 |

**B-59 가 이 전제를 바꾼다.** 사후 샘플링(R8.11)과 블록리스트 재스캔(R9.4)은 **이미 승인된 작품**을 큐에 올리며, 그중에는 `unlisted` 도 있다. 그때는 큐 항목이 목표 가시성을 함께 날라야 한다 — 그러지 않으면 재검수 통과가 `unlisted` 작품을 조용히 공개한다.

**`hold` 는 상태를 바꾸지 않는다.** 큐에 남고 이력만 남는다 — "봤고 판단을 미뤘다"는 아무도 보지 않았다와 다른 사실이며, 얼마나 오래 미뤄져 있었는지는 그 기록으로만 답할 수 있다.

**검수자의 `note` 는 작성자에게 가지 않는다** (R8.7, S-11). 작성자가 보는 것은 카테고리뿐이다. 사람이 쓴 설명에는 걸린 표현이 그대로 들어가며, 그것이 곧 우회 사전이 된다 — 그래서 `reasons` 는 자유 문자열이 아니라 카테고리 열거형만 받는다.

### §13-40 재제출은 무엇을 만드는가 `[결정 필요]`

R8.8 은 *"이후 수정은 새 버전이 되며 재검수를 거친다. 진행 중 세션은 기존 버전을 계속 참조한다"* 이지만, **재검수 동안 이미 승인된 작품이 어떻게 되는지**는 적지 않는다.

**채택: 재제출은 같은 작품에 새 버전을 얹고, 그 작품을 다시 검수 대기로 되돌린다.**

원고가 `story_id` 를 기억하므로(B-54) 두 번째 제출부터는 `publishRevision` 이다. 새 작품을 만들면 두 가지가 따라온다 — **같은 이야기가 라이브러리에 둘**이 되고, 도달률은 `(story_id, ending_no)` 로 집계되므로 **통계가 갈라진다**.

**진행 중 세션은 흔들리지 않는다** (R2.1, I-4, §10.1-12).

| 시점 | 세션이 보는 것 |
|---|---|
| 새 버전 발행 | 옛 버전 — 아직 현재가 아니다 |
| 승인 후 `markCurrent` | **여전히 옛 버전** — 세션은 생성 시 고정됐다 |
| Resume | `version_changed` 로 알린다 (R2.1) |

#### 대가 — 재검수 중에는 라이브러리에서 내려간다

R2.3 은 타인 조회 조건을 `review_status = 'approved'` **AND** `visibility <> 'private'` 로 정한다. 재제출이 `review_status` 를 되돌리므로, **승인돼 있던 작품이 재검수 동안 목록에서 사라진다.** 작성자가 오타 하나를 고쳐도 그렇다.

| 후보 | 문제 |
|---|---|
| `story_version` 에 검수 상태 컬럼을 더한다 | 구조적으로는 이쪽이 맞다. 그러나 스키마·검수 큐·승인 경로를 함께 바꾸며, **그 비용을 지금 치를 근거가 없다** — UGC 는 아직 열리지 않았다 |
| `review_status` 를 그대로 두고 "현재가 아닌 최신 버전"을 큐가 찾는다 | 스키마는 안 바뀌지만, **반려된 개정판이 큐에 영원히 남는다** — 최신 ≠ 현재 상태가 해소되지 않는다 |
| **작품 단위로 되돌린다** ✅ | 진행 중 세션은 영향받지 않는다. 내려가 있는 동안 새로 시작할 수 없을 뿐이다 |

**UGC 정식 오픈 전에 다시 본다.** 검수 SLA 가 정해지면 "내려가 있는 시간"이 실측값이 되고, 그때 버전 단위 검수 상태의 필요가 판단된다 (§16).

#### 기본 엔딩 하한 (#54, R2.11)

**`markCurrent` 가 그 자리다.** 상한("2개 이상 금지")은 partial unique index 가 잡지만 하한("0개 금지")은 **행의 부재**라 CHECK 가 볼 수 없고, 트리거로 막으면 엔딩을 아직 만들지 않은 `draft` 라는 **정상 상태까지 거부**한다.

작품이 **플레이 가능해지는 순간**이 R2.2 의 방지 목적("엔딩 없이 무한히 진행되는 세션")이 실제로 의미를 갖는 유일한 시점이다. 위반은 조용히 넘기지 않고 거절한다 (S-7).

### §13-41 신고가 무엇을 내리는가 `[결정 필요]`

§13.9 는 `targetType` 으로 `turn` 과 `story` 를 모두 받지만, R8.9 의 자동 정지 대상은 **작품**이다. 둘을 어떻게 잇는지는 정해져 있지 않다.

**채택: 작품 신고만 정지 임계에 센다.**

두 가지 이유다.

**모듈 경계.** 턴 신고에서 작품을 알아내려면 `authoring` 이 `play` 의 세션 표를 읽어야 한다 — 스토어가 다르고 (§5.3) 그 참조는 애플리케이션 레벨에서도 열려 있지 않다.

**세는 대상이 다르다.** 세 사람이 서로 다른 턴을 신고한 것과 세 사람이 **그 작품**을 신고한 것은 다른 사실이다. 턴은 한 사람의 플레이에서 생성된 텍스트이지 작품이 아니며, 그것을 작품의 문제로 합산하면 **AI 가 한 번 어긋난 것으로 작품이 내려간다.**

턴 신고는 기록되고 **사후 검수(B-59)의 재료**가 된다.

#### 임계값을 어디에 두는가

**`service_config` 다** (§13-12). 코드에 두지 않는다 — 오탐이 몰리거나 큐가 감당되지 않을 때 재배포를 기다릴 수 없고, 값을 알면 그 아래로 관리할 수 있다 (S-11).

**설정이 없으면 내리지 않는다.** 임의의 기본값을 코드에 두면 그 값이 곧 정책이 되고, 아무도 그것을 정한 적이 없다. 0 으로 읽는 것은 더 나쁘다 — 신고 한 건도 없이 내려간다.

#### 정지에서 돌아오는 길

정지는 `review_status` 만 바꾸고 **`visibility` 는 건드리지 않는다.** 그래서 사람이 통과시킬 때 돌려놓을 자리가 남아 있다 — 신고 하나로 내려간 `unlisted` 작품이 복귀하면서 공개되면 그것은 복귀가 아니다.

§13-39 가 `in_review` 통과를 `public` 으로 정한 것과 **다른 갈래**다. 어디서 왔는지가 답을 정한다.

| 온 자리 | 통과가 여는 가시성 |
|---|---|
| `in_review` | `public` — 그 상태로 오는 길이 `public` 제출 하나뿐이다 (§13-39) |
| `suspended` | **내려가기 전 그대로** — 그 값이 아직 있다 |

#### 정지된 작품은 검수 큐에 오른다

R8.9 가 *"자동으로 `suspended` 전환하고 검수 큐에 올린다"* 고 적는다. B-55 의 큐는 `in_review` 만 보고 있었으므로 `suspended` 를 함께 본다 — **큐에 오르기만 하고 판정할 수 없으면 그것은 큐가 아니다.**

자동으로 내린 것을 자동으로 올리지 않는 것이 요점이다. 그러지 않으면 신고가 곧 판정이 된다.

### §13-42 정지하지 않고 검수 큐에 올리기 `[결정 필요]`

R8.11 은 *"승인 후에도 무작위 샘플링 검수를 수행한다"* 이고, §13-12 는 확산 탐지에 대해 *"자동으로 인간 검수 큐에 올린다. **정지하지는 않는다** — 인기 있는 것과 위험한 것은 다르다"* 고 못박는다.

그런데 **검수 큐는 `story.review_status` 로만 결정돼 있었다** (B-55, B-57). 큐에 올리려면 상태를 바꿔야 하고, 상태를 바꾸면 R2.3(`approved` **AND** `visibility <> private`) 때문에 **작품이 내려간다.** 무작위로 뽑혔다는 것은 아무 근거도 아니므로, 그것으로 게시된 작품을 내리면 검수가 아니라 처벌이다.

**채택: 검수 이력에 표식을 남기고 큐가 그것도 본다.**

표식은 **자동 단계의 보류**다 — `stage = auto` · `verdict = hold`. 이미 있는 어휘이며 뜻도 맞는다: *봐야 하는데 아직 안 봤다.*

| 후보 | 문제 |
|---|---|
| `review_status` 를 바꾼다 | **작품이 내려간다.** §13-12 가 하지 말라고 적은 바로 그것이다 |
| `story` 에 "검수 예정" 컬럼을 더한다 | 상태가 두 곳에 생긴다. 컬럼과 이력이 어긋나면 어느 쪽이 진실인지 매번 문제가 된다 |
| **이력의 표식** ✅ | 상태를 건드리지 않는다. 그리고 `story_review` 는 이미 <b>왜 그렇게 됐는지</b>를 담는 자리다 |

**해소 경로가 따로 없다.** 사람이 판정하면 인간 이력이 얹혀 표식이 더 이상 최신이 아니게 된다 — 지우는 일이 없으니 **지우다 실패하는 일도 없다.**

#### 판정이 여는 가시성 — 세 갈래가 하나로 정리된다

| 온 자리 | 통과가 여는 가시성 | 근거 |
|---|---|---|
| `in_review` | `public` | 그 상태로 오는 길이 `public` 제출 하나뿐이다 (§13-39) |
| `suspended` | 내려가기 전 그대로 | 정지는 가시성을 지우지 않았다 (§13-41) |
| **샘플링 표식** | **있던 자리 그대로** | 내려가지도 가려지지도 않았다 |

규칙은 하나다 — **`in_review` 만 새로 열고, 나머지는 있던 자리로 돌아간다.**

#### 큐의 순서

상태로 올라온 것이 먼저다. 제출을 기다리는 작품과 신고로 내려간 작품은 **사람이 볼 때까지 아무도 못 보거나 아무도 못 하는** 상태이고, 샘플링은 **이미 게시돼 잘 돌아가는** 작품이다.

#### 비율

**`service_config` 다** (§13-12). 검수 인력이 감당하는 양에 맞춰 조정되는 값이고, 그때마다 재배포를 기다릴 수 없다. **설정이 없으면 아무것도 뽑지 않는다** — 임의의 기본 비율을 코드에 두면 그 값이 곧 정책이 되고, 검수 큐가 조용히 차오른다.

파싱이 정수가 아니거나 범위를 벗어나면 **비율 없음**이다. 0 으로 읽으면 안전해 보이지만 100 으로 읽으면 **승인작 전부가 큐에 쏟아진다** — 파싱 실패를 정책으로 바꾸지 않는다.

#### 난수

I-15 는 판정·분기·엔딩·상태 변화량에 난수를 금지하고 **L3 랜덤 샘플링은 허용**한다 (I-15 보강 조항). 이 난수는 **무엇을 볼 것인가**를 정할 뿐 어떤 작품의 운명도 정하지 않는다 — 뽑힌 뒤에 일어나는 일은 전부 사람이 정한다.

### §13-43 작품 개수 상한은 무엇을 세는가 `[결정 필요]`

R8.12 는 *"계정당 일일 `draftOutline` 호출 수, 미리보기 턴 수, **작품 개수** 상한을 둔다"* 이지만 **무엇을 작품으로 세는지**는 정하지 않는다.

미리보기는 **매번 새 `private`·`draft` 작품을 발행한다** (§13-37). 그것까지 세면 **미리보기 몇 번으로 작품을 못 만들게 된다** — 상한이 막으려던 것은 게시물이 무한히 늘어나는 것이지 작성자가 자기 이야기를 확인하는 것이 아니다.

**채택: 제출을 지난 작품만 센다** (`review_status <> 'draft'`).

미리보기가 쌓아 둔 것의 파기는 **B-61** 이 가져간다 (§13-37) — 상한이 그 자리를 대신하지 않는다.

**재제출은 개수를 늘리지 않는다.** 같은 작품에 버전을 얹기 때문이며 (§13-40), 여기서 막으면 상한에 닿은 작성자가 **이미 낸 작품조차 고치지 못한다.**

#### 상한에 닿았을 때의 응답

**`403 STORY_LIMIT_REACHED` 다.** `QUOTA_EXCEEDED`(429) 의 문구는 *"오늘 이용할 수 있는 양을 모두 사용했어요"* 이고, 작품 개수는 **날이 바뀌어도 늘지 않는다** — 기다리라고 안내하면 기다린 만큼 헛되다.

#### 값은 어디에

**`@ConfigurationProperties` 다** (`app.ugc`). 세이프티 임계가 아니므로 `service_config` 로 숨길 이유가 없다 — S-11 이 가리는 것은 **검수 비율과 정지 임계**이고, 이 값은 알아도 그 아래로 관리할 것이 없다. `RateLimitProperties` 와 같은 형태이며 B-46 실측 뒤 조정한다는 이유도 같다.

**세 상한을 한 곳에 모은 것이 이 작업의 절반이다.** 각자 다른 컨트롤러의 상수로 흩어져 있으면 "지금 상한이 얼마인가"를 답하는 데 세 파일을 열어야 하고, 조정할 때 **하나를 빠뜨렸는지**를 아무도 알 수 없다.

### §13-44 탈퇴 파기가 도달률 통계를 되돌린다 `[해소]` — **결정됨 (2026-08-29, 이슈 #228)**

두 기능이 각자 맞는데 만나면 어긋났다.

- **B-61(2/2)** 탈퇴 파기가 그 회원의 `play_session` 을 지운다 (R12.4)
- **B-39** 도달률 집계는 매 회차 `play_session` 을 **전량 재계산**한다 — 누적 카운터가 아니다

그래서 **탈퇴 한 건이 그 사람이 완주했던 모든 작품의 도달률을 줄였다.** 작품에 아무 변화가 없는데
숫자가 바뀌고, R2.8 의 표본 경계(완주 50건) 근처에서는 도달률이 **사라졌다 나타난다.** 작성자도
플레이어도 이유를 알 수 없다.

#### 채택 — C 안: 파기 전에 집계에 반영하고 지운다

| 안 | 왜 아닌가 |
|---|---|
| A 그대로 둔다 | 파기의 의미에는 충실하지만 **작품의 통계가 남의 탈퇴로 흔들린다.** 도달률은 작품에 대한 사실이어야 한다 |
| B 집계를 누적 카운터로 바꾼다 | 도달률은 지켜지지만 **B-39 의 재계산 구조를 통째로 바꾼다.** 재계산은 집계 오류를 다음 회차에 스스로 고치는 성질이 있고, 누적으로 가면 한 번 틀린 값이 영원히 남는다 |
| **C 파기 전에 집계에 반영하고 지운다** | **채택.** 원본은 파기하고 기여분만 익명 합계로 남긴다 |

#### 무엇을 남기고 무엇을 지우는가

**지운다** — `play_session` · `turn` · `game_state_snapshot` · `story_summary`. 회원과 이어지는
원본 기록은 그대로 전부 파기된다. 이 결정은 **파기의 범위를 좁히지 않는다.**

**남긴다** — `purged_session_tally` 의 `(story_id, ending_id, reached_count)`. 그 표에는
`player_ref` 도 `session_id` 도 **플레이 시각도** 없다. 남는 문장은 *"이 작품의 이 엔딩에 몇 번
도달했다"* 하나이며, 그것은 **작품에 대한 사실**이지 회원에 대한 사실이 아니다.

R12.4 가 세션·턴에 대해 *"삭제 **또는 익명화**"* 를 허용한 것이 근거다 — 여기서는 둘 다 한다.
원본은 삭제하고, 통계 기여분만 익명화해 남긴다.

#### 규칙

1. **세는 조건이 집계와 같아야 한다.** 사용자가 지운 세션(`deleted_at`)과 완주하지 않은 세션은
   집계가 세지 않으므로 옮기지도 않는다. 옮기면 파기가 도달률을 **늘린다** — 줄어드는 것보다 나쁘다.
2. **같은 트랜잭션에서 옮기고 지운다.** 나뉘면 *더하고 못 지웠거나 지우고 못 더한* 상태가 남고,
   어느 쪽도 되돌릴 수 없다.
3. **덮어쓰지 않고 더한다.** 파기 배치는 매일 돌므로 덮어쓰면 앞 회차의 몫이 사라진다.
4. **분모도 함께 유지된다.** 도달 수만 남기고 완주 총수를 살아 있는 세션에서만 세면 **도달률이
   1 을 넘을 수 있다.** 완주 총수는 그 작품의 엔딩별 도달 수의 합으로 구한다 — 같은 조건을 두 번
   세지 않는다.

#### 약관·개인정보처리방침에 드러나야 하는 것

> **개별 플레이 기록의 원본은 파기하되, 개인을 다시 식별할 수 없는 집계 통계는 유지한다.**

이 문장이 없으면 C 안은 성립하지 않는다. §13-9 의 UGC 작성자 탈퇴 정책(공개 작품 `unlisted`
강등 + 익명화)과 같은 자리에 적는다 (R12.5 · D-2).

#### 범위 밖

**미리보기 작품과 함께 사라지는 세션은 옮기지 않는다** (§13-37). 그 세션이 물고 있던 작품 자체가
사라지므로 도달률을 지킬 대상이 없다 — `ending_def` 가 없는 도달은 집계에서 버려진다.

### §13-45 프록시 뒤의 IP 를 무엇으로 보는가 `[해소]` — **결정됨 (2026-08-29, 이슈 #234)**

S-8 은 계정 없이 부를 수 있는 경로(인증 · 신고)에 **IP 기준 한도**를 걸었다. 그런데 리버스
프록시 뒤에서 `getRemoteAddr()` 은 **프록시를 가리킨다** — 모두가 같은 IP 로 보이면 그 한도는
서비스 전체에 하나가 된다. `AuthController` 가 이 결정을 B-63 으로 미뤄 두었다.

#### 채택 — **신뢰된 프록시에서 온 전달 헤더만 신뢰한다**

전달 헤더는 **클라이언트가 보낼 수 있는 값**이다. 무조건 믿으면 헤더 한 줄로 한도를 무한히
우회할 수 있고, 관리자 IP 제한(S-4)까지 같은 헤더를 본다면 **우회 대상이 한도가 아니라 접근
통제**가 된다. 반대로 아무것도 믿지 않으면 한도가 사실상 사라진다. 그래서 **믿을 곳을 명시**한다.

- 신뢰하는 프록시의 주소를 설정으로 못박고, **그 목록 밖에서 온 전달 헤더는 읽지 않고 버린다.**
- 앱을 인터넷에 직접 노출하지 않는다. 우회 경로가 있으면 위 규칙은 선언에 그친다.
- **비어 있음을 "전부 신뢰"로 읽지 않는다.** `ADMIN_ALLOWED_CIDR` 을 다루는 방식과 같다 (S-4).

#### 값은 지금 넣지 않는다

**실제 프록시 주소가 정해지지 않았다.** 값 없이 설정 키만 늘리면 `.env` 필수 키가 하나 늘어
**환경이 없는 지금 부팅이 막힌다** (§7.3 — 기본값 패턴 금지). 배선은 스테이징 환경이 생기는
시점의 일이다 (이슈 #224). 여기서 정한 것은 **무엇을 믿을 것인가**이며, 그것이 정해져 있어야
환경을 세울 때 되묻지 않는다.

구조는 `docs/deployment.md` §5 에 있다.

### §13-46 마스킹은 무엇을 가리는가 `[해소]` — **결정됨 (2026-08-31, 이슈 #242)**

§9.2 는 타인 개인정보에 대해 **"생성물은 마스킹 후 통과, UGC 입력은 차단"** 을 규정한다.
입력 쪽은 처음부터 성립했지만 **생성물 쪽은 구현되지 않았고**, 그 자리는
`UnsupportedOperationException` 이었다 (§0.2 — 스텁으로 통과시키지 않는다). 스텁을 두지 않은
판단은 옳았으나 그 카테고리는 **닿을 수 있는 경로**여서, 판정기가 그것을 돌려주면 그 턴이
실패했다.

#### 채택 — **서버가 자리를 아는 것만 가린다**

| 어디서 걸렸나 | 처리 | 왜 |
|---|---|---|
| **1단 — 블록리스트 대조** | **가린 뒤 통과** | 어떤 항목이 어디에 걸렸는지를 결정론적으로 말할 수 있다. 정규화 위치를 원문 위치로 되돌리는 대응이 있다 |
| **2단 — 의미 기반 분류** | **재생성 1회 → 차단** | 분류기는 카테고리만 돌려준다 (§13-21). 자리를 아는 곳이 없다 |

- **`SafetyClassifier` 에 위치를 더하지 않는다.** §13-21 의 결정을 그대로 둔다 — 모델이 말한
  offset 을 믿고 본문을 잘라내면 **모델이 서버의 편집기가 된다.** 그 방향의 오류는 되돌릴 수 없다.
- **정책을 재생성으로 낮추지 않는다.** 그것은 §9.2 를 낮추는 일이다.
- **탐지 강도는 그대로다.** 대조는 여전히 받은 문자열을 전부 이어 붙여 수행한다(#84). 문단 경계에
  걸친 표현은 걸리지만 어느 한 문단 안에서 찾을 수 없으므로 **가리지 못한 것**으로 보고
  재생성으로 내린다.
- **가린 뒤 같은 대조를 한 번 더 건다.** "가렸다고 믿는 것"과 "실제로 지워진 것"은 다르다.

#### 정책의 순서 — 차단 > 재생성 > 마스킹

마스킹은 걸린 자리만 지우고 나머지를 통과시키는 처리다. 재생성 대상이 함께 걸렸다면 그 문단은
애초에 다시 만들어야 한다 — **개인정보를 가렸다고 혐오 표현이 사라지지 않는다.**

#### 입력에서는 가리지 않는다

L1 은 **걸린 것이 곧 거부**다. 출력의 처리(재생성·마스킹)를 입력으로 가져오지 않는다 — 다시
만들 것도 없고, 넣은 사람의 문장을 서버가 고쳐서 들이지도 않는다. 이 규칙이 없으면 마스킹이
붙는 순간 **개인정보가 포함된 입력이 통과**한다.

### §13-47 화자 이름은 가리는가 `[결정 필요]` — **B-30 (#243)**

§13-46 이 마스킹을 정할 때 남긴 항목이다 — *"마스킹이 붙으면 화자 이름도 마스킹 대상인지 정해야 한다"* (#243). 그 전에 더 앞선 결함이 있었다: **화자 이름이 L2 판정 대상에 아예 들어가지 않았다.** `TurnPipeline#screen` 이 판정기에 문단 본문과 선택지만 넘겼고, `speakerName` 은 모델이 만든 문자열이며 `turn.speaker_name` 으로 저장돼 화면에 도달한다 (R5.2, #84). I-2 가 닫아 둔 문이 하나 열려 있었다.

**채택 1: 화자 이름도 판정한다** (1단·2단 모두).

**채택 2: 그러나 가리지 않는다 — 재생성으로 올린다.**

1단은 이름 안의 자리를 알므로 §13-46 의 *"자리를 아는 것만 가린다"* 를 그대로 적용할 수는 있다. 그러나 이름을 통째로 가린 대사는 **누가 말했는지가 사라진 대사**이고, 그것은 본문의 뜻이 달라지는 일이다 — 마스킹이 아니라 훼손이다. 그리고 가려진 화자를 어떻게 렌더할지가 곧바로 프론트 계약의 문제가 된다.

| 후보 | 문제 |
|---|---|
| 본문과 같은 규칙으로 가린다 | 화자를 잃은 대사가 남는다. 렌더 규칙을 새로 정해야 한다 |
| 이름만 통과시킨다 | **검수 표면이 하나 빠진 상태 그대로다** — #243 이 그것이다 |
| **재생성 1회 → 차단** ✅ | 이름은 다시 만들면 되는 값이다. 본문의 마스킹 정책(§13-46)은 건드리지 않는다 |

#### 1단을 두 번 부른다

가릴 수 있는 것(본문·선택지)과 가리지 않을 것(화자 이름)을 나눠 대조한다. **대가는 화자 이름과 본문에 걸친 표현을 잡지 못한다는 것**이다 — 두 값은 화면에서 이어져 보이지만 서로 다른 필드이며, 이어 붙여 대조하면 **마스킹이 가릴 자리와 판정의 근거가 어긋난다.**

#### 즉시차단은 그대로다

화자 이름에서 즉시차단 카테고리가 나오면 차단이고, 2단은 부르지 않는다 (§9.2 의 비용 규칙).

### §13-48 승격 재검수가 반려되면 작품은 어디로 가는가 `[결정 필요]` — **B-55 (#245)**

`docs/openapi.yaml` 이 `PATCH /api/v1/stories/{storyId}/visibility` 를 선언하고 B-55 가 구현한다고 적었지만 **핸들러가 없었다** (#245). `.claude/rules/catalog-authoring.md` 도 *"`unlisted → public` 승격은 인간 검수를 재트리거한다"* 를 규칙으로 적어 두었다.

원문이 정하지 않은 것은 **재검수가 반려됐을 때 이미 게시돼 있던 작품이 어디로 가는가** 이다. §13-40 은 재제출에 대해 *"재검수 중에는 라이브러리에서 내려간다"* 까지만 정했고 반려 이후는 적지 않았다.

**채택: 승격 반려는 있던 자리로 돌려놓는다** (`approved` + 원래 가시성).

승격 요청이 거절되는 것과 이미 승인받은 게시가 취소되는 것은 다른 일이다. 둘을 붙이면 **요청한 것보다 많은 것을 잃으며**, 그러면 아무도 승격을 요청하지 않는다 — 그 길을 막은 것과 같아진다. §13-42 가 *"`in_review` 만 새로 열고, 나머지는 있던 자리로 돌아간다"* 로 정한 규칙과 같은 방향이다.

#### 승격은 가시성을 지우지 않는다

`review_status` 만 `in_review` 로 되돌린다. R2.3 의 타인 조회 조건이 `approved` **AND** `visibility <> 'private'` 이므로 **검수 중 노출은 그 하나로 이미 닫힌다.** 함께 `private` 으로 내리면 반려된 작성자가 원래 갖고 있던 `unlisted` 게시까지 잃는다.

#### 그 남겨 둔 가시성이 경로의 표식이다

| 상태 | 뜻 | 반려가 가는 곳 |
|---|---|---|
| `in_review` + `visibility = private` | 제출·재제출 (B-54 가 그렇게 저장한다) | `rejected` + `private` — 아무에게도 보인 적이 없다 |
| `in_review` + `visibility ≠ private` | **승격** — 이미 게시된 작품 | `approved` + 그 가시성 |

| 후보 | 문제 |
|---|---|
| `story` 에 "승격 요청" 컬럼을 더한다 | 상태가 두 곳에 생긴다. 컬럼과 상태가 어긋나면 어느 쪽이 진실인지 매번 문제가 된다 (§13-39 와 같은 이유) |
| 검수 이력에 새 `stage`·`verdict` 를 더한다 | 열거형과 DB CHECK 를 함께 늘린다. **지금 답이 하나인 값**을 위해 마이그레이션을 치른다 |
| **남겨 둔 가시성을 읽는다** ✅ | 이미 저장돼 있는 사실이고, 두 경로가 그 값에서 이미 갈라져 있다 |

#### `private → public` 은 이 경로가 아니다

아무에게도 보인 적 없는 작품을 공개하는 것은 승격이 아니라 **제출**이고 그 길은 `submit` 에 있다 (§13-39 — *"`in_review` 로 오는 길은 `public` 제출 하나"*). 두 경로가 같은 상태를 서로 다른 뜻으로 쓰면 위 표가 성립하지 않는다. 필요하면 `private → unlisted → public` 두 단계로 간다 — `unlisted` 는 인간 검수를 요구하지 않으므로 (R8.6) 우회가 아니다.

#### 승격도 검수 이력을 남긴다

큐는 **마지막 판정 시각**을 기다린 시각으로 쓴다 (B-55). 남기지 않으면 승인받은 그날부터 기다린 것으로 보여 **재검수가 몇 달을 기다린 것처럼** 줄 앞에 선다.

### §13-49 허용 오리진이 없으면 어떻게 하는가 `[결정 필요]` — **#248**

프론트가 **별도 레포**이므로 (§8.2) 브라우저에서 보면 다른 오리진이다. 그런데 CORS 설정이 코드에도 `application.yml.template` 에도 없었다 — 프론트의 **첫 요청이 preflight 에서 막히는** 상태였다.

원문에 CORS 조항이 없으므로 정할 것이 하나 있다: **허용 목록이 비었을 때 무엇을 하는가.**

**채택: 부팅을 실패시킨다.**

| 후보 | 문제 |
|---|---|
| 빈 목록 = 아무 오리진도 허용 안 함 | 안전해 보이지만, **설정을 빠뜨린 배포가 정상 부팅한 뒤 남의 브라우저에서 실패한다.** 그 실패는 서버 로그에 남지 않는다 — 아무도 모르는 채로 서비스가 죽어 있다 |
| 와일드카드를 기본값으로 | §7.3 이 금지하는 `${VAR:값}` 패턴이며, 회원의 플레이 기록과 저작 원고를 다루는 API 다 (I-8) |
| **값이 없으면 부팅 실패** ✅ | 브라우저에서 드러날 실패를 **부팅 시점으로 당긴다.** `JWT_SECRET`(§7.3)과 같은 취급이다 |

브라우저를 상대하는 API 에서 **오리진 정책이 없는 상태는 최소 설정이 아니라 미완성 설정이다.**

#### 와일드카드와 경로를 거부한다

- `*` 는 "누구나"다. 그리고 언젠가 자격 증명을 켜는 날 **조용히 위험해진다**
- 오리진에는 경로가 없다 — 브라우저가 보내는 `Origin` 은 스킴·호스트·포트뿐이다. 경로나 끝 슬래시를 적으면 **어떤 요청과도 일치하지 않고**, 그 사실이 부팅이 아니라 브라우저에서 드러난다

#### 자격 증명을 허용하지 않는다

인증이 `Authorization` 헤더의 Bearer 토큰이고 쿠키를 쓰지 않으므로 (B-12) 켤 이유가 없다. **켜지 않는 것이 곧 방어다** — `ApiSecurityConfiguration` 의 CSRF 면제는 *"브라우저가 자동으로 실어 보내는 것이 없다"* 를 전제로 서 있고, 자격 증명을 켜면 그 전제가 무너진다.

#### CORS 는 인가보다 먼저 판정된다

Security 체인에 배선한다. MVC 쪽에만 두면 preflight(`OPTIONS`)가 **인가에서 먼저 막힌다** — 브라우저는 `OPTIONS` 에 `Authorization` 을 싣지 않으므로 401 이 나가고, 브라우저는 그것을 **CORS 오류로 보고한다.** 원인이 인증이라는 사실이 어디에도 드러나지 않는다.

#### 범위는 `/api/v1/**` 다

dev 콘솔(B-47)과 계약 서빙은 같은 오리진에서 열린다. 교차 오리진으로 열어 두면 **`dev` 에서만 존재하는 경로를 다른 사이트가 부를 수 있게 된다.**

#### 운영 오리진을 이 레포에 적지 않는다 (S-11)

여기 있는 것은 **키와 형식**뿐이다. 값은 환경변수로만 들어간다.

### §13-50 재제출이 반려되면 이미 게시된 작품은 어디로 가는가 `[결정 필요]` — **B-56 (#249)**

§13-48 이 **승격** 재검수의 반려를 정했다. **재제출**(§13-40)에는 같은 질문이 남아 있었고, 코드는 반대로 답하고 있었다 — 개정판이 반려되면 작품이 `rejected` + `private` 으로 갔다. **작성자가 오타 하나를 고쳤다가 반려되면 고치기 전에 갖고 있던 게시까지 잃는다.**

`.claude/rules/catalog-authoring.md` 는 이미 전이를 `approved → (in_review | approved)` 로 적고 있었다 — **`rejected` 가 없다.** 규칙 문서와 구현이 어긋나 있었다.

**채택: 재제출 반려도 있던 자리로 돌려놓는다** (`approved` + 원래 가시성). §13-48 과 같은 판단이며 이유도 같다 — 개정판을 거절하는 것과 원본을 내리는 것은 다른 일이고, 붙이면 **요청한 것보다 많은 것을 잃는다.** 그러면 아무도 작품을 고치지 않게 되고, 그것은 고치는 길을 막은 것과 같다.

#### 그러려면 돌아갈 자리가 남아 있어야 한다

문제는 반려가 아니라 **제출 쪽**에 있었다. B-54 는 `public` 을 원하는 제출에 대해 `visibility` 를 `private` 으로 덮어썼고, 그 순간 **원래 값이 사라진다.**

**덮어쓸 이유가 없다.** 재검수 동안 작품이 내려가는 것은 `review_status` 하나로 이미 성립한다 — R2.3 의 타인 조회 조건이 `approved` **AND** `visibility <> 'private'` 이기 때문이다. 그래서 **이미 승인돼 있던 작품의 가시성은 그대로 둔다.**

| | `review_status` | `visibility` | 반려가 가는 곳 |
|---|---|---|---|
| 첫 제출 | `in_review` | `private` — 남겨 둘 자리가 없다 | `rejected` + `private` |
| **재제출 · 승격** | `in_review` | **그대로** | **`approved` + 그 가시성** |

두 경우가 그 값에서 이미 갈라지므로 **새 컬럼도 새 상태도 만들지 않았다.** §13-48 이 승격에 쓴 표식이 그대로 재제출에도 성립한다.

#### "있던 자리"는 승인돼 있던 자리다

정지(`suspended`)·반려(`rejected`) 상태에서 낸 재제출은 이 취급을 받지 않는다. 되돌리면 **반려가 정지를 푸는 길**이 된다 — 신고 누적으로 내려간 작품을 작성자가 재제출하고 검수자가 거절하기만 하면 복귀한다.

#### 재검수 중에 내려가 있는 것은 그대로다

§13-40 이 받아들인 대가는 바뀌지 않았다. 가시성을 남겨 두는 것이 **검수 중 노출**을 뜻하지 않는다.

### §13-51 약관 판본을 어디에 두고, 없으면 무엇을 하는가 `[해소]` — **결정됨 (2026-09-03, 이슈 #261 → #279)**

`ConsentItem` 은 `consentType` · `version` · `agreed` 를 **모두 필수**로 받는다 (§13-22). 그런데 **판본을 알려 주는 경로가 없었다** — 프론트가 `CONSENT_VERSION = 'v1'` 을 상수로 들고 있었고, 약관이 개정되면 **옛 판본이 동의 이력에 기록된다.** 조용히 틀리는 종류다.

`GET /consents` 를 신설해 닫았다 (#261). 남은 질문은 **그 판본이 어디서 오는가**였다.

#### 판본의 출처는 종류마다 다르다

| 종류 | 출처 | 왜 거기인가 |
|---|---|---|
| `tos` · `privacy` | `service_config['consent.terms']` | 약관 개정은 배포 주기와 무관하다. 코드에 두면 **개정마다 배포**가 필요하다 |
| `ai_notice` | `service_config['ai.notice']` 의 판본 | **사용자가 실제로 본 문구의 판본**이어야 한다 (R11.3) |
| `age` | `AgeGate.consentVersion()` — 서버가 정한다 | §13-24 가 이미 정한 것이다. 연령 기준은 클라이언트가 고를 값이 아니다 |

**`ai_notice` 를 `consent.terms` 에 중복해 적지 않는다.** 두 곳에 적으면 고지를 갱신한 날 둘이 어긋나고, **어긋난 쪽이 동의 이력에 남는다.** 판본은 문구를 소유한 곳이 갖는다.

#### 설정이 없으면 500 이다

§13-27 이 고지 문구에 대해 내린 것과 **같은 판단**이다.

| 후보 | 문제 |
|---|---|
| `"v1"` 같은 기본 판본 | **이슈 #261 이 고치려던 상태가 서버로 옮겨올 뿐**이고, 그때는 프론트가 상수를 들고 있을 때보다 **찾기 더 어렵다** |
| 빈 판본으로 응답 | 판본 없는 동의가 이력에 남는다. **증빙의 실질이 판본이다** (R10.2) |
| **500 + `log.error`** ✅ | 가입 화면이 뜨지 않는다. 대신 **운영 결함이 즉시 드러난다** |

**대가를 적어 둔다** — 설정하기 전에는 `GET /consents` 가 뜨지 않는다. 그것이 이 결정의 의도이며, 배포 절차(`docs/deployment.md` §3 의 0번 단계)가 `ai.notice` 와 함께 이 키를 든다.

> **`GET /consents` 는 두 키에 모두 의존한다.** `consent.terms` 만 넣으면 `ai_notice` 판본이 없어 여전히 500 이다. 키가 하나 늘어난 것이 아니라 **그 경로가 뜨는 조건이 둘**이다.

#### 값의 모양 — `service_config['consent.terms']`

**최상위는 JSON 객체**이고 동의 종류의 계약 표기를 키로 갖는다. 모양을 아는 곳은 `CatalogConsentTermsQuery` 하나다 (ADR-0002).

```json
{
  "tos":     {"version": "<판본>", "documentUrl": "<절대 URL>"},
  "privacy": {"version": "<판본>", "documentUrl": "<절대 URL>"}
}
```

| 경로 | 타입 | 필수 | 없거나 어긋나면 |
|---|---|---|---|
| `tos` · `privacy` | object | **필수** | 그 종류를 읽지 못해 `GET /consents` 가 500 |
| `<종류>.version` | 비어 있지 않은 문자열 | **필수** | 같다 — 판본 없는 종류는 "어긋난 것"이 아니라 **아직 넣지 않은 것**이다 |
| `<종류>.documentUrl` | 문자열 (**절대 URL**) | 선택 | 응답의 그 필드가 `null` 이다. 200 은 유지된다 |
| `ai_notice` | — | **적지 않는다** | 적어도 읽지 않는다 — 그 판본은 `ai.notice` 가 갖는다 |
| `age` | — | **적지 않는다** | 서버가 조립한다 (§13-24) |

**`documentUrl` 은 절대 URL 이다.** 약관 본문이 API 와 같은 출처에 있으리라는 보장이 없고, 이 값을 그대로 링크로 거는 것은 웹과 앱 **두 클라이언트**다 — 상대 경로는 각자의 기준으로 다르게 풀린다. **주소 자체는 이 저장소에 적지 않는다** (S-11).

**두 종류가 다 있어야 한다.** 하나만 넣으면 그 하나만 읽히고 나머지가 500 을 만든다 — 부분 투입이 부분 동작으로 보이지 않는다.

#### 판본 표기 — `v<major>.<minor>`

**`v1.2` 처럼 적는다** (2026-09-02 확정). 원문에 규칙이 없어 근거는 와이어프레임 `3g` 가 계정 설정에 `이용약관 v1.2` 로 그린다는 것 하나였고, **화면 표기와 저장 값을 같은 모양으로 두는 쪽**을 골랐다.

- **약관 두 종류는 각자 센다.** `tos` 가 `v2.0` 인데 `privacy` 가 `v1.1` 인 상태는 정상이다.
- **문구를 고치면 판본을 올린다.** 문구만 바꾸고 판본을 두면 **동의 이력이 옛 판본을 가리킨 채 새 문구에 동의한 것**이 되고, 그것이 이슈 #261 이 고치려던 상태다.
- `major` 는 다시 동의를 받아야 하는 개정, `minor` 는 그렇지 않은 개정으로 쓴다. **서버는 이 구분을 읽지 않는다** — 재동의 여부는 운영이 판단한다.

> `ai.notice` 의 판본은 날짜 형식이라 **둘이 서로 다른 모양**이다. 맞추지 않은 이유는 그 둘이 같은 표에 있지 않기 때문이다 — 고지 판본은 문구를 소유한 키가 갖고, 약관 판본은 `consent.terms` 가 갖는다. 동의 이력에는 둘 다 남지만 **각자 자기 출처의 표기를 그대로 들고 간다.**

> `age` 만 형식이 다르다 — `age-15` 로 **서버가 조립한다** (§13-24). 표기를 맞추지 않은 이유는 그 값이 약관 판본이 아니라 **판정 기준**이기 때문이다. 기준이 바뀌면 판본도 따라 바뀌어야 하므로 한 곳에서 나온다.

#### 서버는 형식을 검증하지 않는다 — 그래도 결과는 하나다

**비어 있지 않은 문자열이면 받는다.** 표기 규약도 검사하지 않는다. 형식을 강제하면 약관 개정 방식이 코드에 묶이고, 그것은 이 값을 설정으로 뺀 이유와 어긋난다. **규칙은 운영이 지키는 것이지 서버가 막는 것이 아니다.**

대신 **어긋난 값이 조용히 통과하지 않는다.** `CatalogConsentTermsQuery` 는 읽다 실패하면 예외를 올리는 대신 비워서 돌려주고, 판본 없는 종류를 만난 `ConsentTermsService` 가 거기서 멈춘다 — 들어온 모양이 무엇이든 **한 자리로 떨어진다.**

| 넣은 값 | `GET /consents` |
|---|---|
| 키 자체가 없다 | 500 `INTERNAL_ERROR` |
| JSON 이 아니다 | 같다. `log.warn` 에 **키와 예외 종류만** 남는다 — 값은 남기지 않는다 (S-3) |
| 최상위가 객체가 아니다 (배열 · 숫자 · 문자열) | 같다 |
| 종류 하나가 빠졌다 | 같다 |
| `version` 이 없거나 비어 있다 | 같다 |

**"모양이 조금 다른 값"이 통과해 이상한 판본을 동의 이력에 남기는 경로가 없다**는 뜻이다. 응답에는 `code` 와 안전한 `message` 만 실린다 — 스택트레이스 · SQL · 내부 경로가 나가지 않는다 (S-6).

#### 값 자체는 이 저장소가 갖지 않는다

**실제 판본과 약관 주소는 레포에 넣지 않는다** (S-11). 시드 마이그레이션도 만들지 않았다 — 만드는 순간 운영 값이 공개 레포에 들어온다. 확정과 투입은 운영의 일이며, 그 전까지 이 경로는 500 이다.

**투입 절차는 `docs/deployment.md` §3 의 0번 단계**가 든다 — `ai.notice` 와 나란히, 환경마다 한 번 하는 일이다. 넣는 SQL 의 모양은 거기에 있고 **값은 자리표시자**다.

**남은 것은 결정이 아니라 문구다.** 약관·개인정보처리방침 본문 확정은 `docs/open-decisions.md` 의 **D-2** 가 계속 들고 있다 — 이 절이 정한 것은 그 문구를 **어떤 모양으로 어디에 넣는가**까지다.

### §13-52 어떤 응답이 AI 고지 문구를 실어야 하는가 `[해소]` — **결정됨 (2026-09-02, 이슈 #291)**

AI 고지 Footer 를 그리는 화면의 응답에 `noticeText` 가 빠지는 일이 **세 번** 있었다 — #257(라이브러리 · 작품 상세) · #284(내 이야기 · 내 작품 · 플레이 · 기록) · #289(섹션 전체 보기). 매번 **프론트가 화면을 붙이다 발견했다.** 그 전까지 아무도 몰랐다.

#### 어려운 쪽은 목록이 아니라 판정 기준이었다

"Footer 를 그리는 화면"은 **계약에 표시되어 있지 않았다.** 그래서 `OpenApiContractTests` 가 판정 기준을 갖지 못했고, 응답을 하나씩 채우는 방식은 열 번째 화면에서 같은 이슈를 다시 부른다.

| 후보 | 문제 |
|---|---|
| 대상 쪽에 표시 — Footer 응답에 `x-` 표시를 달고 표시된 것만 강제 | **표시를 붙이는 것을 잊으면 그대로 샌다.** #257 → #284 → #289 가 정확히 그 모양이었다 |
| 절차 — PR 템플릿 체크 항목 | 가장 싸다. 그러나 위 셋이 **절차로는 막히지 않았다는 증거**다 |
| **기본을 "싣는다"로 두고 면제 쪽에 표시** ✅ | Footer 와 무관한 응답에까지 표시를 달아야 한다. 대신 **빠뜨리면 침묵하지 않는다** |

#### 규칙

성공 응답(2xx)의 JSON 본문 스키마는 **`noticeText` 를 `required` 로 갖거나, `x-notice-exempt` 에 면제 이유를 적거나 둘 중 하나다.** 본문이 없는 응답은 화면이 아니므로 보지 않는다.

**값을 `true` 가 아니라 문장으로 받는다.** 면제가 늘어날 때 그것이 판단이었는지 관성이었는지를 나중에 구분할 수 있어야 한다.

#### 지금 면제인 것과 그 이유

| 무리 | 이유 |
|---|---|
| 인증 · 계정 · 약관 | AI 생성물을 그리지 않는다 |
| 관리자 (§14) | 사용자에게 보이지 않는다. 사전 고지는 사용자에게 하는 것이다 |
| 세션 시작 · 이어하기 | 고지는 **안에 실린 턴**이 싣거나(`TurnResponse.noticeText`), 이 판정이 가리킨 화면이 싣는다 |
| **작품 만들기 (authoring)** | 아래 |

#### 작품 만들기는 면제다

가장 애매한 자리였다 — 아웃라인 · 미리보기는 **AI 생성물을 작성자에게 보여 준다.**

**창작 도구 화면이며 감상 화면이 아니다**로 정했다 (2026-09-02). 사전 고지는 *이야기를 AI 가 쓴다는 것을 읽는 사람에게 알리는 것*이고, 작품을 만드는 사람은 자기가 AI 를 쓰고 있다는 사실을 이미 안다.

> **원문 확인 없이 내린 결정이다.** `docs/internal/` 이 이 작업 시점의 환경에 없어 R11 원문을 대조하지 못했다. 원문이 작성 화면을 사전 고지 대상으로 규정하고 있다면 **이 항목이 먼저 바뀌어야 하고**, 그때 고칠 자리는 `docs/openapi.yaml` 의 `x-notice-exempt` 다섯 곳이다.

### §13-53 단위가 있는 수치는 계약이 단위를 말한다 `[해소]` · 비용의 통화는 KRW `[해소]` — **이슈 #275 · #311 (2026-09-03)**

`reachRate` 는 타입이 `number` 뿐이라 **`0.12` 인지 `12` 인지 계약이 말하지 않았다.** #260 이 그 필드 하나에 단위·예시·상하한을 적고 계약 테스트로 못박았다.

**방어가 그 필드에만 있었다.** 계약 테스트는 *구현 ⊆ 계약* 한 방향만 보므로 **타입은 맞고 단위가 없는 필드**는 어느 쪽도 잡지 못한다. 컴파일도 테스트도 통과한다.

#### 규칙 — 이름이 단위를 든 것만 본다

> **이름이 `Rate` · `Percent` · `Ms` · `Millis` · `Seconds` · `Micro` · `Tokens` · `Bytes` · `Cost` 로 끝나는 수치 필드는 `description` 에 단위를 적는다.** 그중 비율(`Rate` · `Percent`)은 `minimum` · `maximum` · `examples` 까지 갖는다.

**`chapterNo` · `turnNo` · `order` 같은 카운터는 대상이 아니다.** 계약의 수치 필드는 53개이고 그중 36개에 설명이 없지만, 대부분이 단위 없는 카운터다. 거기까지 강제하면 **규칙이 소음이 되고, 소음이 된 규칙은 형식적으로 채워진다** — "정수"라고 적힌 `description` 은 없는 것과 같다.

비율에만 범위와 예시를 더 요구하는 이유는 **설명만으로는 갈리지 않기 때문**이다. *"도달률"* 이라고 적어도 `0.12` 와 `12` 를 구분해 주지 않는다.

#### `[해소]` — `cost_micro` 의 통화는 **KRW** 다

규칙을 세우자 같은 모양이 하나 더 드러났다. `ai_call_log.cost_micro` 는 **백만분의 1 단위인데 무엇의 백만분의 1인지가 레포 어디에도 없었다** — 엔티티에도, 마이그레이션에도, 계약에도, 설정에도 없었다.

**어느 Provider 도 채우지 않아 항상 `null` 이라 드러나지 않았다.** `reachRate` 와 같은 종류이며, 차이는 이쪽이 **돈**이라는 것이다. 벤더 단가가 USD 로 고시되므로 정하지 않은 채 어댑터마다 채우면 한쪽은 USD, 한쪽은 KRW 가 되고 **합계는 뜻을 잃는다.** 쌓인 행의 통화는 사후에 알 수 없다.

**값이 하나도 없는 지금 정했다.** 되돌릴 비용이 0 인 유일한 시점이다.

| 결정 | 값 |
|---|---|
| 통화 | **KRW** — 비용 보고가 원화로 필요하다 |
| 이름 | 컬럼 `cost_micro_krw` · 계약 `costMicroKrw` · 메트릭 `ai.call.cost.micro.krw` |
| 환율이 개입하는 지점 | **서버 밖.** 설정에 넣는 단가가 이미 KRW 이며, 환산은 그 값을 넣는 사람이 한다 |
| 단가 | `ai.providers.<이름>.pricing.<모델 ID>` — 입력·출력 100만 토큰당 원을 따로 받는다 |
| 단가가 없을 때 | `null`. **지어낸 0 을 넣지 않는다** |

**이름이 통화를 든다.** 다음 사람이 문서를 찾지 않아도 되고, 값을 넣는 사람이 무엇을 넣는지 이름에서 본다. 이름을 바꾸는 마이그레이션은 `promptlog/V4` 이며 **백필이 없다** — 기존 값이 전부 `null` 이기 때문이다.

**환율을 서버에 두지 않는 것이 이 결정의 실질이다.** 이슈가 지목한 대로 정할 것은 통화 자체보다 *"환율이 어디서 개입하는가"* 였다. 서버가 환율을 들면 그 값이 낡는 순간부터 조용히 틀린 수가 쌓이고, 쌓인 뒤에는 **어느 시점 환율로 계산됐는지 알 수 없다.** 단가를 KRW 로 받으면 서버는 곱셈만 하며, 단가를 갱신한 시점 이후의 행만 새 단가로 계산된다 — 그것이 정확히 사실이다.

**0 을 쓰지 않는 이유.** `null` 은 "모른다", 0 은 "공짜로 돌았다"는 **사실 진술**이다. 0 을 넣으면 합계가 조용히 낮아지고 그 위에 세운 예산 알람은 영영 울리지 않는다. 그래서 `MeteredAiCallRecorder` 도 `null` 이면 카운터를 올리지 않는다.

**Ollama 는 영영 `null` 이다.** 로컬 실행이라 벤더 단가라는 개념 자체가 없다. 그것이 "모른다"인지 "공짜"인지 헷갈릴 자리를 남기지 않는다.

**단가 값은 이 레포에 두지 않는다.** 벤더 고시가는 시간에 따라 바뀌고 환산 시점도 환경마다 다르다 — `application.yml.template` 에는 키 이름과 단위만 있다.

### §13-54 탐색은 어디까지 공개인가 `[해소]` — **결정됨 (2026-09-03, 이슈 #306)**

랜딩(`getLanding`)이 `featuredStories` 를 인증 없이 주는데 **라이브러리와 작품 상세는 토큰을 요구했다.** 추천 몇 개는 로그인 없이 보이고 목록은 안 보이는 상태였고, 프론트는 계약을 그대로 따라 익명을 `/login` 으로 보냈다 (#306).

#### 결정 — 목록까지 공개한다

> **`getLibrary` · `getLibrarySection` · `getStoryDetail` 을 `security: []` 로 연다.** 익명도 작품 목록과 상세를 볼 수 있고, **플레이하려 할 때 로그인한다.**

레포 소유자가 세 갈래(둘러보기를 닫는다 / 랜딩을 좁힌다 / 목록을 연다) 중에서 고른 값이다. 근거는 화면의 성격이다 — 라이브러리는 *"당신의 다음 이야기를 선택하세요"* 이고, **서비스를 처음 보는 사람이 무엇이 있는지 보는 자리**다. 그 화면이 로그인 뒤에 있으면 가입 판단의 재료가 가입 뒤에만 있다.

**세션을 만드는 경로는 그대로다.** `POST /api/v1/stories/{storyId}/sessions` 부터 토큰이 필요하다 — 열린 것은 **읽기**뿐이다. 보안 설정도 그것을 `GET` 으로 못박는다: `/api/v1/stories/*` 는 경로만 보면 앞으로 생길 `DELETE /api/v1/stories/{storyId}`(이슈 #290)와 이웃하므로, 메서드를 빼고 열면 **그 날 조용히 함께 열린다.**

#### I-8 과의 관계 — 인증은 그 보장을 대신한 적이 없다

**이것이 이 결정에서 가장 먼저 확인해야 하는 것이다.** "인증이 검수 게이트를 대신 지키고 있었다면" 그것을 걷어내는 순간 미승인 작품이 새기 때문이다.

**대신하고 있지 않았다.** 노출 조건은 `StoryCatalogFacade` 의 SQL **한 곳**에 있고, 목록과 상세가 같은 조건을 쓴다 — `review_status = 'approved'` · `visibility <> 'private'` · `published_at IS NOT NULL` · `current_version_id IS NOT NULL`. 토큰이 있는 누구에게나 같은 조건이 걸려 있었으므로 **이번에 늘어난 것은 "부를 수 있는 사람"이지 "보이는 작품"이 아니다.**

- **볼 수 없는 작품은 `404` 다** — `403` 이 아니다. `403` 은 **작품의 존재를 알린다**: id 하나로 승인 대기 중인 작품이 있는지 확인할 수 있게 된다. 없는 것과 구분되지 않는다는 규칙은 익명에게도 같다.
- **`suspended` 는 조건이 `approved` 를 요구하므로 함께 닫힌다** (R8.10). 정지가 `visibility` 를 건드리지 않는다는 §13-41 의 선택과 맞물린다.
- **공식 작품도 `approved` 를 요구한다.** 종류별로 조건을 다르게 두면 *공식이라는 이유로 검수를 건너뛰는 경로*가 생긴다.

#### 익명 응답에서 비는 것

**"로그인해야 의미가 있는 값"만 빈다.** 작품 쪽은 한 글자도 달라지지 않는다.

| 오퍼레이션 | 익명일 때 |
|---|---|
| `getLibrary` | `continueSessions` 가 **빈 배열**. `genres` · `sections` · `noticeText` 는 같다 |
| `getStoryDetail` | `mySession` 이 **`null`**. `story` · `characters` · `noticeText` 는 같다 |
| `getLibrarySection` | **없다** — 이 응답에는 개인 필드가 처음부터 없다 |

**`null` 과 빈 배열은 세션이 없는 회원의 응답과 같은 모양이다.** 익명 전용 표시를 새로 만들지 않은 것이 요점이다 — 만들면 클라이언트가 분기를 하나 더 갖고, 그 분기는 *로그인했지만 세션이 없는* 다수의 경우와 결국 같은 화면을 그린다.

주체 판별도 두 갈래로 나눴다. `PlayerRefResolver` 는 **없으면 401 인** 물음과 **없어도 되는** 물음을 별도 메서드로 갖는다. 하나로 합쳐 `null` 을 돌려주면 **주인이 필요한 경로가 그것을 조용히 통과한다.**

#### 호출 한도 — 설정 조회와 창을 나눈다

인증 밖으로 열리는 읽기에는 IP 기준 한도가 붙는다 (S-8, 이슈 #277). 다만 **`/landing` · `/consents` 의 창(#277)에 합치지 않았다.**

합치는 논리(#277)는 *두 경로가 같은 것을 지키고 같은 빈도로 불릴 때* 성립한다. 여기서는 둘 다 아니다 — 탐색은 한 화면이 섹션 더 보기와 작품 상세로 이어져 **몇 분에 수십 번** 불리고, 설정 조회는 화면당 한 번이다. 한 창에 넣으면 **둘러보던 사람이 창을 다 쓴 뒤 가입하지 못한다**: `/consents` 가 막히면 약관 판본을 읽을 수 없고 가입 요청이 성립하지 않는다.

**우회로가 되지 않는 이유는 지키는 대상이 다르기 때문이다.** 탐색 창을 다 써도 설정 조회의 DB 읽기는 여전히 자기 한도로 묶여 있다. 반대로 **탐색 셋은 한 창을 공유한다** — 같은 화면 흐름이고 같은 catalog 읽기라서, 따로 세면 한 축을 다 쓴 뒤 다른 축으로 옮겨 가면 된다.

#### `unlisted` 는 목록에 오르지 않는다 — 목록과 조회를 가른다

확인 중에 드러났다. 노출 조건이 `visibility <> 'private'` 하나였으므로 **`unlisted` 가 커뮤니티 목록에 올라오고 있었다.** 지금까지는 로그인이 그 앞에 서 있어 드러나지 않았지만, 이 작업이 목록을 익명에게 열면서 **사람이 본 적 없는 작품을 둘러보던 사람이 그냥 만나는** 모양이 됐다 — `unlisted` 는 사람 검수를 요구하지 않는 범위다 (R8.6).

**레포 소유자가 "목록에서 뺀다"를 골랐다 (2026-09-03).** 그래서 조건을 하나에서 둘로 나눴다.

| | 가시성 조건 | 왜 |
|---|---|---|
| **목록** (섹션 카드 · 장르 섹션) | `visibility = 'public'` | 사람 검수를 지난 것만 둘러보기에 오른다 |
| **조회** (작품 상세) | `visibility <> 'private'` | **링크로 닿는 것이 `unlisted` 의 정의다.** 여기까지 좁히면 `unlisted` 가 `private` 과 같아지고 세 값 중 하나가 뜻을 잃는다 |

**검수 조건 셋은 양쪽이 그대로 공유한다** — `approved` · `published_at IS NOT NULL` · `current_version_id IS NOT NULL`. 이 셋이 갈라지면 목록에서 가린 작품을 id 를 아는 사람이 그대로 읽는다 (I-8). **가시성만 한 칸 다르다.**

§13-48 이 인용한 R2.3 의 *타인 조회* 조건(`approved` AND `visibility <> 'private'`)은 **상세를 말하는 것으로 읽는다.** 목록은 그 조건에 `public` 을 더한 것이지 그 조건을 뒤집은 것이 아니다. **R2.3 원문은 대조하지 못했다** — `docs/internal/` 이 이 작업 시점의 환경에 없다.

§13-9(탈퇴 작성자의 공개 작품을 `unlisted` 로 강등)와 §13-41(정지 복귀가 있던 자리로 돌아간다)은 **이 변경으로 더 정확해진다.** 강등의 뜻이 "목록에서 내린다"가 되고, 복귀가 `unlisted` 를 공개로 만들지 않는다.

### §13-55 표시명은 어디서 정해지는가 `[해소]` — **결정됨 (2026-09-03, 이슈 #271)**

`author_profile.display_name` 을 **읽는 곳은 셋**이었다 — 작품 상세(#258) · 커뮤니티 카드 · `GET /api/v1/me`(#262). **쓰는 프로덕션 경로는 없었다.** 그 행을 만드는 것은 테스트뿐이었고, 그래서 실사용에서 `displayName` 은 사실상 항상 `null` 이었다. 계약이 nullable 이라 동작은 정상이었지만, 화면은 **"아직 안 정한 것"과 "원래 비는 값"을 구분할 수 없었다.**

#### 경로 — `PATCH /api/v1/me`

계정 화면이 이미 있는 자리다. 표시명만을 위한 새 리소스(`/api/v1/me/profile` 같은)를 두면 **한 화면이 두 경로에 쓰게** 되고, 그때 "역할·상태는 어디서 바꾸나"가 또 갈린다.

`PUT` 이 아니라 `PATCH` 인 이유는 **보내지 않은 필드를 지운다는 뜻을 만들지 않기 위해서**다. 이 요청이 다루는 것은 계정의 일부다.

**설정과 변경이 한 경로다** (upsert). 프로필이 없으면 만들고 있으면 바꾼다 — 나누면 화면이 존재 여부를 먼저 물어야 하고, 그 두 요청 사이에 다른 요청이 끼면 어느 쪽도 맞지 않는 순간이 생긴다.

#### 모듈 경계 — identity 가 받고 catalog 가 쓴다

표시명은 **catalog 소유**다 (`author_profile`, §13-7). 요청을 받는 것은 identity 이고, identity 의 허용 의존은 `common` 하나다. 그래서 계약을 `common/spi` 에 두고 **구현을 데이터 소유 모듈에** 둔다 — 읽기(`AuthorDisplayNameQuery`)가 이미 그 형태다 (ADR-0002).

**읽기 인터페이스에 쓰기를 더하지 않고 인터페이스를 하나 더 두었다** (`AuthorDisplayNameWriter`). 읽기 계약은 읽기 전용 트랜잭션으로 구현돼 있고, 거기에 쓰기를 섞으면 **이름을 읽기만 하면 되는 세 호출자가 쓰는 능력을 함께 얻는다.** `common/spi` 에는 이미 같은 방향의 선례가 있다 — `AiNoticeQuery` 와 `AiNoticeRecorder` 는 한 데이터를 읽고 쓰면서 서로 다른 인터페이스다.

**넘어가는 식별자는 `playerRef` 하나다** (I-3). identity 는 `user.id` 를 catalog 로 넘기지 않으며, `author_profile` 에는 그것을 담을 컬럼이 애초에 없다.

#### 규칙의 정본은 하나다

검증은 **기존 `DisplayNames`** 가 한다. 규칙을 요청 DTO 나 화면에 복사하면 정본이 둘이 되고, 갈라지는 순간 **한쪽이 통과시킨 이름을 다른 쪽이 거절한다.** 요청 DTO 는 *키가 왔는가*만 본다.

도메인은 `IllegalArgumentException` 을 던진다. 그것을 그대로 잡으면 **구현의 버그까지 400 이 되므로**, 경계를 넘는 전용 타입(`InvalidDisplayNameException`)으로 바꿔 전달하고 identity 가 `VALIDATION_ERROR` 로 사상한다. **거절된 입력값은 응답에 담지 않는다** (S-3) — 어긴 규칙만 말한다.

#### 중복은 허용한다

`author_profile` 에 표시명 유일 제약이 **없다.** `catalog/V7` 이 표를 만들 때도, `catalog/V11` 이 길이·문자·공백 제약을 더할 때도 유일 인덱스를 두지 않았다.

**이 작업은 제약을 새로 만들지 않는다.** 유일성을 도입하는 것은 마이그레이션이자 정책 변경이고(대소문자·자모 정규화·기존 중복 행 처리를 함께 정해야 한다), 이 이슈의 범위가 아니다.

그러므로 **같은 표시명을 가진 회원이 둘 이상 있을 수 있다.** 그것이 계약에 적혀야 하는 이유는, 적지 않으면 화면이 표시명을 **식별자처럼** 쓰기 시작하기 때문이다. `409` 를 두지 않은 것은 충돌이 일어나지 않아서가 아니라 **충돌이라는 개념이 없어서**다.

#### 트랜잭션이 갈라지는 지점

identity 스토어와 catalog 스토어는 **DataSource 가 다르다.** 한 트랜잭션으로 묶을 수 없고, 묶으려 드는 순간 스토어 분리가 무너진다.

그래서 이 경로는 **쓰기를 한쪽에만 둔다.** identity 는 회원을 **읽기만** 하고(존재·상태 확인), 쓰기는 catalog 의 트랜잭션 하나에서 끝난다. 갈라져서 반쪽만 남을 상태가 없다 — 실패하면 **이름이 바뀌지 않았을 뿐**이고, 다시 부르면 된다.

읽기와 쓰기 사이에 회원 상태가 바뀔 수는 있다(확인 직후 탈퇴). 그 창은 이 요청 하나의 길이이며, 남는 결과는 *탈퇴한 계정에 표시명이 하나 남는 것*이다. 파기 배치가 그 행을 익명 이름으로 덮으므로 **배치의 결과는 달라지지 않는다.**

#### 정지·탈퇴 회원은 바꾸지 못한다 (403)

액세스 토큰은 탈퇴 후에도 만료 전까지 살아 있다 (R12.5 · §13-9). 여기서 막지 않으면 파기 배치가 익명으로 바꿔 둔 이름을 **탈퇴한 계정이 도로 되돌릴 수 있다.** 로그인·재발급이 이미 같은 기준으로 막고 있으므로(`SocialAccountRegistrar`) 규칙이 하나로 유지된다.

> **원문 확인 없이 내린 결정이다.** `docs/internal/` 이 이 작업 시점의 환경에 없어 R12 · §13.7 원문을 대조하지 못했다. 원문이 표시명의 유일성이나 변경 횟수 제한을 규정하고 있다면 **이 항목이 먼저 바뀌어야 한다.**

### §13-56 조건 템플릿은 키만으로 완성되지 않는다 · 작성 메타데이터는 한 경로가 준다 `[해소]` — **이슈 #282 · #315 (2026-09-03)**

#### 먼저 답해야 했던 것 — (a) 인가 (b) 인가

이슈 #282 는 목록 경로보다 **이것이 먼저**라고 적었다. `affinity_at_least` 는 키만으로 쓸 수 없다 — **무엇에 대한 호감도인지**와 **임계값**이 필요하다.

- (a) 키 하나에 대상·임계가 **접혀 있다** → 그 표기법이 계약에 없다
- (b) **접혀 있지 않다** → 그렇다면 계약이 템플릿마다 필요한 입력을 말해야 한다

**채택: (b) 다.** 추정이 아니라 코드에서 확인한 사실이다.

`ConditionEvaluator` 가 읽는 연산자는 `all` · `any` · `not` · `gte` · `gt` · `lte` · `lt` · `eq` · `has` · `turnGte` 이고, 수치 비교의 피연산자는 **`["<수치 경로>", <정수>]` 두 자리**다. 수치 경로는 `GameState` 가 `affinity.<인물>` 처럼 **점 경로 하나로 평평하게** 들고 있는 값이며, 그 표기는 `state_schema` 가 선언한 화이트리스트에서 온다. 즉 §13-35 의 넷은 다음으로 조립된다.

| 템플릿 | 조립되는 조건식 | 작성자가 채워야 하는 값 |
|---|---|---|
| `affinity_at_least` | `{"gte": ["affinity.<인물>", <임계>]}` | **둘** — 인물 · 정수 임계 |
| `has_flag` | `{"has": ["flags", "<플래그>"]}` | 하나 — 플래그 |
| `lacks_flag` | `{"not": {"has": ["flags", "<플래그>"]}}` | 하나 — 플래그 |
| `turn_at_least` | `{"turnGte": <임계>}` | 하나 — 정수 임계 |

**빈칸이 있는 템플릿은 지금 하나도 없다.** 그러므로 키 문자열 하나로 조건을 표현하는 계약은 처음부터 성립하지 않았다.

**(b) 가 `affinity_at_least` 를 탈락시키지 않는다.** #282 는 (b) 를 *"작성자가 고를 수 없는 템플릿"* 으로 적었지만, 그것은 **계약이 입력을 선언할 수 없다는 전제**에서만 참이다. 선언하면 된다 — 5차 와이어프레임이 철거한 3단 드롭다운은 형태가 틀렸던 것이 아니라 **근거가 계약에 없었던 것**이다.

그래서 각 템플릿이 `parameters[]` 를 스스로 싣는다: `name` · `type`(`character` · `flag` · `integer`) · `label`. **자유 텍스트 타입을 두지 않는다** — 두는 순간 화면은 입력창을 그리게 되고, 그것은 작성자가 조건식을 직접 쓰는 것과 같아진다.

**`character` 와 `flag` 의 선택지는 이 응답이 주지 않는다.** 인물은 **작성 중인 원고의 캐릭터 목록**에서 오고, 플래그는 그 원고가 선언한 것에서 온다 — 원고마다 다르므로 서버가 전역 목록으로 줄 수 있는 값이 아니다. 계약이 그 사실을 적는다.

#### 경로는 하나다 — `GET /api/v1/authoring/metadata`

장르(#315)와 조건 템플릿(#282)은 **같은 화면이 같은 시점에** 필요로 한다. 나누면 화면 하나가 왕복을 둘 하고, 새 항목이 생길 때마다 경로가 는다. `operationId` 는 `getAuthoringMetadata` 이며 **작성자 경로이므로 토큰을 요구한다** — `/api/v1/consents` 가 열려 있는 것은 *가입 전에* 불리기 때문이고 이 경로는 그렇지 않다.

#### 정본이 어디인가 — 둘이 다르다

| 목록 | 정본 | 이유 |
|---|---|---|
| **장르 다섯** (§13-25) | **`catalog` 의 `genre` 표** | 운영이 늘릴 수 있는 데이터다. 코드에 다섯을 적으면 라이브러리가 보여 주는 목록과 작성자가 고를 수 있는 목록이 **서로 다른 정본**을 갖게 되고, 갈라지는 날 *작성자가 고른 장르로는 열리지 않는 섹션*이 생긴다 (#315). 순서는 `display_order` 이며 라이브러리와 같다 |
| **조건 템플릿 넷** (§13-35) | **코드의 열거형** | 넷은 **조건 평가기가 지원하는 형태**이지 운영 데이터가 아니다. 표에 한 줄을 더해도 그것을 평가할 코드가 없고, 평가기는 모르는 키를 **조용히 `false`** 로 본다 — 늘린 사람은 조건이 영영 참이 되지 않는 것만 본다 |

**라벨의 정본은 어느 쪽이든 서버다.** 프론트가 `affinity_at_least` 를 "호감도 이상"으로 옮기기 시작하면 **표시 문구의 정본이 하나 더 생긴다** — `noticeText`(#257) · `ConsentItem.version`(#261) 과 같은 종류의 문제이며, 그 둘은 같은 이유로 닫혔다.

#### 이 절이 하지 않은 것

**작성한 조건을 저장하는 경로는 여기 없다.** 이 경로는 *무엇을 고를 수 있는가*만 답한다. 고른 것을 `chapter_def.entry_condition` · `ending_def.condition` 으로 조립해 저장하는 쓰기 경로는 별도 작업이며, 거기서 정해야 할 것이 더 있다 — 조립된 JSON 을 **서버가 만드는가 클라이언트가 보내는가**(I-1 과 같은 이유로 서버여야 한다), 인물·플래그 이름이 `state_schema` 화이트리스트 안에 있는지의 검증, 그리고 기본 엔딩이 조건을 갖지 못한다는 §13-16 의 강제다.

> **원문 확인 없이 내린 결정이다.** `docs/internal/` 이 이 작업 시점의 환경에 없어 R7.16 원문을 대조하지 못했다. 위 표의 조립식은 **레포의 `ConditionEvaluator` · `GameState` · `StateSchema` 에서 읽은 것**이며, 원문이 다른 문법을 규정하고 있다면 `parameters[]` 의 구성이 먼저 바뀌어야 한다.

### §13-57 신청 시각과 승인 시각은 어디서 오는가 `[해소]` — **이슈 #290-1 (2026-09-03)**

와이어프레임 `3f`(공개 범위 · 검수 상태)가 *"2월 21일 **신청** · 보통 1~3일"* 과 *"2월 18일 **승인**"* 을 그린다. 계약에는 `updatedAt` 하나뿐이라 **프론트가 둘을 구분할 수 없었고**, 날짜를 추측해 붙이는 대신 "마지막 갱신"만 표시했다 — 기다리는 사람에게 필요한 정보가 아니다.

**신청한 날과 승인된 날은 다른 사실이다.** "보통 1~3일"이라는 안내는 **언제부터 세는지**를 알아야 뜻을 갖는다.

#### 채택: `story_review` 에서 파생한다. `story` 에 컬럼을 더하지 않는다

| 후보 | 문제 |
|---|---|
| `story` 에 `submitted_at` · `reviewed_at` 컬럼을 더한다 | **같은 사실이 두 곳에 생긴다.** 검수 이력이 append-only 인데 컬럼은 덮어쓰기이므로, 둘이 어긋났을 때 어느 쪽이 진실인지 매번 문제가 된다 — §13-48 · §13-50 이 "남겨 둔 가시성을 읽는다"로 답한 것과 같은 판단이다. 마이그레이션과 백필도 따라온다 |
| **검수 이력에서 읽는다** ✅ | 이미 저장돼 있는 사실이다. `story_review` 는 `story_id` · `stage` · `verdict` · `reviewed_at` 을 갖고 `(story_id, reviewed_at DESC)` 인덱스가 이미 있다 (B-55 가 검수 큐를 위해 만든 것) |

#### 회차를 가르는 정의 — `auto` + `pass` 기록이 회차의 시작이다

재제출이 있으므로 같은 작품에 기록이 여러 회차 쌓인다. **어느 신청에 대한 어느 판정인지**가 갈리지 않으면 지난 회차의 승인 시각이 이번 신청 옆에 붙는다.

**원문에 회차의 정의가 없다.** 지어내는 대신 **코드에 이미 있는 사실**을 근거로 삼았다 — `stage='auto'` + `verdict='pass'` 기록을 남기는 곳은 둘뿐이고, **둘 다 작성자가 검수를 요청하는 행위**다.

| 기록 | 남기는 곳 | 요청인가 |
|---|---|---|
| `auto` + `pass` | 제출 · 재제출 (B-54) · `unlisted → public` 승격 (B-55, §13-48) | **그렇다** |
| `auto` + `reject` | 승인작 재스캔 (B-59, R9.4) | 아니다 — 작성자가 부른 적이 없다 |
| `auto` + `hold` | 검수 샘플링 (B-59, R8.11, §13-42) | 아니다 — 무작위로 뽑혔을 뿐이다 |
| `human` + 판정 | 인간 검수 (B-55) | 판정이지 요청이 아니다 |

> **`submittedAt`** = 가장 최근 `auto` + `pass` 기록의 `reviewed_at`.
> **`reviewedAt`** = **그 시각 이후**의 마지막 `human` 기록의 `reviewed_at`.

**`reviewedAt` 을 회차 안으로 한정하는 이유.** 재제출·승격 직후에는 `null` 로 돌아간다 — **아직 답이 없다**는 것이 사실이기 때문이다. 지난 회차의 승인 시각을 그대로 두면 화면은 "검수 대기"라고 적으면서 승인 날짜를 함께 보여 준다.

#### `null` 의 뜻

| 값 | 뜻 |
|---|---|
| `submittedAt = null` | **검수를 요청한 적이 없다.** 아직 제출하지 않은 원고와 미리보기로만 만들어진 작품(§13-5), 자동 검수에서 반려되어 작품 자체가 만들어지지 않은 경우 |
| `reviewedAt = null` | **이번 회차를 사람이 판정한 적이 없다.** 검수를 기다리는 중이거나, `unlisted` 처럼 **자동 검수만으로 열린** 작품이다 (R8.6 — `public` 만 사람을 거친다) |

**자동 통과 시각을 승인 시각이라고 적지 않는다.** 그러면 화면은 **사람이 본 작품과 보지 않은 작품을 구분하지 못한다.** 기록이 하나도 없으면 두 값 모두 `null` 이며, **지어낸 시각을 넣지 않는다.**

#### 읽는 경로 — `common/spi`, 구현은 데이터 소유 모듈

`story_review` 를 쓰는 모듈은 `authoring` 하나다. 반면 "내가 만든 작품" 목록을 만드는 것은 `catalog` 이고 그 허용 의존은 `common` 뿐이다 — `catalog → authoring` 을 열면 `authoring → catalog` 와 만나 순환이 된다.

그래서 ADR-0002 와 같은 형태를 쓴다: **계약을 `common/spi` 에 두고 구현을 데이터 소유 모듈에 둔다.** 회차를 가르는 규칙이 한 곳에만 있게 되므로 목록(`getMyStories`)과 상세(`getDraftReview`)가 **같은 날짜를 말한다.**

**작품마다 묻지 않는다.** 목록은 쪽 전체의 `story_id` 를 한 번에 넘기고 조회 한 번으로 받는다 — 줄마다 물으면 20줄이 21번의 조회가 된다 (§15).

### §13-58 게시된 작품을 지운다는 것은 무엇인가 `[해소]` — **결정됨 (2026-09-03, 이슈 #290-3)**

계약의 `DELETE` 는 넷이었다 — `/sessions/{id}` · `/me` · `/authoring/drafts/{draftId}` · `/admin/blocklist/{id}`.
**원고는 지울 수 있는데 게시된 작품은 지울 수 없었다.** 와이어프레임 `3f` 의 정지 화면이 [작품 삭제] 버튼을
그렸고 갈 곳이 없어 프론트가 뺐다 (#290).

**채택: `DELETE /api/v1/stories/{storyId}` 를 열되 소프트 삭제.** 사용자에게는 '삭제됨'이고 내부는
`review_status = 'deleted'` 다. 이슈가 짚은 대로 `visibility: private` 이 그 역할을 대신할 수도 있었지만,
그것은 **"아무도 못 보게 한다"이지 "지운다"가 아니다** — 작성자의 목록에 남고, 되돌릴 수 있으며,
작성자가 무엇을 원했는지가 화면과 데이터 어디에도 기록되지 않는다.

#### 1. `deleted` 는 `review_status` 에 둔다

| 후보 | 판단 |
|---|---|
| `visibility` 에 넷째 값 | ❌ 가시성은 작성자가 `PATCH /visibility` 로 **언제든 되돌리는 다이얼**이다. 삭제를 거기 두면 가시성 변경 한 번이 삭제를 되돌린다. `private · unlisted · public` 은 **넓이의 눈금**이고 삭제는 눈금 위의 점이 아니다 |
| `story` 에 `deleted_at` 컬럼 | ❌ 상태가 두 곳에 생긴다. 컬럼과 상태가 어긋나면 어느 쪽이 진실인지가 매번 문제가 된다 — §13-48 이 "승격 요청" 컬럼을 같은 이유로 물린 자리다 |
| **`review_status` 에 `deleted`** ✅ | §13-9 가 **상태 머신**으로 정의한 자리이고, 되돌아오지 않는 값은 전이 규칙이 있는 쪽에 있어야 한다 |

**"검수 판정이 아닌데 왜 검수 상태인가"** — `draft` 도 판정이 아니다. 이 열거형은 *누가 판정했는가*가 아니라
*작품이 지금 어떤 상태인가*를 담으며, R2.3 의 타인 조회 조건이 `approved` 를 요구하므로 **여기에 값을 하나 두는
것만으로 모든 노출 경로가 한 번에 닫힌다.** 가시성에 두면 `visibility <> 'private'` 를 쓰는 모든 질의를
따로 고쳐야 하고, 그중 하나를 빠뜨린 날이 유출 경로다 (I-8).

#### 2. 되돌릴 수 없다

**복구 API 를 만들지 않는다.** 사용자에게 '삭제'라고 말한 이상 되돌리는 문을 함께 두는 쪽이 거짓말이다.
`deleted` 는 §13-9 상태 머신의 **흡수 상태**이며 나가는 전이가 없다.

CHECK 로는 단방향을 강제할 수 없다 — CHECK 는 한 행의 현재 값만 보고 이전 값을 모른다. 트리거로 옮기면
상태 전이 규칙이 마이그레이션과 애플리케이션 두 곳에 생기므로, **조회와 쓰기 양쪽에서** 지킨다.

- `statusOf` · `ownerStatusOf` 가 `deleted` 행을 **보지 못한다** → 제출·재제출·검수 판정·신고·가시성 변경·두 번째 삭제가 전부 `404` 로 끝난다
- `applyReview` · `suspend` 가 `deleted` 행을 **건드리지 않는다** → 삭제 직전에 상태를 읽어 둔 검수 판정이 나중에 도착해도 되살리지 못한다

조회만 막는 것으로는 부족하다. 검수자가 큐를 연 뒤 작성자가 지우는 순서가 실제로 가능하기 때문이다.

#### 3. 진행 중인 세션 — **새 에러 코드를 만들지 않는다**

지운 작품의 세션은 **사라진 작품의 세션과 같은 답**을 받는다. 그 자리는 이미 있다.

| 요청 | 답 |
|---|---|
| 다음 턴 | `423 STORY_SUSPENDED` — 읽기 전용이라는 뜻이다 |
| `resume` | `storySuspended` |
| 이미 읽은 턴 · 히스토리 | 그대로 열린다 |
| 이어하기 카드 · "내 세션" 목록 | 조용히 빠진다 (카드를 만들 작품 정보가 없다) |

`PlayTurnService` 와 `SessionResumeService` 는 **"없는 작품과 정지된 작품을 구분해 알릴 이유가 없다"**(I-8 과
같은 판단)를 이미 코드에 적어 두었고, 삭제는 그 판단에 정확히 들어맞는다. 구분해 알리면 **작성자의 처분이
독자에게 드러난다** — 읽던 사람이 알 필요가 없고, 알면 작성자를 특정할 단서가 된다.

**세션은 지우지 않는다.** 지운 것은 작품이지 그 사람이 플레이한 기록이 아니다.

#### 4. 작성자 본인만 — 공식 작품은 이 문이 아니다

공식 작품(`author_type = 'official'`)은 `story_author_type_ref_check`(catalog V12)가 `author_ref` 를 `NULL` 로
못박으므로 **어떤 요청자와도 일치하지 않는다.** 데이터가 이미 답을 갖고 있어 조건을 따로 쓰지 않았다.
공식 카탈로그를 내리는 것은 작성자의 처분이 아니라 운영의 조치이고 그 문은 §14 다.

**상태는 가리지 않는다.** 가시성 변경과 달리 `approved` 를 요구하지 않는다 — 그쪽은 작성자가 **검수 결과를
되돌리는** 길이 될 수 있어 막지만, 삭제는 어떤 판정도 되돌리지 않는다. 정지된 작품을 지우는 것은 정지를 푸는
일이 아니라 **더 내리는** 일이다. 검수를 기다리던 작품을 지우면 큐에서도 빠진다 — 검수자가 아무에게도 보이지
않을 작품을 읽지 않는다.

#### 5. 기록은 남는다

§13-44 와 같은 근거다. 작품에는 **플레이한 사람들의** 기록이 매달려 있고 그것은 작성자의 것이 아니다.

| 남는 것 | 사라지는 것 |
|---|---|
| `play_session` · `turn` · `game_state_snapshot` · `story_summary` | 라이브러리 목록 · 상세 · 이어하기 카드 |
| `ending_stat` (도달률은 `(story_id, ending_no)` 집계다) | 작성자의 "내 작품" 목록 |
| `content_report` · `story_review` (신고와 검수의 기록) | 검수 큐 |
| `story_version` · `chapter_def` · `ending_def` (세션이 고정한 버전이다, I-4) | — |

**작품 개수 상한은 지운 작품을 세지 않는다** (R8.12). 지우고도 자리가 비지 않으면 상한에 닿은 작성자에게
**남은 선택지가 아무것도 바꾸지 않는다.**

#### 원고는 지우지 않는다 — 그리고 그 원고는 새 제출이 된다

`story_draft` 는 그대로 둔다. 지운 것은 작품이지 원고가 아니다. 다만 원고는 자기 작품을 기억하므로(B-56),
그 작품이 없어진 원고의 제출은 **재제출이 아니라 새 제출**이다 — 새 작품이 되고 개수 상한을 다시 센다.
`getDraftReview` 도 그 원고를 `draft`(아직 내지 않음)로 답한다. `404` 로 답하면 작성자는 **원고가 사라졌다**고
읽는데, 사라진 것은 작품이다.

이 자리는 삭제 이전에도 비어 있었다 — 미리보기가 만든 작품을 파기(B-61)가 지우면 같은 상태가 된다.

### §13-59 자동으로 내려간 것을 사람이 다시 보는 길 `[해소]` — **결정됨 (2026-09-03, 이슈 #290-2)**

와이어프레임 `3f` 의 정지 화면은 *"검토 후 복구되거나 삭제될 수 있습니다. **이의가 있으면 문의해 주세요.**"* 와 [이의 제기] 버튼을 그렸고, **갈 곳이 없어 둘 다 빠졌다** (#290). 문의하라고 적어 놓고 문의할 곳이 없으면 안내가 아니라 방치다.

**채택: `POST /api/v1/stories/{storyId}/appeal` 을 연다.** 신고 누적으로 **자동** 정지된 작품에 대해 작성자가 재검토를 요청하는 경로다 (R8.9).

#### 이 요청이 실제로 바꾸는 것

**작품의 상태를 바꾸지 않는다.** 정지된 작품은 **이미** 인간 검수 큐에 있다 — §13-41 이 *"정지된 작품은 검수 큐에 오른다"* 로 정했고 큐가 `in_review` 와 `suspended` 를 함께 본다. 그러므로 "요청하면 큐로 돌아간다"는 말은 **이미 참인 것을 다시 말하는 것**이고, 그것을 API 로 만들면 아무것도 바꾸지 않는 버튼이 된다. 여기서 `review_status` 를 움직이면 더 나쁘다 — 작성자가 검수 결과를 되돌리는 길이 열린다 (I-8).

바뀌는 것은 둘이다.

| | 무엇 | 왜 |
|---|---|---|
| **기록** | `story_appeal` 한 행 — 작품 · 작성자 · 사유 · 시각 | *자동으로 내려갔다*와 *내려갔고 작성자가 다투었다*는 다른 사실이다. 사후에 "정지가 얼마나 다투어졌는가"는 이 표로만 답해진다 |
| **신호** | 검수 큐의 `ReviewQueueItem.appealed` | 검수자가 목록에서 그것을 알아본다. 알아보지 못하면 기록은 아무에게도 닿지 않는다 |

**순서는 바꾸지 않는다.** 요청은 공짜이므로 앞세우면 줄을 사는 길이 되고, **아직 아무도 보지 못한** 작품들이 그만큼 밀린다 (§13-42 의 큐 순서와 같은 이유).

#### 몇 번 요청할 수 있는가 — **정지 건마다 한 번**

작품마다 한 번으로 정하면 한 번 복구된 작품은 **두 번째 자동 정지에 아무 말도 못 하게 된다.** 무제한이면 큐를 반복해 채울 수 있다.

**정지 사건에는 id 가 없다** — 정지는 `review_status` 를 바꾸는 일이지 행을 만드는 일이 아니다 (§13-41). 대신 **인간 판정이 그 사건을 닫는다**: 통과하면 작품이 돌아오고 반려하면 내려간 채로 끝난다. 그래서 규칙은 하나다.

> **요청 뒤에 인간 검수 이력이 얹히지 않았으면 그 요청은 열려 있다.** 열려 있는 동안 두 번째 요청은 `409 ALREADY_EXISTS` 다.

같은 규칙 하나가 "답을 받기 전 두 번 못 낸다"와 "다시 정지되면 다시 낼 수 있다"를 함께 말한다. **자동 이력은 세지 않는다** — 재스캔·샘플링은 사람이 답한 것이 아니다 (§13-42).

#### 작성자가 사유를 쓸 수 있는가 — **쓴다. 검수자만 읽는다**

사유는 **필수**이며 500자 상한이다. 정지된 작품은 이미 큐에 있으므로 사유 없는 요청은 검수자에게 아무것도 주지 않는다 — 그러면 이 경로는 큐를 다시 채우는 버튼일 뿐이다.

**노출면을 열지 않는다** (S-11). 이 문자열은 요청의 응답에도, 검수 큐의 한 줄에도, 다른 사용자가 보는 어떤 화면에도 실리지 않는다. AI 페이로드로도 가지 않는다.

**Safety L1 을 태우지 않는다.** I-17 이 막는 것은 **AI 로 들어가는** 무검열 자유 입력이고, 이 글은 프롬프트로도 다른 사용자에게도 가지 않는다 — 유일한 독자가 검수자다. 그리고 정지를 다투는 글은 **걸린 표현을 인용할 수밖에 없어**, 여기에 L1 을 걸면 정확히 이의를 제기해야 하는 사람이 제기하지 못한다. 막는 수단은 길이 상한과 **노출면의 부재**다.

#### 누가 부를 수 있는가

**작성자 본인**, 그리고 작품이 `suspended` 일 때만이다. 남의 작품은 `404` 다 — 존재를 알려 주지 않는 것이 가시성 변경(§13-42, #245)과 같은 규칙이다. 정지 상태가 아니면 `409 STORY_NOT_SUSPENDED` 이며, `400` 이 아닌 이유는 **요청의 형태가 아니라 작품이 놓인 자리**가 맞지 않기 때문이다 — 400 으로 답하면 클라이언트는 자기가 보낸 값을 고치려 든다.

#### 사람이 반려한 작품(`rejected`)에는 열지 않는다

이슈가 말한 것은 **자동 정지**다 (*"자동으로 내려간 것을 사람이 다시 볼 길"*). `rejected` 는 이미 사람이 본 결과이며, 같은 판정을 다시 보여 달라고 하는 것은 재검토가 아니라 재요청이다. 그리고 **고쳐서 다시 내는 길이 그쪽에 이미 있다** (§13-40 — 재제출은 같은 작품에 새 버전을 만든다). 두 경로를 겹치면 반려당한 작품이 수정 없이 큐를 왕복할 수 있다.

넓히지 않은 이유가 하나 더 있다 — **넓히면 되돌리기 어렵다.** 좁게 열어 두고 필요가 드러나면 그때 넓힌다.

> **원문 확인 없이 내린 결정이다.** `docs/internal/` 이 이 작업 시점의 환경에 없어 R8.9 원문을 대조하지 못했다. 위 판단의 근거는 이슈 #290 · §13-41 · §13-42 와 레포의 `ReviewQueueService` · `StoryPublisher` 다.

**그때까지 계약은 "통화가 정해지지 않았다"를 명시한다.** 지어낸 통화를 적는 것보다 정확하고, 값을 채우려는 사람이 이슈 #311 을 먼저 보게 된다.

### §13-60 리프레시 토큰은 재발급 경로 전용 쿠키로 오간다 `[해소]` — **이슈 #278 (2026-09-03)**

**ADR-0008 이 정본이다** (`docs/adr/0008-refresh-token-transport.md`). 여기서는 계약이 무엇이 되었는지만 적는다.

#### 무엇이 문제였나

`GET /me`(#262)가 *"지금 로그인돼 있는가"* 를 물을 자리를 만들었지만 **물어볼 토큰 자체가 새로고침에서 사라졌다.** 메모리에만 두면 탭을 새로 고치는 순간 없고, `localStorage` 에 두면 XSS 하나로 30일짜리 리프레시 토큰이 나간다. 즉 **"로그인 유지"가 계약상 구현 불가능했다.**

#### 계약이 어떻게 바뀌나

| | 전 | 후 |
|---|---|---|
| `TokenResponse` | `accessToken` · `refreshToken` · `tokenType` · `expiresIn` | **`refreshToken` 이 빠진다.** 셋이다 |
| `RefreshRequest` | `{ refreshToken }` | **없어진다.** 재발급 요청에 본문이 없다 |
| `POST /auth/oauth/{provider}` 200 | 본문뿐 | `Set-Cookie` 가 붙는다 |
| `POST /auth/refresh` | 본문의 토큰으로 인증 | **쿠키로 인증한다.** `X-XSRF-TOKEN` 헤더를 함께 요구한다 |
| 액세스 토큰 | `Authorization: Bearer` | **그대로다** |

쿠키의 속성 넷 중 셋은 서버가 고정한다 — `HttpOnly`, `Path=/api/v1/auth/refresh`, `SameSite=Strict`. `Secure` 만 배포 설정(`auth.refresh-cookie.secure`)이며 **기본값이 없다**(§7.3). 값이 없으면 부팅이 실패한다.

#### 왜 본문에서 빼는가 — 남겨 두면 아무것도 하지 않기 때문이다

`HttpOnly` 는 *"JS 가 읽을 수 없다"* 는 보장이다. **같은 값을 본문으로도 주면 그 보장이 문장으로만 남는다** — 본문으로 나간 값은 JS 가 읽었다는 뜻이고, 그 값이 어디로 가는지 서버는 알지 못한다. `RefreshRequest` 를 없애는 것도 같은 이유다: 자격 증명을 받는 자리가 둘이면 그중 약한 쪽이 실질 계약이 된다.

#### 새로 감당하는 것 — CSRF 를 그 경로에서만

쿠키는 브라우저가 알아서 붙는다. 그것이 새로고침을 견디는 이유이자 위조가 성립하는 이유다.

- **`/api/v1/**` 의 CSRF 면제를 `POST /api/v1/auth/refresh` 하나에서 좁힌다.** 나머지는 면제 그대로이며, 거기서 켜면 토큰 없는 요청이 **401 이 아니라 403** 이 되어 계약(§13.1)의 `UNAUTHENTICATED` 가 나가지 않는다
- 방식은 **double-submit 쿠키**다. 서버가 모든 `/api/v1/**` 응답에 `XSRF-TOKEN` 쿠키를 갱신하고, 프론트가 그 값을 `X-XSRF-TOKEN` 헤더로 돌려보낸다
- **CORS 에 자격 증명이 켜졌다.** 허용 오리진 목록은 이제 *"응답을 읽을 수 있는 곳"* 이 아니라 **"자격 증명을 붙여 부를 수 있는 곳"** 이다 — `CorsProperties` 의 와일드카드 거부가 선택에서 필수로 바뀌는 지점이다 (#248)

#### 배치 제약 — 프론트와 API 는 같은 사이트에 있어야 한다

`SameSite` 는 오리진이 아니라 **사이트**를 본다. 다른 오리진이어도 같은 사이트면 `Strict` 로 동작하며(포트는 보지 않는다), 프론트가 CSRF 쿠키를 읽을 수 있으려면 그 조건이 필요하다. **서브도메인으로 가르는 배치는 CSRF 쿠키에 `Domain` 이 필요해지므로 그때 ADR-0008 을 다시 본다.**

#### 프론트가 고쳐야 하는 것

1. 로그인 응답에서 `refreshToken` 을 읽지 않는다 — **없다**
2. 로그인·재발급 요청에 `credentials: 'include'` 를 실는다. 실지 않으면 브라우저가 `Set-Cookie` 를 버린다
3. 재발급 요청에 본문을 보내지 않고 `X-XSRF-TOKEN` 헤더를 싣는다

#### 범위 밖

**로그아웃 경로는 계약에 없고 만들지 않는다.** 탈퇴(`DELETE /api/v1/me`)에서도 쿠키를 지우지 않는데, 재발급이 회원 상태를 먼저 보므로 **탈퇴한 회원의 쿠키는 남아 있어도 `403`** 이기 때문이다 — 쿠키가 남는 것과 자격이 남는 것은 다르다. *"브라우저에서 흔적을 지운다"* 는 별개의 요구이며 로그아웃 경로를 만드는 시점의 것이다.

> **원문 확인 없이 내린 결정이다.** `docs/internal/` 이 이 작업 시점의 환경에 없어 R 조항 원문을 대조하지 못했다. 근거는 이슈 #278 의 선택지와 소유자의 결정 (a) 다.

### §13-61 검수자는 무엇을 보고 판정하는가 `[해소]` — **이슈 #316-① (2026-09-03)**

큐(`listReviewQueue`)는 **무엇을 볼 차례인가**를 답한다. `ReviewQueueItem` 은 그래서 원고 본문을 담지 않고, 스스로 *"원문 열람은 **감사가 걸린 다른 문**"* 이라고 적었다 — **그 문이 계약에 없었다.** 지금 계약대로면 관리자는 제목과 상태만 보고 승인/반려한다. 그것은 검수가 아니다.

`GET /api/v1/admin/reviews/{storyId}` (`readReviewManuscript`) 가 그 문이다.

#### 무엇을 담는가

| 담는 것 | 왜 |
|---|---|
| 제목 · 한 줄 소개 · 세계관 소개 · 상태 · 가시성 · 생성 시각 | 기본 정보. 어떤 작품을 왜 지금 보는가 |
| 작성자 **표시명** | §13-7 — `player_ref` 는 나가지 않는다 (I-3). 설정하지 않았으면 `null` 이고 서버가 이름을 지어내지 않는다 |
| 세계관 프롬프트 원문 | **UGC 원고의 본체다.** 매 턴 모델에게 들어가는 문장이므로 판정 대상의 중심이다 |
| 캐릭터 이름 + 페르소나 프롬프트 | 작품 상세 화면(`CharacterCard`)은 페르소나를 감춘다. **검수는 반대다** — 그것을 보지 않은 승인은 작품의 절반만 본 승인이다 |
| 챕터 번호 · 제목 · 최소/최대 턴 | 이야기의 뼈대 |
| 엔딩 번호 · 라벨 · **에필로그 원문** · 기본/비밀 여부 | 에필로그는 독자가 마지막에 읽는 작성자의 문장이다 |
| 자동 검수 요약 — 판정 · **카테고리** · 시각 | R8.5 · R8.7. 어떤 항목에 걸렸는지는 담지 않는다 — 그러면 이 응답이 우회 사전이 된다 (S-11) |

**가장 마지막 버전을 본다** (R8.8). 승인이 현재로 만드는 것이 그 버전이므로, 판정과 열람이 다른 버전을 보면 **승인된 적 없는 원고가 열린다.**

**상태로 거르지 않는다.** 큐는 기다리는 것만 고르지만 이 문은 **이미 지목된 한 건**을 여는 자리다 — 여기서 상태를 보면 방금 판정한 작품을 다시 열 수 없게 된다.

#### 무엇을 담지 않는가

- **미리보기 3턴.** 와이어프레임 `3h` 가 요구하지만 **검수 대상 작품에서 그 턴으로 가는 길이 없다.** §13-5 대로 미리보기는 임시 `draft` · `private` **작품**과 그 위의 테스트 세션을 만들고, 제출은 그것과 **별개의 작품**을 발행한다. 원고가 기억하는 작품 id 는 제출된 쪽 하나이며, 미리보기 작품은 아무 데도 연결되지 않은 채 파기 대상이 된다 (§13-37, B-61). **없는 것을 지어내는 대신 비웠다** — 담으려면 미리보기 세션을 원고에 연결하고 파기 정책을 다시 정해야 하며, 그것은 별개의 작업이다.
- **진입 조건식·엔딩 조건식.** 판정 로직이지 사람이 읽는 문장이 아니다.
- **`player_ref`** (I-3) · **검수 이력 전체**(#316-③ 이 답한다) · **신고 내역**(#316-② 가 답한다).
- **캐릭터 초상·커버 이미지.** 이미지 업로드 자체가 아직 열려 있지 않다 (#315).

#### 감사 기록 — 두 줄이 남는다

| 기록 | 어디에 | 실패하면 |
|---|---|---|
| 관리자 **행위** (R14.5) | `admin_audit_log` — `AdminAccessGuard.recordAction("admin.review.manuscript", …)` | 행위를 막지 않는다 |
| **원문 열람** (R12.3, S-5) | `access_audit_log` — `AccessAuditRecorder.record(…, STORY_DRAFT, storyId)` | **원문이 나가지 않는다** |

**기존 장치를 그대로 쓴다.** `AuditedResource.STORY_DRAFT` 는 *"검수 전 UGC 원고. 작성자 말고는 볼 수 없어야 하는 것"* 으로 이미 정의되어 있었고, 이 문이 그 값의 첫 사용처다.

**순서가 규칙이다.** ① 작품을 찾고 ② 열람을 기록하고 ③ 원문을 읽는다. ①을 뒤로 미루면 감사 로그가 존재하지 않는 작품으로 채워지고, ②를 뒤로 미루면 **읽고 나서 기록에 실패한** 열람 — 곧 기록되지 않는 열람 경로 — 가 생긴다.

#### 세 조건은 이 문에도 서 있다 (S-4)

역할 · IP 허용목록 · 2FA 승격을 모두 통과해야 한다. 여기 열리는 것은 **아직 아무도 보지 못한 작품의 원문**이며, 그것이 새면 검수 전 UGC 가 새는 것과 같다 (I-8).

#### 큐는 작성자를 감추는데 여기는 보인다

의도된 차이다. 큐는 **줄줄이 흐르는 목록**이라 이름이 함께 오면 그것이 순서와 판정에 섞인다. 반면 상세는 **한 건을 열어 판정하는 자리**이고, 신고 누적으로 내려온 작품(R8.9)이 누구의 것인지는 판정의 재료다. 나가는 것은 어느 쪽이든 **표시명뿐**이다.

### §13-64 사람이 손으로 내리는 정지 `[해소]` — **이슈 #316-④ (2026-09-03)**

자동 정지는 신고 임계가 한다 (R8.9). 그런데 **사람이 손으로 정지시키는 값이 없었다** — `decideReview` 의 판정은 `pass` · `reject` · `hold` 셋이고, 관리자 화면(`yonggyu/neowadaeum-frontend#62`)이 그리는 조치는 **작품 정지 / 반려 / 기각 / 작성자 경고** 넷이다. 정지가 그중 어디에 해당하는지 답이 없었다.

**채택: `ReviewVerdict` 에 `suspend` 를 더해 네 값으로 한다.**

§13-41 이 *"자동으로 내린 것을 자동으로 올리지 않는다"* 로 정한 이상 **그 반대 방향에도 사람 손이 필요하다.** 그 손이 없으면 임계만이 유일하게 내리는 길이 되고, 임계에 닿지 않은 것은 — 명백히 내려야 하는 것이라도 — 아무도 내릴 수 없다.

새 엔드포인트를 만들지 않은 이유가 있다. 정지는 **검수자가 검수 화면에서 내리는 판정**이고, `story_review` 는 이미 **왜 그렇게 됐는지**를 담는 자리다 (append-only, I-5). 별도 경로를 파면 같은 사실이 두 표에 갈라져 남는다.

#### 정지는 가시성을 건드리지 않는다

**§13-41 의 규칙을 그대로 따른다.** 자동 정지(`StoryPublisher.suspend`)가 이미 `review_status` 만 바꾸며, 수동 정지도 **같은 자리를 쓴다** — 두 경로가 같은 일을 다르게 하면 되돌리는 규칙도 둘이 된다.

가시성을 지우면 사람이 나중에 통과시킬 때 **어디로 돌려놓아야 하는지**를 알 수 없다. 신고 하나로 내려간 `unlisted` 작품이 복귀하면서 공개되면 그것은 복귀가 아니다.

#### 어느 상태에서 부를 수 있는가 — `approved` 만

`decideReview` 는 *"기다리는 중인 작품만"* 이고 아니면 `409 REVIEW_NOT_PENDING` 이다. 그런데 **수동 정지의 대상은 이미 승인돼 돌아다니는 작품**이고, 그런 작품은 정의상 큐에 없다.

| 후보 | 문제 |
|---|---|
| (i) `suspend` 도 큐 안에서만 | **사후 샘플링(R8.11)이 뽑아 준 것만 내릴 수 있다.** 무엇을 내릴지를 사실상 난수가 고르게 되며, 명백히 내려야 하는 작품을 두고 검수자가 **뽑히기를 기다린다** |
| **(ii) `suspend` 만 큐 밖에서도** ✅ | **채택.** 409 규칙에 예외가 생기지만, 그 예외가 왜 안전한지 아래에 적는다 |

**채택: `suspend` 는 `review_status = 'approved'` 인 작품에만 내린다.** §13-9 의 상태 전이 `approved → suspended` 가 이미 그 하나뿐이다 — 새 전이를 만들지 않았다.

**예외가 안전한 이유.** 409 가 막으려던 것은 *"두 검수자가 같은 작품을 각자 열어 두면 나중에 누른 쪽이 이기고, **진 쪽은 자기 판정이 사라진 줄도 모른다**"* 는 경합이다. 정지는 그 경합을 만들지 않는다 — **한 방향으로만** 움직이기 때문이다.

- **아무것도 열지 않는다.** 가시성을 넓히는 일이 없으므로, 잘못 눌러도 노출이 늘어나지 않는다 (I-8).
- **아무 판정도 끝내지 않는다.** 정지된 작품은 **큐에 남고** (§13-41), 이어지는 `pass` / `reject` 를 그대로 받는다. 사라지는 판정이 없다.
- **되돌릴 자리가 남는다.** 가시성을 건드리지 않으므로 `pass` 한 번이 내려가기 전 그 자리로 복귀시킨다.

**`in_review` 를 정지시키지 않는 이유.** 그 작품은 아직 아무에게도 보인 적이 없어 내릴 것이 없고 (R2.3 의 조회 조건이 `approved` **AND** `visibility <> private`), 정지시키면 **"어디서 왔는가"라는 표식을 잃는다** (§13-48) — 통과가 `public` 을 열어야 할 작품이 있던 자리로 돌아가게 된다. 열지 않기로 하는 판정은 `reject` 다.

#### 이미 `suspended` 인 것을 또 정지시키면 — 409

**멱등하지 않다.** 조건이 `approved` 하나이므로 `suspended` 는 그대로 `409 REVIEW_NOT_PENDING` 이다.

이력이 append-only 이므로 (I-5) 멱등하게 받으면 **정지 기록이 두 줄 남고, 그것은 두 번의 사건으로 읽힌다** — 사후에 "이 작품이 몇 번 내려갔는가"를 물으면 틀린 답이 나온다. 그리고 이미 내려간 작품에 남은 일은 `pass` 또는 `reject` 이지 정지가 아니므로, 409 는 검수자에게 **당신이 하려던 일은 이미 되어 있다**를 알린다.

`StoryPublisher.suspend` 의 조건절(`review_status <> 'suspended'`)은 그대로 둔다 — 자동 정지에는 그 멱등이 필요하다. 신고는 계속 들어오고 매번 상태를 바꿀 이유가 없다.

#### 사유는 카테고리만이다

`reasons` 는 `SafetyCategory` 열거형만 받는다 (R8.7, S-11). 정지도 예외가 아니다 — 이 값은 **작성자에게 그대로 전달**되므로, 검수자가 문장을 적을 수 있으면 **걸린 표현이 그 문장에 실려** 작성자에게 간다. 그것이 곧 우회 사전이다. 검수자가 문장을 적을 자리는 `note` 이고 **그것은 작성자에게 가지 않는다.**

#### 작성자는 그 사실을 어떻게 아는가 — 이미 있는 두 경로

새로 만들 것이 없다. `ReviewStatus` 열거형이 `suspended` 를 이미 갖고 있고 두 응답이 그 값을 그대로 싣는다.

| 경로 | 필드 |
|---|---|
| `getDraftReview` (`ReviewStatusResponse`) | `reviewStatus` · `rejectReasons` |
| `getMyStories` (`MyStoryItem`) | `reviewStatus` · `rejectReasons` |

작성자가 **왜** 내려갔는지는 카테고리로 본다. 이의는 §13-59 의 재검토 요청이 받는다.

#### '작성자 경고'를 만들지 않은 이유 — **범위 밖**

관리자 화면의 조치 넷 중 **작성자 경고만 대응하는 값이 없다.** 만들지 않았다.

**보낼 곳이 없기 때문이다.** 지금 계약에 알림 채널이 없다 — 푸시도, 메일도, 인앱 알림함도 없다. 판정값만 더하면 경고는 `story_review` 에 한 줄로 남고 **작성자는 영원히 그것을 보지 못한다.** 그러면 검수자는 경고를 보냈다고 믿고, 작성자는 아무것도 받지 않은 채 다음 위반으로 정지된다 — **아무 일도 하지 않는 것보다 나쁘다.**

경고가 의미를 가지려면 **알림 채널이 먼저 있어야 하고**, 그것은 이 작업의 범위가 아니다. 채널이 생기면 그때 `warn` 을 더한다 — 지금 자리만 만들어 두지 않는 이유는, 비어 있는 자리가 **있는 것처럼 보이기** 때문이다.

#### 마이그레이션

`story_review.verdict` 의 CHECK 제약에 `'suspend'` 를 더한다 (`catalog/V16`). **컬럼도 표도 늘리지 않는다** — 이미 있는 어휘에 값 하나가 더해질 뿐이다.

### §13-62 검수자는 무엇이 신고됐는지 어떻게 보는가 `[해소]` — **이슈 #316-② (2026-09-03)**

신고는 **접수 경로 하나**(`POST /api/v1/reports`)뿐이고 응답 본문도 없었다. 그래서 검수 화면은 좌측의 *신고 목록(사유 · 신고 수 · 대상 turn)* 을 그릴 수 없었고, 검수자는 **제목과 상태만 보고 승인/반려**하게 되어 있었다. 그것은 검수가 아니다.

**채택: `GET /api/v1/admin/reviews/{storyId}/reports` 하나를 연다.**

#### 별도의 큐가 아니다

§13-41 이 임계에 닿은 작품을 **같은 인간 검수 큐**에 `suspended` 로 올리고, `ReviewQueueItem.reviewStatus` 가 갈래를 구분한다. 없던 것은 큐가 아니라 **그 안에서 무엇이 신고됐는가**였다. 그래서 새 큐를 만들지 않고 큐의 형제 경로로 붙인다 — 판정(`/verdict`)이 서 있는 자리 옆이다.

#### 담은 것 — 집계와 목록을 함께 준다

| 담은 것 | 왜 |
|---|---|
| **사유별 집계**(사유 · 건수) | 검수자가 판정에 쓰는 것이 이 숫자다. **전건**이며 상한이 없다 — 페이지에 잘리면 같은 작품이 볼 때마다 다르게 보인다 |
| **개별 신고**(접수 시각 · 상태 · 대상 턴 · 사유) | 집계가 말한 것을 되짚는 재료다. 최근 것부터이며 **상한이 있다** |

한 경로가 둘을 함께 답한다. 나누면 검수자가 두 번 요청해야 하고, **그 사이에 집계와 목록이 다른 시점을 가리킨다.**

#### 빼놓은 것 — 신고자

**`reporter_ref` 를 싣지 않는다** (I-3).

누가 신고했는지는 **판정에 쓰이지 않는다.** 판정은 *무엇이 몇 건 신고됐는가*로 하며, 신고자를 알면 그것이 판정에 섞인다 — 검수 큐가 작성자를 담지 않는 것과 같은 이유다 (B-55). **쓰이지 않는 식별자는 담지 않는다**는 것이 I-3 의 기본값이고, 담아야 할 근거가 제시되지 않았다.

보장을 DTO 한 곳에만 두지 않았다. `ContentReport` 에 `reporterRef` 게터를 만들지 않는다 — **없는 게터는 잊혀도 새지 않는다.**

#### 빼놓은 것 — 신고자가 쓴 자유 문장(`detail`)

**관리자에게도 보내지 않는다.** 세 가지 이유다.

- 자유 문장에는 **신고자를 특정하는 말**이 그대로 들어간다("제가 쓴 작품을 베꼈다"). 신고자를 빼면서 그가 쓴 문장을 실으면 뺀 것이 되지 않는다.
- 자유 문장에는 **걸린 표현이 원문 그대로** 들어간다 (S-11). R8.7 이 반려 사유를 카테고리만으로 제한한 것과 같은 축이다.
- **판정에 먼저 필요한 것은 무엇이 몇 건인가**다. 사유 카테고리와 건수로 분류가 끝나고, 실제 판정은 원고를 열어서 한다 (#316-①).

문장은 **표에 남는다.** 사후 조사에 필요해지면 그때 별도의 문을 연다 — 좁게 열어 두고 필요가 드러나면 넓히는 편이 그 반대보다 되돌리기 쉽다.

#### 작품 신고만 온다

턴 신고는 **여기에 오지 않는다.** 턴 신고에서 작품을 알아내려면 `authoring` 이 `play` 의 세션 표를 읽어야 하고, 스토어가 다르며(§5.3) 그 참조는 애플리케이션 레벨에서도 열려 있지 않다 — §13-41 이 정지 임계에 대해 내린 것과 **같은 판단**이다. 정지 임계가 세는 것과 검수자가 보는 것이 같아야 **왜 내려갔는지**가 화면에서 설명된다.

그래서 응답의 `turnNo` 는 현재 구현에서 항상 `null` 이다. **키를 없애지 않는다** — 신고 한 건이 갖는 자리이고, 프론트가 키 존재 여부로 분기하지 않게 한다.

#### 신고된 장면의 원문은 담지 않는다

담을 대상이 없다. 작품 신고에는 `session_id` 도 `turn_no` 도 없고(그 두 컬럼은 턴 신고의 것이다), 턴 신고는 위 이유로 작품에 붙지 않는다. **원문을 실으려면 먼저 턴을 작품에 잇는 길**(`play` 쪽 SPI 로 턴 → 작품 역참조)**이 필요하며, 그것은 이 결정의 범위 밖이다.** 판정에 먼저 필요한 것은 무엇이 몇 건 신고됐는가다.

#### 읽는 것도 감사에 남는다

`admin.review.reports.read` 로 기록한다 (R14.5). 신고는 **이용자가 쓴 것**이고, 특정 작품에 대해 사람들이 무엇을 문제 삼았는지를 **누가 언제 열었는지**는 사후에 되짚을 수 있어야 한다 — 큐 목록(무엇을 볼 차례인가)과 다른 성격이며, 원고 열람(#316-①)과 같은 쪽이다. 기록에 남기는 것은 **대상과 건수**까지다.

문은 형제와 같다 — S-4 의 세 조건(역할 · 허용목록 · 승격)을 그대로 통과해야 한다.

> **원문 확인 없이 내린 결정이다.** `docs/internal/` 이 이 작업 시점의 환경에 없어 R8.9 · R13.5 원문을 대조하지 못했다. 위 판단의 근거는 이슈 #316 · §13-41 · §13-42 와 레포의 `ContentReport` · `ReportService` · `ReviewQueueService` 다.

### §13-63 지난 판정을 어떻게 보는가 `[해소]` — **이슈 #316-③ (2026-09-03)**

Admin 검수 화면(`3h`)의 상단 탭 넷 중 *"처리 이력"* 이 그릴 것이 없었다. **지난 판정을 조회할 경로가 계약에 없다.** 데이터는 이미 있다 — `story_review` 는 append-only 이고 `(story_id, reviewed_at DESC)` 인덱스까지 B-55 가 만들어 두었다 (§13-57 이 같은 표에서 신청·승인 시각을 읽는다). **없는 것은 문 하나다.**

#### 채택: 작품 하나의 이력 — `GET /api/v1/admin/reviews/{storyId}/history`

두 갈래가 있었다.

| 후보 | 판단 |
|---|---|
| **(i) 작품 하나의 이력** ✅ | **판정에 직접 쓰인다.** 검수자가 지금 보는 작품이 *전에 무엇으로 걸렸던 작품인지*는 이번 판정의 근거다 — 재제출(§13-40)과 승격(§13-48)이 같은 작품을 여러 번 큐에 올리므로 흔한 상황이다. 범위가 좁고 형제 경로(`/{storyId}/verdict`)와 같은 자리에 선다 |
| (ii) 전체 이력 — 최근 판정을 시간순으로 | **아직 무엇을 답해야 하는지가 정해지지 않았다.** 운영 지표인지(누가 얼마나 처리했는가), 되짚기인지(무엇이 반려됐는가)에 따라 필요한 필드와 정렬이 갈리고, 전자는 **검수자별 처리량**을 답해야 하는데 그것은 이 응답이 담지 않기로 한 값이다(아래) |

**둘 다 만들지 않았다.** 이슈의 문장(*"상단 탭 넷 중 처리 이력이 여기 걸린다"*)은 탭이 큐 목록의 것인지 상세 패널의 것인지를 가르지 않는다. 확신이 서지 않는 쪽을 지금 계약에 넣으면 **프론트가 쓰지 않는 경로**가 생기고, 그것은 다음 사람에게 "이미 있다"고 읽힌다. (ii) 가 실제로 필요하면 **후속 이슈**로 연다 — 그때는 이 경로를 지우지 않고 옆에 선다.

#### `reviewer_ref` 는 담지 않는다 (I-3)

그 값은 `player_ref` 다. 관리자 화면이라는 이유로 실으면 **화면 하나가 회원 식별자를 나르는 통로**가 된다.

**표시명으로 바꿔 싣지도 않는다.** catalog 가 가진 표시명(`author_profile`)은 **작성자**의 것이고 검수자의 것이 아니다 — 실으려면 Identity 를 이 경로에 끌어와야 하고, 그것은 *"누가 판정했는가"* 하나를 위해 경계를 여는 일이다. 그 물음에 답하는 자리는 이미 있다: 관리자 감사 기록이 `admin.review.verdict` 를 `admin_user_id` 와 함께 남긴다 (R14.5). **이력은 무엇이 어떻게 판정됐는가를 답하고, 감사는 누가 했는가를 답한다.**

응답 DTO 에 그 자리를 두지 않은 것이 구조적 보장이다 — 서비스가 돌려주는 값에도 없으므로 실수로 실릴 곳이 없다.

#### 담는 것 — 단계 · 판정 · 사유 카테고리 · 시각 · `note`

- **`stage` 를 담는다.** 자동 통과는 **사람이 본 것이 아니다** (R8.6). 구분이 없으면 화면은 아무도 보지 않은 작품을 승인된 작품으로 적는다 — §13-57 이 `reviewedAt` 을 사람 판정으로만 채운 것과 같은 이유다.
- **`reasons` 는 카테고리만이다** (R8.7, S-11). 저장된 것이 이미 카테고리 배열이므로 그대로 나간다.
- **`note` 는 담는다.** 관리자 전용 경로이고(S-4) 검수자가 문장을 적는 유일한 자리다. **작성자 응답에는 가지 않는다** — 작성자가 보는 검수 상태 응답은 카테고리만 싣는다.

#### 페이지네이션은 두지 않는다

한 작품의 기록은 **제출 회차 수를 따라간다** — 제출·재제출·승격·재스캔·샘플링·사람 판정이 전부 합쳐도 몇 건 수준이다. 커서를 두면 **화면이 쓰지 않는 상태**가 계약에 들어가고, 프론트는 마지막 쪽까지 도는 코드를 쓴 뒤 그것이 한 번도 두 쪽이 되지 않는 것을 보게 된다. 늘어나는 것이 관측되면 그때 더한다.

#### 없는 작품과 판정 없는 작품은 다르다

작품이 없으면 `404` 이고 판정이 없으면 **빈 목록**이다. 아직 아무도 판정하지 않은 작품은 존재한다 — 미리보기로만 만들어진 원고가 그렇다 (§13-5). 그것을 `404` 로 답하면 화면은 **없는 작품**이라고 적는다. 지워진 작품은 `404` 다 (§13-58).

#### 감사 기록을 남기지 않는다

R14.5 가 기록을 요구하는 자리는 **상태를 바꾸는 판정**과 **원고 원문 열람**이다 (#316-①). 이력은 관리자가 **자기들이 남긴 기록**을 다시 보는 일이고 UGC 원문을 담지 않는다 — 큐를 여는 `listReviewQueue` 가 감사를 남기지 않는 것과 같은 판단이다. 문 자체는 형제와 같다: 역할 · 허용목록 · 승격 세 조건 전부다 (S-4).

> **원문 확인 없이 내린 결정이다.** `docs/internal/` 이 이 작업 시점의 환경에 없어 R8.7 · R14.5 원문을 대조하지 못했다. 근거는 이슈 #316 과 §13-41 · §13-42 · §13-57, 그리고 레포의 `ReviewQueueService` · `StoryReviewTimeline` · `AdminAccessGuard` 다.

### §13-65 이미지는 어떻게 올라오고 언제 보이는가 `[해소]` — **결정됨 (2026-09-03, 이슈 #315)**

계약 전체에 `multipart` 가 한 번도 없었고 업로드 URL 을 내주는 오퍼레이션도 없었다. `coverImage` · `portraitImage` 는 **읽기 응답에만** 있었으므로, 프론트는 자리만 두고 파일 입력을 붙이지 않았다 — 붙였다면 고른 파일이 아무 데도 가지 않으면서 **저장된 것처럼 보였을 것**이다.

**소유자 결정 (2026-09-03).** presigned URL 로 지금 연다. 커버·초상 이미지는 **사람 검수 대상에 포함**한다 (I-8). 형식은 `jpeg` · `png` · `webp`, 상한은 **5 MiB**. 자동 이미지 분류기는 붙이지 않는다 — 없다.

#### 1. 저장소 클라이언트 — S3 호환 API, 설정으로만

`software.amazon.awssdk:s3` 하나를 더했다 (BOM 으로 버전 고정). 하는 일은 **URL 서명**과 **업로드 후 확인(HEAD)·삭제** 셋뿐이고, 셋 다 SigV4 서명을 요구한다. **직접 서명하지 않는 이유**는 서명 오류가 "가끔 403" 으로 나타나고 그때 의심하는 곳이 서명이 아니라 정책이기 때문이다.

엔드포인트·리전·버킷·자격증명은 **전부 설정**(`app.image-storage.*`)이며 기본값을 두지 않는다 (§7.3). path-style 접근을 강제하므로 **S3 전용이 아니다** — S3 호환 API 를 말하는 저장소면 설정만 갈아 끼운다. 실제 엔드포인트·버킷명·자격증명은 레포에 없다 (S-11).

**인터페이스를 두지 않았다.** 구현이 하나이고, 바뀌는 것은 코드가 아니라 엔드포인트다. 테스트도 같은 자리를 쓴다(엔드포인트를 고정 응답 서버로 돌린다) — "교체 가능성"을 이유로 포트를 파면 그 포트의 구현이 영원히 하나인 채 남는다 (CLAUDE.md 추상화 제한).

**설정이 절반만 있으면 부팅이 선다.** 다섯 중 하나가 빠진 상태는 "쓰지 않는다"가 아니라 설정하다 만 것이다. **하나도 없으면 부팅은 되고 업로드 경로만 죽는다** — 로컬과 CI 는 저장소를 갖지 않으며, 없는 설정을 강요하면 그 자리에 아무 값이나 들어간다 (Anthropic 어댑터와 같은 판단).

#### 2. 발급 경로 — 키를 서버가 정한다

`POST /api/v1/authoring/drafts/{draftId}/images` 는 **원고 소유자에게만** 발급한다. 남의 원고는 없는 것과 구분되지 않는다 (I-8).

요청이 고르는 것은 **자리(`cover` | `portrait`)와 형식**뿐이다. 키는 서버가 `drafts/{draftId}/{slot}/{uuid}.{ext}` 로 만든다 — **클라이언트가 경로를 정하면 남의 자리에 덮어쓸 수 있고**, 그때 잃는 것은 남의 원고다. 키에 원고 id 가 들어 있으므로 소유 판정이 곧 경로 판정이 된다. 파일 이름도 확장자도 받지 않는다.

#### 3. 형식과 크기를 무엇이 거는가 — 서명 하나, 확인 하나

서버는 바이트를 보지 못한다. 그래서 둘을 **다른 자리**에서 건다.

| | 무엇이 거는가 | 어긋나면 |
|---|---|---|
| 형식 | **서명**. `Content-Type` 이 서명된 헤더에 들어간다 | 저장소가 업로드를 거절한다 |
| 크기 | **확정 단계의 HEAD** | 서버가 객체를 지우고 `400` |

presigned PUT 은 크기를 서명으로 묶지 못한다. 그래서 상한을 확인 없이 두면 5 MiB 는 **계약에만 적힌 숫자**가 된다. 어느 쪽도 "클라이언트가 지킬 것"으로 두지 않았다.

**바이트 자체의 형식(매직 넘버)은 아직 보지 않는다.** 확인하는 것은 저장소가 기록한 `Content-Type` 이며, 그것은 업로드 요청이 정한 값이다. 서명이 그 값을 묶으므로 *발급받은 형식과 다른 형식으로 올릴 수는* 없지만, *jpeg 라고 말하면서 다른 바이트를 올리는 것*은 이 단계가 잡지 못한다. **사람 검수가 그 뒤에 있다** — 자동 이미지 분류기는 없다.

#### 4. 업로드 완료를 서버가 어떻게 아는가 — 확정 단계를 둔다

`POST .../images/commit` 이 그 자리다. 발급만 하고 끝내면 서버는 **무엇이 올라왔는지도, 올라왔는지도** 모른다.

확정은 (1) 이 원고의 키인지 다시 보고 — 발급을 받았다는 사실이 아무 키나 확정할 수 있다는 뜻은 아니다 — (2) 저장소에 물어 형식과 크기를 확인하고 (3) 어긋나면 그 객체를 지운다. **확정되지 않은 키는 확인된 적이 없는 키**이며 원고에 적을 값이 아니다.

원고의 `payload` 에 키를 적는 것은 기존 단계 저장(`PATCH /drafts/{draftId}`)이 한다. **제출 시점에 그 키를 다시 확인하는 것은 후속이다** — B-54 의 제출 경로를 건드리게 되므로 이 작업에서 분리했다.

#### 5. 검수 전 노출을 무엇이 막는가 — **이 작업에서 가장 중요한 판단** (I-8)

**버킷은 비공개다. 영구 공개 URL 이 존재하지 않는다.**

원고에 적히는 값은 URL 이 아니라 **객체 키**다. 키를 아는 것과 이미지를 보는 것은 다르다 — 비공개 버킷의 객체는 서버가 서명해 주지 않으면 아무도 열지 못한다. 그래서 노출 여부는 *"버킷 설정이 어떤가"* 가 아니라 *"서버가 누구에게 서명해 주는가"* 로 결정되고, 그 자리는 코드 안에 있다.

**이 작업은 읽기 URL 을 하나도 발급하지 않는다.** 발급되는 URL 은 업로드용 하나뿐이고 짧게 만료된다. 즉 **승인 전 이미지가 타인에게 닿는 경로가 존재하지 않는다.** 확정 응답에도 URL 이 없다.

버킷이 공개로 설정되면 이 보장은 **코드 밖에서** 깨진다. 그래서 설정 주석과 배포 문서가 그 사실을 못박는다 — 코드가 강제할 수 없는 조건은 문서가 들고 있어야 한다.

#### 6. 검수 화면이 이미지를 본다 — **후속으로 둔다**

`GET /api/v1/admin/reviews/{storyId}`(#316-①)가 원고를 열지만 이미지를 담지 않는다. **그 파일을 건드리지 않았다** — 같은 자리를 두 PR 이 고치면 충돌한다.

열람 경로는 **소유자용과 검수자용을 함께** 여는 것이 맞다. 둘 다 "서버가 짧은 서명 URL 을 준다"는 같은 모양이고, 다른 것은 누구에게 주는가뿐이다. 그때 **검수자의 열람은 감사 기록 대상**이라는 조건이 붙으므로(#316-① 이 이미 그렇게 열었다) 그 PR 위에 얹는 편이 낫다.

그전까지 작성자는 **자기 브라우저에 있는 파일**로 미리보기를 그린다. 방금 고른 파일이므로 서버 왕복이 필요 없다.

#### 범위 밖

- **버려진 객체의 수거.** 발급만 받고 올리지 않은 키, 확정 뒤 원고에서 빠진 키는 지금 아무도 지우지 않는다. 보관 주기(R12.4)와 함께 볼 일이다
- **작품 발행 시 이미지 이관.** `story.cover_url` 계열 컬럼은 여전히 URL 문자열이다. 승인된 작품의 커버를 어떤 URL 로 내보낼지는 발행 경로의 결정이며, 그때 **공개 CDN 을 붙일지 서명 URL 을 계속 쓸지**를 정한다
- **자동 이미지 분류기.** 없다 (소유자 결정). 사람 검수가 유일한 판정이다

> **원문 확인 없이 내린 결정이다.** `docs/internal/` 이 이 작업 시점의 환경에 없어 R 조항 원문을 대조하지 못했다. 근거는 이슈 #315 와 소유자의 결정(presigned URL · 검수 대상 포함 · jpeg/png/webp · 5 MiB)이다.

### §13-66 작품에서 원고로 가는 길은 무엇인가 `[해소]` — **이슈 #340 (2026-09-04)**

**"내 작품" 목록이 막다른 길이었다.** `MyStoryItem` 은 `storyId` 까지만 실었고, 화면이 그 줄에서
할 수 있는 일이 **상태 보기 하나**였다. 마법사는 `/authoring/drafts/{draftId}` 에 서 있는데
그 `draftId` 를 알 방법이 없었고, `GET /authoring/drafts/{draftId}/review` 는 **부를 수 있는
화면이 없어** 계약에만 남아 있었다.

#### 왜 화면에서 우회하지 않는가

우회하려면 원고 목록을 함께 불러 **제목 같은 것으로 짝지어야** 한다. **제목은 식별자가 아니다** —
같은 제목의 원고가 둘이면 조용히 남의 것을 연다. 그리고 그 순간 *"작품과 원고를 잇는 규칙"* 이
서버가 아니라 화면에 생긴다. 저장 구조를 아는 쪽이 답해야 하는 질문이다.

#### 채택 — `MyStoryItem.draftId`, `[string, 'null']`

필드 하나를 더한다. 새 경로를 여는 쪽은 목록마다 왕복이 하나 더 늘고, 그 왕복이 하는 일은
**서버가 이미 아는 사실을 되묻는 것**뿐이다.

**`null` 이 실제로 존재한다.** 미리보기는 임시 작품을 발행하지만 원고와 잇지 않으므로
(§13-5) **원고 없는 작품이 있다.** 그 줄에 아무 원고나 붙이면 화면은 남의 원고를 연다 —
없다고 말하는 편이 사실이다.

#### 방향을 뒤집지 않았다

`story` 에 `draft_id` 컬럼을 만들지 않는다. 저장 구조는 **원고가 발행한 작품을 기억하는**
방향이고 (`story_draft.story_id`), 뒤집으면 catalog 가 **원고를 지워도 남는 값**을 들게 된다.

#### 어떻게 읽는가 — SPI, 그리고 쪽 단위 조회

`story_draft` 를 소유하는 것은 authoring 이고 읽어야 하는 것은 catalog 다. catalog 의 허용 의존은
`common` 하나이므로 계약을 `common/spi` 에 두고 **구현을 데이터 소유 모듈에** 둔다
(`StoryDraftLinkQuery` — `StoryReviewTimesQuery` 와 같은 자리, ADR-0002).

**줄마다 묻지 않는다** (§15). 20줄짜리 목록이 21번의 조회가 되는 것은 이 필드를 더하면서
가장 쉽게 저지르는 실수다 — 쪽 전체의 작품 id 를 한 번에 넘긴다.

#### 범위 밖

- **한 작품에 원고가 둘인 상태.** 지금 그것을 만드는 경로는 없다(제출은 원고 하나가 작품 하나를
  낳는다). 조회는 최근 원고를 돌려주도록 순서를 박아 두었을 뿐이며, **유일성을 제약으로 걸지는
  않았다** — 걸어야 할 이유가 생기면 그때가 마이그레이션 자리다

### §13-67 관리자가 세션을 찾는 길과 여는 길은 다른 층이다 `[해소]` — **이슈 #339 (2026-09-04)**

`getSessionDebug` 는 **`sessionId` 를 이미 아는 사람만** 부를 수 있었다. 세션을 **찾는** 경로가
없어 Debug 콘솔은 `/admin/sessions/:sessionId/debug` 를 **URL 로 직접 열어야** 들어갔다.

#### 왜 목록을 디버그와 같은 층에 둘 수 없는가

**디버그는 읽을 때마다 감사 한 줄을 남긴다** (R12.3, S-5). 목록을 그리려고 후보 세션들의 원문을
미리 불러 두면 **열어 본 적 없는 세션이 열람 기록에 남는다.** 감사 로그가 *"이 관리자가 이 세션을
봤다"* 를 말해야 하는데, 목록을 그린 것만으로 스무 줄이 생기면 그 로그는 더 이상 그 사실을 말하지
않는다.

#### 채택 — `GET /api/v1/admin/sessions`, 감사를 남기지 않는 메타데이터 층

주는 것은 **식별자와 메타데이터뿐**이다 — `sessionId` · `storyId` · `storyVersionId` ·
`storyTitle` · `status` · `turnNo` · `chapterNo` · `testSession` · `deletedAt` · 시각 둘.
**원문은 하나도 없다** — 게임 상태 JSON · 본문 · 선택지 · 프롬프트 · 응답 어느 것도.
그래서 이 경로는 `access_audit_log` 에 쓰지 않는다.

**관리자 행위 기록은 남는다** (`admin_audit_log`, R14.5). "목록을 열었다"는 행위이고, 열람 감사와
**다른 표 · 다른 뜻**이다. 둘을 같은 것으로 보면 어느 쪽도 쓸모가 없어진다.

**세 조건은 여기서도 AND 다** (S-4). 찾는 것이 여는 것보다 헐거우면 문이 둘이 아니라 하나 반이 된다.

**클래스를 나눴다.** `SessionListFacade` 는 `SessionDebugFacade` 와 별개다 — 둘의 차이는 무엇을
읽는지가 아니라 **읽는 행위가 무엇을 남기는지**이고, 한 클래스에 두면 언젠가 한쪽 규칙이 다른 쪽으로
샌다. 새는 방향은 늘 **감사가 사라지는 쪽**이다.

#### 함께 정한 둘

**1. 작품 이름은 목록이 싣는다.** 세션이 고정한 버전으로 찾는다 (I-4) — 세션이 보고 있는 것은 지금의
작품이 아니라 그때 고정된 버전이다. **지워진 작품의 세션은 이름이 `null`** 이다 (§13-58) — 세션은
남고 작품이 없어진 것이므로 지어내지 않는다. 조립은 admin 이 하며 `catalog :: query` 를 허용 의존에
더했다 (§5.4 의 "admin ← 전 모듈").

**2. 지난 턴에서 고른 선택지의 문구 — 계약을 넓히지 않는다.** 그 값은 **이미 응답 안에 있다.**
디버그가 돌려주는 각 턴의 `choices` 는 발급 당시의 배열 원문이고 그 안에 `choiceId` 와 `text` 가
함께 들어 있다 — 콘솔은 이전 턴의 `choices` 에서 `chosenChoiceId` 를 찾아 문구를 얻는다.
**파생 필드를 새로 만들지 않는다.** 만들면 같은 사실의 정본이 둘이 되고, 저장된 것과 다시 가공한
것이 갈라지는 날 디버그는 자기가 틀렸다는 것을 말해 주지 못한다.

#### 범위 밖

- **상태로 좁히는 필터.** 지금 좁히는 축은 작품 하나다. `:param IS NULL` 을 한 쿼리에 넣으면
  PostgreSQL 이 null 파라미터의 타입을 정하지 못해 첫 쪽이 통째로 실패하므로(§13.7 에서 이미 겪었다)
  축이 늘 때마다 조회가 갈라진다 — 실제 필요가 생기면 그때 만든다
- **비용.** 표류 12 (`cost_micro`) 그대로다. 값이 채워지는 것은 다른 작업이다

### §13-68 미리보기를 원고에 잇고, 검수가 끝날 때까지 살려 둔다 `[해소]` — **이슈 #332 (2026-09-04)**

`PreviewController` 는 §13-5 대로 임시 `draft`·`private` **작품**을 새로 발행하고 그 위에 테스트
세션을 만든다. 그런데 그것을 **어디에도 붙이지 않았다** — `SubmissionService` 는 제출 시 별개의
작품을 발행하고 원고가 기억하는 것은 그쪽 하나뿐이다. 미리보기가 만든 것은 **고아**로 남아 파기를
기다렸고, 검수자는 그 턴에 **도달할 길이 없었다** (§13-61 이 그 자리를 비워 둔 이유다).

#### 1. 어느 쪽이 정본인가 — 원고가 미리보기를 기억한다

**원고 쪽에 둔다.** 미리보기 작품은 파기 대상이고 원고는 남는다 — 사라지는 쪽이 남는 쪽을 가리키면
그 값은 언젠가 아무것도 가리키지 않는다.

**`story_id` 를 재사용하지 않는다.** 그 컬럼은 **제출된 작품** 하나를 가리키며 재제출이 같은 작품에
버전을 얹는다 (R8.8). 미리보기 작품을 같은 자리에 넣으면 제출이 그것을 덮어쓰거나, 더 나쁘게는
**재제출이 미리보기 작품에 버전을 얹는다.** `preview_story_id` · `preview_session_id` ·
`previewed_at` 을 따로 둔다.

#### 2. 여러 번 돌리면 무엇이 남는가 — 마지막 것

원고는 **마지막 미리보기**를 기억한다. 이전 것은 연결이 끊겨 보관 기간 뒤에 파기된다.
검수자가 보는 것은 **작성자가 마지막으로 확인한 것**이며, 그것이 작성자가 "이 정도면 됐다" 고
판단한 상태다.

**`previewedAt` 을 함께 준다.** 오래된 미리보기는 **지금 원고와 다른 문장**을 보여 줄 수 있다 —
작성자가 미리보기 뒤에 원고를 고치고 제출했다면 그렇다. 그 사실을 숨기면 검수자는 자기가 보고 있는
것이 무엇인지 모른 채 판정한다. 회차를 고정하지 않은 대신 **시각을 말한다.**

#### 3. 파기 정책 — 유예하되 영구가 아니다

30일(§13-37)은 *"원고가 남아 있으니 다시 부르면 된다"* 를 근거로 정해졌다. **그 근거는 검수자가
그 턴을 보는 동안 성립하지 않는다** — 파기되고 나면 검수 상세는 조용히 빈 자리를 그리고, 그 침묵은
*이 작품은 아무 문장도 내놓지 않았다* 로 읽힌다.

**유예 조건은 둘이 함께다.** 원고가 그 미리보기를 가리키고 있고, 그 원고가 낸 작품이 **판정을
기다리고** 있어야 한다(`pending` · `in_review`). 하나만 보면 검수와 무관한 미리보기가 영원히
남거나, 검수 중인데 지워진다.

**판정이 나면 다시 파기 대상이다.** 검수자가 볼 일이 끝났고 작성자는 언제든 다시 부를 수 있다 —
30일을 정한 근거가 그대로 돌아온다.

#### 4. 검수자가 무엇을 보는가

`GET /api/v1/admin/reviews/{storyId}` 가 `previewTurns` 를 싣는다. **가공하지 않는다** — 본문과
선택지는 저장된 JSON 원문 그대로다. 검수는 *독자가 볼 것*을 보는 자리이고, 다시 만들면 그것이
실제로 나간 문장인지 알 수 없게 된다 (§14 Debug 와 같은 판단).

**빈 배열이 실패가 아니다.** 미리보기를 돌리지 않았거나 보관 기간을 넘겼다 — 어느 쪽이든 없다는
것이 사실이며, 여기서 404 를 내면 **검수 상세 전체가 열리지 않는다.**

#### 경계

- 턴은 `play` 스토어의 것이고 `authoring` 은 `play` 를 알지 못한다 — `common/spi` 의
  `PreviewTurnsQuery` 로 읽는다 (`TestSessionStarter` 와 같은 경계, 반대 방향).
- 파기 유예 판정에 필요한 것은 `story_draft` 이고 소유는 `authoring` 이다 — `batch` 는 파사드가
  아니라 `common/spi` 를 쓴다 (ADR-0003). `PreviewRetentionHold` 가 그 자리다.

#### 범위 밖

- **제출 시점의 미리보기 고정.** 지금은 마지막 것이고 시각으로 그 사실을 말한다. 회차를 박으려면
  미리보기 이력을 쌓아야 하며, 그때 저장·파기 규칙이 한 벌 더 생긴다
- **파기 후보를 고른 뒤 유예를 묻기까지의 틈.** 그 사이에 제출이 일어나면 이번 회차에서 그 미리보기가
  지워진다. 30일을 넘긴 미리보기를 같은 순간에 제출하는 경우이며, 결과는 검수 상세의 빈 배열이다
  (계약이 이미 허용하는 상태) — 다음 회차가 아니라 **그 회차에서만** 다르다

### §13-69 고른 조건은 어디로 저장되고, 무엇이 그것을 참이 되게 하는가 `[해소]` — **이슈 #326 (2026-09-04)**

#282 이 **목록을 주는 경로**(`GET /authoring/metadata`)를 열었지만 거기서 고른 것을 **저장하는
경로가 없었다.** `OutlineChapter.conditionTemplateKey` · `OutlineEnding.conditionTemplateKey` 는
항상 `null` 이었고, 발행되는 엔딩은 전부 **도달 불가 조건**을 달고 나갔다.

#### 1. 어디로 저장하는가 — 기존 단계 저장의 `payload`

`PATCH /api/v1/authoring/drafts/{draftId}` 가 받는다. `chapters[]` · `endings[]` 각 항목이
`condition: {templateKey, params}` 를 싣는다.

**새 경로를 열지 않았다.** 원고를 쓰는 문이 둘이 되면 순서 규칙이 생기고("조건은 아웃라인 저장
뒤에"), 그 규칙은 어디에도 적히지 않은 채 화면과 서버 양쪽에 반씩 남는다. B-51 이 payload 를
통째로 저장하기로 한 판단과 같은 자리다.

#### 2. 왜 조건식 JSON 을 받지 않는가

**클라이언트가 만든 구조를 그대로 평가기에 먹이면 그것이 곧 DSL 입력면이 된다.** I-1 이
`choiceId` 에 대해 세운 것과 같은 이유이고, R7.16 이 정한 것은 **템플릿 선택만**이다. 오는 것은
*고른 것*이고, 조립은 서버가 한 자리에서 한다 (`ConditionAssembler`).

**조건 평가기를 고치지 않았다.** 이미 있는 문법에 값을 끼워 넣을 뿐이다.

#### 3. 무엇을 검증하는가 — 그리고 **왜 그것만으로는 부족했는가**

이름은 **그 원고가 선언한 것**이어야 한다 — `payload` 의 `characters[].name` 과 `flags[]`.
없는 이름을 가리키는 조건은 평가기에서 조용히 거짓이 되고, 그 챕터·엔딩은 **영원히 도달되지
않는다.**

**여기서 하나가 더 드러났다.** 검증만으로는 부족하다 — UGC 작품은 지금까지 `state_schema` 를
상수 `{"flags":[]}` 로 발행했고, **그 스키마에서는 어떤 호감도도 어떤 플래그도 병합 대상이
아니다** (R4.1). 즉 검증을 통과한 조건도 런타임에는 **무엇이든 거짓**이었다. 조건을 저장하는
일과 스키마를 선언하는 일은 **따로 할 수 없다.**

그래서 `state_schema` 를 **같은 목록에서** 만든다 (`DraftStateSchema`). 검증이 보는 이름과
화이트리스트에 선언되는 이름이 갈라지면, 갈라진 그 순간부터 검증은 아무것도 지키지 않는다.

**호감도의 눈금은 작성자가 정하지 않는다** (기본 채택안). `min 0 / max 100 / maxDeltaPerTurn 5`
— 공식 작품 시드가 쓰는 것과 같은 값이다. 작품마다 다른 눈금을 허용하면 같은 "호감도 50" 이
작품마다 다른 뜻이 되고, 델타 상한은 AI 가 상태를 한 번에 흔들지 못하게 하는 장치이므로
작성자가 낮추거나 높일 값이 아니다. **원문 대조는 하지 못했다** — `docs/internal/` 이 이 환경에
없다.

#### 4. 언제 거절하는가 — 저장 시점

발행까지 미루지 않는다. 제출한 뒤에야 알려 주면 작성자는 **왜 그 엔딩이 안 나오는지**를 끝내
알지 못한다. 다만 저장 시점에 보는 것은 **조건뿐**이다 — 아직 채우지 않은 단계가 있는 것은
정상이고(5단계 저장, R8.3), 제목이 없다고 저장을 막으면 작성 중인 원고를 저장할 수 없다.

**모르는 템플릿 키를 조용히 무시하지 않는다.** 무시하면 작성자가 고른 조건이 사라진 채 발행되고,
결과는 "저장은 됐는데 그 엔딩이 안 나온다" 다.

#### 5. §13-16 기본 엔딩

**바뀌지 않았다.** 서버가 조건 없는 기본 엔딩을 하나 더한다 — 작성자가 쓴 엔딩을 폴백으로
바꾸면 그 엔딩이 아무 조건에서나 나온다. 조건을 고르지 않은 일반 엔딩은 여전히 **도달 불가**
조건을 받는다 (V4 의 CHECK 상 일반 엔딩은 조건을 반드시 갖는다).

#### 범위 밖 — **이슈 후보**

- **UGC 작품의 등장인물이 발행되지 않는다.** 원고 `payload` 의 `characters[]` 는
  `DraftStoryDefinition` 이 읽지 않으며 `character` 테이블에 아무것도 들어가지 않는다. 이 작업이
  `state_schema` 의 `affinity.<이름>` 은 세우지만, **인물 카드·페르소나 프롬프트는 여전히 비어
  있다** — 검수 상세의 `characters` 가 UGC 작품에서 늘 빈 배열인 것도 같은 원인이다
- **플래그를 작성자가 어디서 선언하는가.** 계약은 `payload.flags[]` 를 읽지만 마법사에 그것을
  입력하는 단계가 있는지는 프론트의 것이다. 없으면 `has_flag` · `lacks_flag` 는 고를 수 있는
  값이 없다

### §13-70 원고 payload 의 필드 이름은 계약이 정한다 `[해소]` — **이슈 #354 (2026-09-04)**

#350(인물 발행)을 착수하며 확인한 것이다. **인물보다 앞이 막혀 있었다.**

#### 무엇이 있었나

계약이 원고 `payload` 를 `additionalProperties: true` 로만 열어 두어 **필드 이름을 아무도 정해
주지 않았다.** 그래서 화면과 발행이 각자 정했고 갈라졌다 — 발행은 `worldPrompt` 를 **필수로**
읽는데 마법사는 그 이름을 쓴 적이 없다. **실제 마법사로는 UGC 제출이 한 번도 성공하지 못했다.**

**통합 테스트는 전부 초록이었다.** 픽스처가 발행이 읽는 이름으로 쓰여 있었기 때문이다 —
테스트가 계약이 아니라 **자기 자신을 확인**하고 있었다. 이것이 이 항목에서 가장 중요한 교훈이며,
같은 모양은 *"양쪽이 같은 값을 각자 이름 짓는 자리"* 어디서나 다시 생긴다.

#### 왜 이렇게 됐나

`payload` 를 통째로 저장하기로 한 것(B-51)은 단계가 늘 때마다 컬럼이 느는 것을 막기 위해서였고,
그 대가는 *"언젠가 누군가는 그것을 읽어야 한다"* 였다. 읽는 자리는 하나로 두었지만 **무엇을
읽을지는 계약이 말하지 않았다.** 열어 둔 것과 정하지 않은 것은 다르다.

#### 채택 — 계약에 `DraftPayload` 를 세우고, 발행이 발행물의 이름을 읽는다

**이름은 발행물 계약이 이미 쓰는 것을 그대로 쓴다.** `shortDescription` 은 `StoryDetail` 의
것이고 `oneLine` · `portraitImage` 는 `CharacterCard` 의 것이다. 원고와 발행물이 같은 말을 쓰면
게시 시점에 옮겨 적을 것이 없고, **옮김이 없으면 빠뜨릴 것도 없다.**

반대로 화면을 고치면 **이미 저장된 원고가 전부 무효**가 되고 두 레포를 함께 고쳐야 한다.

**`settingDetail` 만 이름이 다르다.** 화면의 라벨이 *설정 상세*이고 발행물은 `worldPrompt` 라고
부른다 — 독자에게 보이는 값이 아니라 발행물 쪽에 짝이 없기 때문이며, 옮기는 자리는 한 곳뿐이다.

**`additionalProperties` 는 열어 둔다.** `PATCH` 가 payload 를 통째로 받으므로 아직 붙지 않은
단계의 값을 화면이 그대로 실어 보낼 수 있어야 한다 — 아는 키만 남기면 **다음 단계가 붙일 값을
이전 단계 화면이 매번 지운다.**

**필수 필드를 두지 않는다.** 원고는 첫 글자를 치기 전에 이미 만들어져 있고 그 상태가 예외가
아니라 기본값이다. 무엇이 있어야 발행되는지는 제출이 판정한다.

#### 조건은 형제 필드다 — §13-69 정정

§13-69 는 조건을 `condition: {templateKey, params}` 로 정했다. **그것을 물린다.**

초안 응답(`OutlineChapter` · `OutlineEnding`)이 `conditionTemplateKey` 를 **그 높이에** 돌려주므로,
저장이 한 겹 접으면 화면은 **받은 모양과 보내는 모양이 다른** 상태를 매번 변환해야 하고 그
변환이 어느 날 하나를 빠뜨린다. `conditionParams` 를 형제로 둔다 — 화면이 이미 그렇게 쓰고 있다.

**`null` 을 오류로 읽지 않는다.** 화면은 조건을 지울 때 키를 지우는 대신 `null` 을 보낸다 —
그것을 거절하면 **고른 조건을 되돌릴 수 없다.**

#### 뒤따르는 것

- **#350 — 인물 발행.** `characters[]` 를 발행이 읽고 `character` 표에 넣는다. `persona` 자리를
  원고에 열되 **비어 있으면 `oneLine` 이 대신 간다** — 서버가 문장을 지어내지는 않는다
- **장르 · 커버 발행.** `genres[]` · `coverImage` 도 아직 읽히지 않는다
