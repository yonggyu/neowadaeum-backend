# ADR-0003: batch 모듈의 의존 범위

## 상태

승인 (2026-08-23) — 이슈 #10

## 맥락

`CLAUDE.md` §5.2 는 batch 의 범위를 정한다.

```
batch/   ending_stat 집계, 세션 만료, UGC 재스캔, 로그 파기
```

그런데 **§5.4 의 의존 규칙 목록에 `batch` 행이 없다.** (`config` 도 마찬가지다.) batch 가 무엇을 참조할 수
있는지가 상위 문서 어디에도 적혀 있지 않다.

실행 주체(batch)와 데이터 소유자가 전부 어긋난다. 집계는 catalog + play, 재스캔 판정은 safety,
프롬프트 로그 파기는 ai, 탈퇴 삭제·익명화는 identity, 감사 로그 파기(S-10)는 admin 소관이다.

**그리고 코드가 문서보다 먼저 결정을 내렸다.** B-02(PR #4)가 batch 를 `common` 하나만 참조하는
스케줄 실행기로 좁혔고, 근거는 `package-info.java` 주석에만 있다. ADR(§9.5)이 없다.
이 상태는 "문서에는 규칙이 없고 코드에는 규칙이 있는" 것이며, §0.2 가 금지하는 "상위 문서의 결정을
코드에서 조용히 뒤집는" 것과 형태가 다를 뿐 결과는 같다.

## 결정

**현행을 유지하고 문서에 소급 기록한다 — `batch ← common`, 실행은 SPI 주입.**

실행 인터페이스를 `common/spi` 에 두고 **데이터를 소유한 모듈이 구현한다.** batch 는 스케줄링
(`@Scheduled` + ShedLock)과 실행만 한다.

### 왜 이 안인가

**1. 순환을 예외 없이 막는 유일한 안이다.**

B(safety·ai 추가)는 필요한 목록이 safety·ai 로 끝나지 않는다. B-39 는 catalog + play, B-61 은
identity + play + ai, S-10 은 admin 이 필요하다.

`admin` 은 §5.4 상 도메인 전 모듈을 참조한다. 여기에 `batch → admin` 이 더해지면 양방향이 되어 순환이고,
`ApplicationModules.verify()` 가 빌드에서 잡는다. **B-02 가 `admin → batch` 를 미리 끊어 그 가능성을
없앴다** — 이 ADR 은 그 조치를 소급 승인하는 것이기도 하다. §5.4 의 `admin` 행도 "전 모듈"이 아니라
"도메인 전 모듈, batch 제외"로 정정했다(문서가 코드와 달랐고, 그것이 이 이슈가 제기된 이유와 같은 종류다).

C(admin 만 제외)는 순환을 피하지만 파기 배치 하나만
다른 곳에 사는 비대칭이 생긴다 — **"batch 는 무엇인가"에 예외가 붙으면 다음 사람은 그 예외를 근거로
또 다른 예외를 만든다.** 그리고 7개 모듈 참조는 사실상 경계 없음이다.

**2. §5.3 의 연장선이다.**

"각 스토어는 자기 데이터만 만진다 / 스키마 간 JOIN 금지"는 B-05 에서 코드와 테스트로 고정됐다.
batch 가 6~7개 모듈의 데이터를 직접 다루는 것은 그 규칙을 **실행 계층에서 우회하는 모양**이 된다.

**3. 되돌리기 비용이 비대칭이다.**

A → B 는 싸고(`allowedDependencies` 를 넓히고 구현을 옮긴다), B → A 는 비싸다(batch 에 모인 로직을
다시 각 모듈로 흩어야 한다). **확신이 없을 때는 싼 쪽을 먼저 고른다.**

### 함께 확정한 것

이슈 #10 이 "이걸 빼면 B-39 착수 시 같은 논의를 반복한다"고 지적한 네 가지다.

**1. SPI 의 형태와 위치 — `common/spi`, 배치별 개별 인터페이스**

공통 `BatchTask` 하나에 식별자를 붙이는 방식은 쓰지 않는다. 배치마다 입력·출력·실패 의미가 다르고,
하나로 묶으면 그 차이가 식별자 문자열로 숨는다. §5.2 트리에 `common/spi` 를 추가한다.
ADR-0002(블록리스트)의 조회 SPI 도 같은 자리에 둔다 — 패턴이 하나여야 근거를 재구성할 수 있다.

**2. ShedLock 잠금 이름 — batch 소유**

SPI 계약에 넣지 않는다. 잠금 이름은 **"언제 어떻게 실행하는가"의 일부**이고 그건 batch 의 책임이다.
구현 모듈이 잠금 이름을 알면 실행 정책이 두 곳으로 갈라진다.

**3. 실행 결과·실패 보고 — 구현 모듈이 적재, batch 는 실행과 로깅만**

B-59 는 "배치 실행 결과가 검수 큐에 적재"를 완료 조건으로 요구한다. **적재 주체는 구현 모듈(authoring)이다.**
검수 큐는 authoring 의 데이터이고, batch 가 적재하면 batch → authoring 의존이 생겨 1번 결정이 무너진다.
batch 는 실행 성공/실패와 소요를 구조화 로그로 남긴다 (§9.4).

**4. §5.4 에 `batch` 와 `config` 행을 추가한다**

지금 두 모듈은 규칙 목록에 없다. `config` 는 배선 지점이라 전 모듈을 참조한다 — 이미 코드가 그렇고,
문서에 없던 것을 채운다.

## 결과 (되돌리기 비용 포함)

| | |
|---|---|
| 코드 변경 | **없음.** B-02 의 현행 경계가 그대로다 |
| 되돌리기 비용 | **낮음** — `allowedDependencies` 를 넓히고 구현을 batch 로 옮기면 된다 |

### 남는 부담

- SPI 인터페이스가 `common/spi` 에 쌓인다(집계·만료·재스캔·파기로 최소 4종).
- 스케줄 설정과 실제 구현이 다른 모듈에 있어 **"이 배치가 무엇을 하는가"를 읽으려면 한 단계를 더 건너야 한다.**
  이 비용을 받아들인다. 대가로 얻는 것은 batch 가 8개 모듈을 알게 되는 상황을 원천 차단하는 것이다.

### ADR-0002 와의 관계

같은 패턴이다 — SPI 는 `common/spi`, 구현은 데이터 소유 모듈, 호출자는 주입받는다.
R9.4(블록리스트 갱신 시 승인 UGC 재스캔) 배치가 두 결정이 만나는 지점이며, 두 안이 같은 방향이라
충돌하지 않는다.
