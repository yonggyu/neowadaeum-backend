# ADR-0008: 리프레시 토큰은 재발급 경로 전용 쿠키로 오간다

## 상태

승인 (2026-09-03) — 이슈 #278 (B-12 의 전제 변경)

**B-12 를 뒤집는 결정이 아니다.** B-12 가 세운 네 전제 중 **하나만** 바꾼다.

## 맥락

### B-12 가 세운 것

`ApiSecurityConfiguration` 은 서로 맞물린 네 문장 위에 서 있다.

| # | 전제 | 그래서 |
|---|---|---|
| 1 | 세션을 만들지 않는다 (`STATELESS`) | 서버가 기억하는 것이 없다 |
| 2 | 자격 증명은 `Authorization` 헤더로만 온다 | 브라우저가 **자동으로** 실어 보내는 것이 없다 |
| 3 | 그래서 위조할 요청이 성립하지 않는다 | `/api/v1/**` 에서 **CSRF 를 면제한다** |
| 4 | 그래서 CORS 에 자격 증명을 켜지 않는다 | 와일드카드의 유혹도 성립하지 않는다 |

**3 과 4 는 2 의 결과다.** 그 클래스의 주석이 이미 이렇게 경고해 두었다.

> 쿠키로 인증하는 경로를 만든다면 `/api/v1/**` 밖에 두거나 이 면제를 좁혀야 한다 — 그러지 않으면 그 경로가 조용히 무방비가 된다.

### 그런데 로그인 유지가 성립하지 않는다

`GET /api/v1/me`(#262)가 *"지금 로그인돼 있는가"* 를 물을 자리를 만들었다. 그러나 **물어볼 토큰 자체가 새로고침에서 사라진다.**

- 토큰을 메모리에만 두면 → 탭을 새로 고치는 순간 없다
- `localStorage` 에 두면 → **XSS 하나로 리프레시 토큰이 30일치 그대로 나간다.** 프론트가 그것을 하지 않기로 한 것이 F-3 이다

즉 지금 계약에는 **"XSS 로 나가지 않으면서 새로고침을 견디는 자리"가 하나도 없다.** 이것은 프론트의 구현 문제가 아니라 **계약이 그 자리를 만들지 않은 것**이다.

## 결정

**리프레시 토큰은 `POST /api/v1/auth/refresh` 하나에만 붙는 `HttpOnly` 쿠키로 오간다.**

| | 전 | 후 |
|---|---|---|
| 액세스 토큰 | `Authorization: Bearer` | **그대로다** |
| 리프레시 토큰(발급) | `TokenResponse.refreshToken` 본문 | `Set-Cookie` (`HttpOnly`) |
| 리프레시 토큰(제출) | `RefreshRequest.refreshToken` 본문 | 쿠키 (`Path` 가 재발급 경로 하나) |
| `/api/v1/**` CSRF | 전부 면제 | **재발급 경로만 면제에서 뺀다** |
| CORS 자격 증명 | 끔 | **켠다** (허용 오리진은 여전히 정확 일치·와일드카드 불가) |

**바뀌는 것은 위 넷뿐이다.** 보호 API 는 여전히 헤더로 인증하고, 세션은 여전히 없다.

### 왜 (a) 인가

| | **(a) 채택** 재발급 경로 전용 쿠키 | (b) 헤더 유지 | (c) 재발급 전용 저장소 |
|---|---|---|---|
| XSS 로 리프레시 토큰이 나가는가 | **안 나간다** — `HttpOnly` 는 JS 가 읽지 못한다 | 나간다 (`localStorage`) 또는 새로고침마다 재로그인 | 저장소에 따라 다르다 |
| 새로고침 후 로그인 유지 | **된다** | **안 된다** | 된다 |
| 새로 감당하는 것 | **CSRF** (아래) | 없음 | 저장소 하나와 그 유출 위험 |
| 프론트가 고칠 것 | `credentials: 'include'` 와 CSRF 헤더 | 없음 | 저장소 접근 코드 전부 |

**(b) 를 기각한 이유**는 그것이 결정을 미루는 것이 아니라 **"로그인 유지를 하지 않는다"를 정하는 것**이기 때문이다. 액세스 토큰이 30분이므로 사용자는 30분마다, 그리고 새로고침마다 구글 로그인을 다시 지난다. 15세 이용가 서비스에서 그것은 이탈이다.

**(c) 를 기각한 이유**는 그것이 (a) 의 문제를 옮기기만 하기 때문이다. "JS 가 읽을 수 있는 저장소"인 한 XSS 앞에서 `localStorage` 와 같고, "JS 가 읽을 수 없는 저장소"는 **브라우저에서는 `HttpOnly` 쿠키 하나뿐**이다. 즉 (c) 는 (a) 를 우회해서 (a) 에 도착하거나, 아니면 (b) 가 된다.

**(a) 는 선호가 아니라 유일한 조합이다** — *"XSS 로 나가지 않는다"* 와 *"새로고침을 견딘다"* 를 동시에 만족하는 브라우저 기능이 `HttpOnly` 쿠키 말고 없다.

## 무엇을 새로 감당하는가 — CSRF

쿠키는 **브라우저가 알아서 붙인다.** 그것이 새로고침을 견디는 이유이자 CSRF 가 성립하는 이유이며, 둘은 같은 성질의 앞뒤다.

이 경로에서 CSRF 가 성공하면 공격자가 얻는 것은 **응답을 읽는 것이 아니다** — CORS 가 읽기를 막으므로 새 액세스 토큰은 공격자에게 가지 않는다. 얻는 것은 **피해자의 토큰을 임의로 회전시키고 IP 한도를 소모시키는 것**이다. 훔치는 공격이 아니라 **밀어붙이는 공격**이며, 그래도 막는다.

### 1. `SameSite=Strict` — **코드가 고정한다. 설정으로 받지 않는다**

셋 중 하나를 고르는 일처럼 보이지만 실제로는 둘이고, 그중 하나는 **고를 수 없다.**

| 값 | 이 경로에서 |
|---|---|
| `Lax` | **`Strict` 와 구별되지 않는다.** `Lax` 가 여는 것은 *교차 사이트의 최상위 GET 내비게이션* 하나인데, 이 경로는 `fetch` 의 `POST` 다. 골라도 얻는 것이 없다 |
| `None` | 교차 **사이트** 프론트에만 필요하다. 그런데 그 배치에서는 **CSRF 토큰을 프론트에 전달할 방법이 사라진다**(아래) — 즉 지원할 수 없는 값이지 덜 선호하는 값이 아니다 |
| **`Strict`** ✅ | 교차 사이트 요청에 쿠키가 **아예 붙지 않는다.** CSRF 의 대부분이 성립 자체를 못 한다 |

**"다른 오리진"과 "다른 사이트"는 다르다.** `SameSite` 는 오리진이 아니라 **사이트**(스킴 + 등록 가능 도메인)를 본다. 포트는 보지 않는다. `#248` 이 예시로 둔 `http://localhost:5173` 은 API 와 **다른 오리진이지만 같은 사이트**이고, 그래서 `Strict` 로 정상 동작한다.

**그래서 이 값은 설정 항목이 아니라 배치 제약이다.** *"프론트와 API 를 같은 사이트에 둔다"* 가 (a) 의 전제이며, 값을 설정으로 열어 두면 **전제를 어긴 배치가 부팅에 성공한 뒤 남의 브라우저에서 실패한다** — `CorsProperties` 가 기본값을 거부하는 것과 같은 이유다.

### 2. CSRF 토큰 — 그 경로에서만 요구한다

`Strict` 는 **다른 사이트**를 막지만 **같은 사이트의 다른 오리진**은 막지 않는다. 그래서 면제를 좁히고 그 경로에 표준 CSRF 필터를 켠다.

- 토큰 저장소는 **쿠키**다 (double-submit). 세션이 없으므로(전제 1) 서버가 기억할 자리가 없다
- CSRF 쿠키는 **`HttpOnly` 가 아니다.** 프론트가 읽어 `X-XSRF-TOKEN` 헤더로 돌려보내야 하며, 그것이 이 방식의 전부다
- 토큰을 **BREACH 마스킹하지 않는다.** 마스킹이 막는 것은 *압축된 응답 본문에 실린 토큰*이고, 이 서버는 HTML 을 그리지 않는다 — 토큰은 본문에 실리지 않는다

**프론트가 CSRF 쿠키를 읽을 수 있어야 한다**는 조건이 위의 배치 제약을 한 번 더 좁힌다. 쿠키는 포트를 무시하므로 `localhost:5173` ↔ `localhost:8080` 에서는 읽힌다. 운영에서는 **같은 오리진(리버스 프록시로 `/api` 를 얹는 배치)** 이 이 조건을 자동으로 만족한다. 서브도메인으로 가르는 배치는 CSRF 쿠키에 `Domain` 이 필요해지므로 **그때 이 ADR 을 다시 본다.**

### 3. 나머지 `/api/v1/**` 은 면제 그대로다

좁힌다는 것은 **한 경로를 빼는 것**이지 전부를 켜는 것이 아니다. 나머지 경로에는 여전히 브라우저가 자동으로 붙이는 자격 증명이 없고(리프레시 쿠키는 `Path` 가 재발급 경로 하나다), 거기서 CSRF 를 켜면 **토큰 없는 요청이 401 이 아니라 403 이 된다** — 계약(§13.1)이 약속한 `UNAUTHENTICATED` 가 나가지 않는다. 이 경계가 지켜지는지는 테스트가 못박는다.

## 함께 정한 것

### `Path` 는 재발급 경로 하나다 — 이 결정의 핵심

`Path=/api/v1/auth/refresh` 다. **브라우저가 다른 어떤 경로에도 이 쿠키를 붙이지 않는다.**

이것이 없으면 리프레시 토큰이 **모든 API 요청에 자동으로 실린다.** 그러면 로그 · 프록시 · 오류 리포트가 30일짜리 자격 증명을 계속 지나가게 되고, CSRF 를 감당해야 하는 경로가 **한 개에서 전부로** 늘어난다. `Path` 를 좁히는 것은 최적화가 아니라 **CSRF 를 한 경로에 가두는 장치**다.

> `__Host-` 접두어는 쓰지 않는다. 그 접두어는 `Path=/` 를 **요구하므로** 위와 정면으로 충돌한다. 접두어가 주는 보장(도메인 고정)보다 경로 축소가 이 설계에서 크다.

### `Secure` 는 설정으로 받는다 — 기본값 없이

`auth.refresh-cookie.secure` 다. **기본값을 두지 않는다** (§7.3 — `${VAR:값}` 금지). 값이 없으면 부팅이 실패한다.

로컬 개발은 HTTP 이므로 `false` 여야 하고, 배포된 모든 환경은 `true` 여야 한다. **프로파일로 갈라 자동으로 정하지 않는다** — `dev` 프로파일이 보안 속성을 스스로 낮추는 구조가 정확히 #34 가 지운 것이다. 어느 값인지는 배포가 **명시해서 밝힌다.**

`SameSite` 를 코드가 고정하고 `Secure` 를 설정으로 받는 것이 엇갈려 보이지만 성질이 다르다 — `SameSite` 는 **틀린 값이 존재하지 않는** 자리이고(다른 값은 지원 불가), `Secure` 는 **환경이 HTTPS 인가**라는 배포 사실이다.

### 로그인 응답에서 `refreshToken` 을 뺀다

`TokenResponse` 는 이제 `accessToken` · `tokenType` · `expiresIn` 셋이다. 리프레시 토큰은 **본문에 없다.**

계약이 바뀐다는 것을 알고 하는 것이다. **남겨 두면 이 결정이 아무것도 하지 않는다** — 본문으로 한 번 나간 값은 JS 가 읽었다는 뜻이고, 그 값이 `localStorage` 로 가는 것을 서버는 막을 방법이 없다. `HttpOnly` 는 *"JS 가 읽을 수 없다"* 는 보장이며, 같은 값을 본문으로도 주면 그 보장이 문장으로만 남는다.

같은 이유로 `RefreshRequest` 를 없앤다. **재발급 요청에는 본문이 없다.** 자격 증명이 쿠키 하나이므로 본문이 받을 것이 없고, 남겨 두면 *"본문으로도 보낼 수 있다"* 는 우회로가 계약에 남는다.

### 로그아웃은 이 작업의 범위 밖이다

**로그아웃 경로가 계약에 없다** (§13.1 에는 로그인 둘과 재발급 하나뿐이다). 만들지 않는다 — 범위를 넓히지 않는다.

탈퇴(`DELETE /api/v1/me`)에서도 **쿠키를 지우지 않는다.** 지울 필요가 없기 때문이다: 재발급은 `requireActive(playerRef)` 로 회원 상태를 먼저 보므로, 탈퇴한 회원의 쿠키는 남아 있어도 `403` 이다. **쿠키가 남는 것과 자격이 남는 것은 다르다.**

다만 *"브라우저에서 흔적을 지운다"* 는 별개의 요구이며, 그것이 필요해지는 시점이 로그아웃 경로를 만드는 시점이다. **후속 이슈 후보로 남긴다.**

## 결과 (되돌리기 비용 포함)

| | |
|---|---|
| 계약 수정 | `TokenResponse` 에서 필드 하나 삭제 · `RefreshRequest` 삭제 · `Set-Cookie` 선언 |
| 프론트 수정 | **필요하다.** 두 경로에 `credentials: 'include'`, 재발급에 `X-XSRF-TOKEN` 헤더 |
| 마이그레이션 | 없음 — 저장소가 늘지 않는다 |
| 배포 설정 | `auth.refresh-cookie.secure` 한 줄이 늘고, **없으면 부팅이 실패한다** |
| **종합** | **중간** — 코드는 작지만 **프론트와 함께 배포해야 한다** |

### 되돌리는 방법

(b) 로 돌아가려면 `TokenResponse` 에 `refreshToken` 을 되살리고 `RefreshRequest` 를 복원한 뒤 CSRF 면제를 `/api/v1/**` 전체로 되돌린다. **쿠키를 굽는 코드를 남긴 채 본문을 되살리지 않는다** — 둘 다 있는 상태가 가장 나쁘다(위의 "빼는 이유"가 그대로 적용된다).

### 남는 부담

- **브라우저가 아닌 클라이언트를 지원하지 않는다.** 네이티브 앱은 쿠키 저장소가 다르고 `SameSite` 가 뜻을 갖지 않는다. 앱이 생기면 재발급용 헤더 경로를 **다시 열어야 하고**, 그때 그 경로는 CSRF 를 감당하지 않는 대신 **토큰을 어디에 둘 것인가**를 다시 답해야 한다
- **리프레시 토큰 회전이 없다.** 재발급이 새 리프레시 토큰을 굽지만 **옛 것을 무효화하지 않는다** — 저장소가 없기 때문이다(§13). 쿠키로 옮긴다고 달라지지 않으며, 이것은 이 ADR 이 만든 부담이 아니라 **옮겨 온 부담**이다
- **CORS 에 자격 증명이 켜진다.** 허용 오리진 목록이 이제 *"읽을 수 있는 곳"* 이 아니라 *"자격 증명을 붙여 부를 수 있는 곳"* 이 된다. `CorsProperties` 가 와일드카드를 거부하는 것이 **선택에서 필수로** 바뀌는 지점이다

## 후속

- [ ] 프론트가 `credentials: 'include'` 와 `X-XSRF-TOKEN` 을 붙인다 (프론트 레포)
- [ ] 서브도메인 배치를 하게 되면 CSRF 쿠키의 `Domain` 을 다시 본다 — 이 ADR 의 배치 제약이 그때 깨진다
- [ ] 로그아웃 경로가 생기면 그 자리에서 쿠키를 지운다 (후속 이슈 후보)
- [ ] 리프레시 회전·폐기 저장소는 여전히 열린 문제다 (§13)
