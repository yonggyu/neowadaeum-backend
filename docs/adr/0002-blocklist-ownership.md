# ADR-0002: 블록리스트의 소유 모듈과 접근 경로

## 상태

승인 (2026-08-23) — 이슈 #9

## 맥락

`CLAUDE.md` §5.2 가 **블록리스트를 두 모듈에 동시에 기재**하고 있었다.

```
authoring/   UGC 드래프트·검수·신고·블록리스트
safety/      L0~L3 판정기, 블록리스트, 카테고리 정책
```

소유 모듈이 정해지지 않은 채로는 §5.4 가 성립하지 않는다. `safety ← (도메인 모듈 참조 X)` 이므로
`blocklist_entry` 가 authoring 소유라면 **safety 는 그 테이블을 읽을 수 없고**, R9.2(정규화 후 블록리스트
대조)와 B-30 의 L2 판정에서 항목을 쓸 수 없다. 반대로 safety 소유로 두면 §5.3 의 스토어 배정이 걸린다 —
스키마는 4개(identity / catalog / play / promptlog)뿐이고 safety 몫이 없다.

B-10 이 `blocklist_entry` 마이그레이션을 만드는 작업이므로, 테이블이 생긴 뒤에 소유가 바뀌면
스키마 이동 마이그레이션 + DataSource 재배정 + 데이터 이관이 함께 따라온다.

> **근거 확보 상태.** 이 레포에는 `docs/backend-requirements.md` 가 없다(§15 는 위치를 가리키지만 파일은
> 비공개 문서 쪽에 있다). 아래 R 조항은 `CLAUDE.md` 가 인용·요약한 범위만 근거로 삼았다.
> **이슈 대상에 있던 `R2.4` 는 `CLAUDE.md` 어디에도 인용이 없어 근거로 쓰지 않았다.**
> 원문에 소유 모듈을 직접 규정하는 문장이 있다면 이 ADR 을 재검토한다.

## 결정

**`blocklist_entry` 는 `authoring` 이 소유한다. `safety` 는 `common` 의 조회 SPI 로 읽기만 한다.**

- 테이블 위치: **catalog 스키마** (§5.3 의 "Catalog + Authoring"). B-10 정의 그대로이며 이동이 없다.
- 쓰기(운영 중 갱신, R9.4): authoring 이 소유한다. B-49 의 `POST /admin/blocklist` 가 그 경로다.
- 읽기: `common` 에 조회 SPI 를 두고 authoring 이 구현, safety 가 주입받는다.
- **§5.4 는 한 줄도 고치지 않는다.** `safety ← (도메인 모듈 참조 X)` 가 그대로 유지된다.

### 왜 이 안인가

세 안(A safety 소유 / B authoring 소유 + common SPI / C `safety → authoring` 파사드 예외) 중
**§5.2 문구 정정 외에 상위 문서를 하나도 고치지 않는 유일한 안**이다.

| 조항 | A | **B** | C |
|---|---|---|---|
| §5.3 4-스토어 (스키마 4개뿐) | **충돌** — 5번째 스키마 또는 catalog 계정 공유 | 적합 | 적합 |
| §5.3 "각 계정은 자기 스키마에만" | **충돌** — safety 가 catalog DataSource 를 잡는다 | 적합 | 적합 |
| §5.4 `safety ← 도메인 모듈 X` | 적합 | 적합 | **충돌** |
| §5.4 순환 금지 (`authoring ← safety` 존재) | 적합 | 적합 | **충돌** — `verify()` 가 깨진다 |
| R9.2 (L2 판정 시 대조) | 적합 | 적합 | 적합 |
| §0.2 (상위 문서를 조용히 뒤집지 않는다) | §5.3 을 고친다 | **아무것도 고치지 않는다** | §5.4 를 고친다 |

A 를 택하면 §5.3 이 B-05 에서 이미 코드로 고정됐다는 점이 걸린다. `StoreSchema` enum 이 스키마 4개의
단일 출처이고, 통합 테스트가 "각 계정이 다른 스키마를 읽지 못한다"를 12개 조합으로 강제한다.
5번째 스키마를 만들거나(B-05 산출물 확장) 계정을 공유해야 하는데, 후자는 그 검증 장치를 약화시킨다.

C 는 `authoring ← safety` 가 이미 허용되어 있어 양방향 순환이고, `ApplicationModules.verify()`(B-02)가
빌드에서 잡는다. 그 테스트는 "문서로만 있는 경계는 반드시 깨진다"(§2.1)를 막으려고 만든 것이다.

### 함께 확정한 것 — SPI 미주입·조회 실패 시 **fail-closed**

safety 가 판정 재료를 외부 주입에 의존하게 되므로, **비어 있을 때의 동작을 여기서 함께 정한다.**
나중에 정하면 그때의 기본값이 그대로 굳는다.

| 상황 | 동작 |
|---|---|
| SPI 구현 빈이 없다 | **부팅 실패** (fail-fast). §7.3 과 같은 원칙 — 조용히 뜨는 것보다 안 뜨는 게 낫다 |
| 조회가 실패한다 (런타임) | **차단** (fail-closed) + `ERROR` 로그 + 알람 (§9.4) |

근거는 I-2("L2 통과 전까지 사용자에게 도달하지 않는다")다. **세이프티에서 fail-open 은 장애가 곧
검수 우회가 된다.** 블록리스트를 못 읽는 상태에서 통과시키면, 블록리스트가 존재하지 않는 것과 같다.

### SPI 위치

`common/spi/` 를 신설한다. ADR-0003(batch)의 SPI 도 같은 자리에 둔다.

흩어두면 "이 인터페이스는 어디에 두는가"가 매번 논쟁거리가 된다. SPI 는 성격이 하나다 —
**모듈 간 계약이며 구현은 데이터를 소유한 쪽에 있다.** 한 곳에 모으면 그 성격이 위치로 드러난다.

| | |
|---|---|
| 스키마 이동 마이그레이션 | 불필요 |
| DataSource 재배정 | 불필요 |
| §5.4 · 경계 테스트 수정 | 불필요 |
| 되돌릴 때 고쳐야 하는 것 | 인터페이스 위치와 구현 주체뿐 |

### 남는 부담

R9.4(운영 중 갱신)를 만족시키려면 **갱신 → 캐시 무효화** 경로를 별도로 설계해야 한다.
다만 이는 A 를 골라도 같은 크기로 남는 일이다 — 갱신 경로는 어느 안에서도 소유 모듈이 갖는다.
**B-49 의 완료 조건에 명시했다.**

### ADR-0003 과의 관계

두 결정은 **같은 패턴을 쓴다** — SPI 는 `common`, 구현은 데이터 소유 모듈, 호출자는 주입받는다.
어긋나면 "어떤 것은 SPI, 어떤 것은 직접 참조"가 되어 3개월 뒤에 근거를 재구성할 수 없다.

R9.4(블록리스트 갱신 시 승인 UGC 재스캔)가 두 결정이 만나는 지점이다. 그 배치는 블록리스트 항목 +
safety 판정기 + 승인 UGC 본문(catalog)을 동시에 쓴다. **ADR-0003 의 A 안(batch ← common, SPI 주입)이
유지되므로 충돌하지 않는다** — batch 는 스케줄만 잡고, 재스캔 로직은 데이터를 소유한 모듈이 구현한다.

### `R2.4` 확인 결과 (2026-08-23, S-8 #61)

비공개 원문이 확보되어 확인했다. **`R2.4` 는 소유 모듈을 규정하지 않는다** — `story_draft.payload` 의
보관 주기와 접근 통제를 세션 데이터와 분리하라는 조항이다. 블록리스트와 무관하다.

→ **재검토 사유가 없다. 이 ADR 의 결정은 그대로 유지된다.**

같은 확인에서 이 문서의 인용 오류를 하나 발견했다 — *"쓰기(운영 중 갱신, **R2.5**)"* 의 조항 번호가
맞지 않는다. 원문 **R2.5 는 `normalized_value` 의 정의**(정규화를 적용한 값이며 조회는 항상
정규화된 값끼리 비교한다)이고, **운영 중 갱신은 R9.4** 다. 결정 자체는 영향받지 않으며
`tasks.md` B-49 의 DoD 는 두 조항을 모두 적고 있어 범위도 맞다.

**정정 완료 (#62).** 위 두 곳의 인용을 `R9.4` 로 고쳤다. R2.5 는 여전히 이 ADR 과 관계가 있다 —
조회를 정규화된 값끼리 비교하라는 조항이며, 그것은 SPI 의 입력 계약에 해당한다. 바뀐 것은
**"운영 중 갱신"의 근거 번호**뿐이다.
