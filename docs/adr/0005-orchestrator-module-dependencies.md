# ADR-0005: 오케스트레이터의 모듈 의존 — `play → ai`, `play → safety`

## 상태

승인 (2026-08-23) — 이슈 #64 (S-9-1)

## 맥락

S-9-1(턴 파이프라인 코어) 착수 중 **상위 문서 두 곳이 서로 맞지 않는다는 것이 드러났다.**

| 문서 | 내용 |
|---|---|
| **§4.3** 턴 처리 파이프라인 | 4단계에서 **Provider 를**, 7단계에서 **Safety L2 를** 호출한다 |
| **§5.2** 패키지 구조 | `play/ └── orchestrator/ **TurnOrchestrator (§4.3 파이프라인)**` |
| **§5.4** 의존 규칙 | `play ← catalog(파사드 O), identity(X)` — **`ai` 도 `safety` 도 없다** |

§5.2 는 오케스트레이터를 `play` 에 두라고 하고, §4.3 은 그것이 `ai` 와 `safety` 를 부르게 하는데,
§5.4 는 그 호출을 허용하지 않는다. **세 문서를 동시에 만족시킬 수 없다.**

문서만의 문제가 아니다. B-02 가 만든 `ModuleStructureTests` 가 `ApplicationModules.verify()` 로
§5.4 를 빌드에서 강제한다. `play` 에 `import com.neowadaeum.ai.provider.StoryProvider;` 한 줄을
넣고 확인했다.

```
ModuleStructureTests > S5_4_module_dependencies_are_within_allowed_boundaries() FAILED
    org.springframework.modulith.core.Violations
```

**이 테스트가 제 역할을 한 것이다** — "문서로만 있는 경계는 반드시 깨진다"(§2.1)를 막으려고 만든
장치가 문서 사이의 모순을 먼저 잡았다.

## 결정

**`play` 의 허용 의존에 `ai` 와 `safety` 를 추가한다.**

```java
@ApplicationModule(allowedDependencies = { "common", "catalog :: query", "ai :: provider", "safety :: l2" })
package com.neowadaeum.play;
```

**모듈 이름이 아니라 명명 인터페이스로 적는다.** Spring Modulith 는 기본적으로 모듈의 **베이스
패키지만** API 로 본다 — 실제로 `play` 에 의존을 허용한 직후에도 `verify()` 는 계속 실패했고,
이유는 참조 대상이 전부 내부 하위 패키지(`ai.provider` · `safety.l2` · `catalog.query`)였기 때문이다.

그래서 각 모듈이 **계약 패키지 하나씩만** `@NamedInterface` 로 노출한다.

| 모듈 | 노출 | 닫힌 채로 남는 것 |
|---|---|---|
| `catalog` | `query` — 조회 파사드 | 엔티티·Repository (B-08) |
| `ai` | `provider` — `StoryProvider` seam + DTO | `gateway` · `prompt` · `schema` · `log`, **벤더 어댑터** |
| `safety` | `l2` — 판정기와 결과 | L0 · L1 · L3 |

**모듈 이름만 적지 않는 이유** — `"ai"` 라고 쓰면 그 모듈의 *모든* 명명 인터페이스가 열린다.
나중에 다른 패키지를 노출했을 때 `play` 가 그것까지 조용히 쓸 수 있게 된다. §5.4 의
*"모듈 간 호출은 파사드로만"* 이 선언으로 표현된 것이 이 형태다.

벤더 어댑터가 `ai.provider.anthropic` 처럼 더 깊은 패키지에 있는 것이 여기서 값을 한다 —
`ai :: provider` 를 열어도 **구현체는 닫혀 있어** I-14(Provider 선택은 관리자 전용)가 유지된다.

§5.4 의 해당 줄을 같은 내용으로 고친다. **문서와 애노테이션이 어긋난 채로 두지 않는다** — 어느
한쪽만 고치면 다음 사람이 다른 쪽을 근거로 반대 결론을 낸다.

**이 결정이 허용하지 않는 것을 명시한다.**

- **`ai → play` 를 허용하지 않는다.** `ai ← (도메인 모듈 참조 X)` 는 그대로다.
- **`safety → play` 를 허용하지 않는다.** `safety ← (도메인 모듈 참조 X)` 도 그대로다.
- 두 모듈은 **`play` 의 도메인 엔티티를 알지 못한다.** `ai` 는 순수 DTO(`TurnRequest`/`TurnResult`)만,
  `safety` 는 문자열과 자기 판정 타입만 주고받는다.

바뀌는 것은 **누가 `ai`·`safety` 를 부를 수 있는가** 하나뿐이다. 호출 방향은 단방향이다.

### 왜 순환이 없는가

`ai` 와 `safety` 는 §5.4 상 **어떤 도메인 모듈도 참조하지 않는다.** 나가는 간선이 없는 노드로
들어가는 간선을 추가하는 것이므로 순환이 생길 수 없다.

```
play ──→ ai      (ai 에서 나가는 도메인 간선 없음)
play ──→ safety  (safety 에서 나가는 도메인 간선 없음)
play ──→ catalog (기존)
```

ADR-0002 가 C 안(`safety → authoring` 파사드 예외)을 기각한 이유는 **`authoring ← safety` 가 이미
있어 양방향이 되기 때문**이었다. 여기에는 그 조건이 없다.

### 왜 이 안인가

| | **A 허용 추가** | B `common/spi` 로 뒤집기 | C 현상 유지 |
|---|---|---|---|
| §4.3 (파이프라인이 Provider·L2 호출) | 적합 | 적합 | **불가능** — 파이프라인을 만들 수 없다 |
| §5.2 (오케스트레이터는 `play`) | 적합 | 적합 | 적합 |
| §5.4 | **두 줄 추가** | 두 줄 추가 + SPI 계층 | 그대로 |
| 순환 위험 | 없음 | 없음 | — |
| `ai ← 도메인 참조 X` | 유지 | 유지 | 유지 |
| I-3 구조적 보장 | 유지 | 유지 | 유지 |
| 추가되는 간접층 | 없음 | **인터페이스 2 + 어댑터 2** | — |

**C 는 선택지가 아니다.** §4.3 은 시스템의 심장이고 그것을 구현하지 않는 것은 제품을 만들지 않는
것이다. 남는 것은 A 와 B 다.

**B 를 기각한 이유.** `common/spi` 패턴은 §5.4 가 그 존재 이유를 명시한다 — *"둘 다 자기가 필요한
데이터의 소유자가 아니면서 **그 데이터를 참조할 수 없는** 모듈이다."* `safety → 블록리스트`(ADR-0002)와
`batch → 도메인 데이터`(ADR-0003)가 그렇다. **여기는 그 조건이 없다.** `play` 는 `ai` 를 참조해도
순환이 생기지 않으므로 "참조할 수 없는" 상태가 아니다.

CLAUDE.md 설계 원칙은 다음 이유만으로 인터페이스를 만들지 말라고 한다 — *"나중에 필요할 수도
있어서 / Clean Architecture 이므로."* B 는 **해결할 경계 문제가 없는 자리에 간접층을 넣는 것**이고,
그 결과 "어떤 것은 SPI, 어떤 것은 직접 호출"의 기준이 흐려진다. 기준은 ADR-0002 가 이미 세웠다 —
**참조할 수 없는 모듈이 SPI 를 쓴다.**

### 함께 확정한 것 — 파사드 규칙과의 관계

§5.4 는 *"모듈 간 호출은 `XxxFacade` 인터페이스로만"* 이라고 한다. 이 결정은 그것을 면제하지 않는다.

- `ai` 호출은 `StoryProvider` 인터페이스를 거친다 (S-3 이 만든 seam). 구현체를 직접 붙잡지 않는다.
- `safety` 호출도 판정기 타입으로 받는다. 내부 구현 클래스를 새로 노출하지 않는다.
- **`ai` · `safety` 의 Repository·Entity 를 직접 참조하지 않는다.** 두 모듈에는 애초에 엔티티가 없다.

### 되돌리는 방법 — Port/SPI 로의 전환

나중에 `ai` 또는 `safety` 를 별도 배포 단위로 떼거나, `play` 가 그 둘을 참조할 수 없게 만들어야
할 이유가 생기면 **B 안으로 전환한다.** 그때 필요한 일은 다음뿐이다.

1. `common/spi` 에 `StoryGenerationPort` · `SafetyGate` 를 정의한다
2. `ai` · `safety` 가 각각 구현한다 (기존 클래스에 인터페이스를 붙이는 수준)
3. `play` 의 주입 타입을 포트로 바꾸고 허용 의존에서 두 모듈을 뺀다

**호출부의 형태가 바뀌지 않는 것이 요점이다.** `play` 는 지금도 인터페이스(`StoryProvider`)로
받으므로, 전환은 그 인터페이스의 **위치를 옮기는 일**이지 파이프라인을 다시 쓰는 일이 아니다.
그래서 이 결정을 지금 내려도 나중 선택지가 닫히지 않는다.

### 남는 부담

**`play` 의 허용 의존이 네 개가 된다.** 모듈 하나가 넓어질수록 경계의 의미가 옅어지므로, 여기에
다섯 번째를 더할 때는 그 자체를 재검토 신호로 본다. `identity` 는 앞으로도 `X` 다 — `play` 는
`player_ref` 만 받는다 (§5.3, I-3).
