# ADR-0007: fallback 은 세션의 provider 고정을 바꾸지 않는다

## 상태

승인 (2026-08-26) — 이슈 #108 (B-23)

**I-4 에 예외를 두는 결정이 아니다.** I-4 가 무엇을 고정하는지를 좁혀 읽는 결정이다.

## 맥락

R3.7 은 provider 장애 시 fallback 체인을 요구한다.

> **R3.7** provider 장애 시 fallback 체인을 지원하고, 발동 사실을 `ai_call_log.fallback_from`에 기록한다.

그런데 I-4 는 이렇게 적는다.

> **I-4** 세션은 생성 시 provider/model에 고정. 중간 변경 불가

**fallback 은 정의상 그 고정을 벗어난다.** 지목된 provider 가 죽어서 다른 것이 대신 답하는 것이 fallback 이므로, "중간 변경 불가"를 문자 그대로 읽으면 **R3.7 을 구현할 수 없다.**

두 조항이 같은 문서 안에 있고 둘 다 유효하므로, **무엇이 고정되는가**를 정해야 한다.

## 결정

**세션에 고정된 값은 바뀌지 않는다. fallback 은 그 값을 건드리지 않는다.**

| 대상 | fallback 발동 시 |
|---|---|
| `play_session.provider_id` · `model_id` | **그대로다.** 쓰지 않는다 |
| `ai_call_log.provider_id` · `model_id` | **실제로 답한 것**을 남긴다 |
| `ai_call_log.fallback_from` | **원래 지목됐던 provider** 를 남긴다 |

즉 세션은 자기가 어느 provider 로 시작했는지를 계속 알고 있고, **그 턴 하나가 다른 곳에서 돌았다는 사실은 호출 로그에만** 남는다.

### 근거 — I-4 가 지키려는 것은 무엇인가

I-4 의 목적은 **한 세션의 이야기가 모델이 바뀌어 튀지 않는 것**이다. 문체와 판단 성향이 턴마다 달라지면 사용자는 같은 작품을 읽고 있다고 느끼지 못한다. 그것이 "중간 변경 불가"가 막는 사고다.

**장애 시 한 턴을 살리는 것과 세션 전체를 옮기는 것은 다르다.**

- 전자는 **한 번**이고, 그다음 턴은 다시 원래 provider 로 돌아간다
- 후자는 **그 뒤 모든 턴**이 다른 모델로 간다

전자를 막으면 얻는 것은 *"일관성을 지키다 턴이 실패한다"* 이고, 사용자가 보는 것은 **502 다.** 그것이 I-4 가 의도한 보호는 아니다.

### 이 결정이 허용하지 않는 것

- **`play_session.provider_id` 를 fallback 결과로 갱신하지 않는다.** 한 번 넘어갔다고 세션이 옮겨가면 그때부터는 진짜 I-4 위반이다
- **사용자에게 노출하지 않는다** (I-14). 어느 provider 로 돌았는지는 관리자 디버그 콘솔(B-41)의 것이다
- **fallback 을 조용히 두지 않는다.** 발동은 언제나 `fallback_from` 에 남는다 — 남기지 않으면 *"왜 이 턴만 문체가 다른가"* 를 사후에 설명할 수 없다

## 함께 정한 것 — 무엇이 fallback 대상인가

R3.7 은 *"provider 장애 시"* 라고만 적는다. 지금 실패는 네 갈래이고 **성격이 전혀 다르다.**

| 실패 | 승계하는가 | 근거 |
|---|---|---|
| 연결 실패 · 5xx | **한다** | 벤더 장애다. 다른 벤더면 답한다 |
| 인증 실패 · 4xx | **안 한다** | **우리 설정이 틀렸다.** 넘겨도 같은 실수가 반복될 뿐이고, 그동안 두 벤더에 청구된다 |
| 스키마 위반 소진 | **안 한다** | 이미 R5.8 · R3.3 의 재요청을 다 쓴 뒤다. 거기에 다른 provider 호출을 더하면 **한 턴의 비용 상한이 사라진다** |
| 시간 초과 | **안 한다** | 예산을 이미 다 썼다 (§13-19). 넘기면 25초를 두 배로 쓰고, 클라이언트는 그 전에 끊는다 |

**즉 승계는 "벤더가 죽었다"에만 해당한다.** 나머지 셋은 다른 provider 로 넘겨서 나아지는 종류가 아니며, 넘기는 순간 **한 턴의 비용과 시간 상한이 둘 다 무너진다.**

## 고려한 대안

| | **A 채택** 세션 고정 유지 | B 세션을 옮긴다 | C fallback 을 만들지 않는다 |
|---|---|---|---|
| R3.7 | 충족 | 충족 | **불충족** |
| I-4 의 목적(문체 일관성) | 유지 — 다음 턴은 원래대로 | **깨진다** — 그 뒤 전부 다른 모델 |
| 장애 시 사용자 경험 | 턴이 살아남는다 | 살아남는다 | **502** |
| 사후 설명 가능성 | `fallback_from` 으로 설명된다 | 세션 값이 바뀌어 이력이 사라진다 | — |

**B 를 기각한 이유**는 위 표의 두 번째 줄이다. 한 번의 장애가 세션의 나머지를 영구히 바꾼다.

**C 를 기각한 이유**는 R3.7 이 요구사항이라는 것 하나로 충분하다.

## 결과 (되돌리기 비용 포함)

| | |
|---|---|
| 문서 수정 | 없음 — I-4 의 문구는 그대로다. 이 ADR 이 읽는 법을 정한다 |
| 코드 수정 | fallback 체인이 세션을 건드리지 않는다는 것뿐 (건드리는 코드를 <b>애초에 쓰지 않는다</b>) |
| 마이그레이션 | 불필요 — `fallback_from` 은 B-11 이 이미 만들었다 |
| **종합** | **낮음** |

### 되돌리는 방법

B 로 가려면 fallback 발동 시 `play_session.provider_id` 를 갱신하면 된다. 다만 그때는 **이미 진행 중인 세션들이 섞인 상태**가 되므로, 그 전환 자체가 별도 결정이다.

### 남는 부담

**`fallback_from` 이 비어 있으면 fallback 이 없었다는 뜻이어야 한다.** 기록에 실패해도 턴은 살아남으므로(B-25 의 결정), **드물게 발동했는데 기록이 없는 경우가 생긴다.** 그때 남는 단서는 `ai_call_log.provider_id` 가 세션의 값과 다르다는 것뿐이다 — B-41(Admin Debug)이 그 두 값을 나란히 보여야 하는 이유다.

## 후속

- [ ] B-23 에서 이 결정대로 구현한다
- [ ] B-41(Admin Debug 콘솔)이 세션 provider 와 호출 provider 를 나란히 보여 준다
