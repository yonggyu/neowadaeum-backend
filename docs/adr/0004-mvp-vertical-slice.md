# ADR-0004: MVP 수직 슬라이스 재편

## 상태

승인 (2026-08-23) — 이슈 #32

> **번호 주의.** 발의는 `0002` 를 지정했으나 그 번호는 ADR-0002(블록리스트 소유, #9)가 이미 쓰고 있다.
> 덮어쓰지 않고 `0004` 로 발행했다.

## 맥락

64개 작업 중 5번째(B-05 완료)인데 **기능 코드가 0줄**이고, 문서의 핵심 가정이 B-32 까지 한 번도
검증되지 않는다.

| 가정 | 출처 | §12 순서에서의 최초 검증 |
|---|---|---|
| 컨텍스트 4,000토큰 예산 | §4.4 | B-20 (20번째) |
| Provider 25초 / 동기 응답 28초 | §1, §4.3 | B-32 (32번째) |
| 8레이어 프롬프트 구조 | §3.3 | B-20 |
| L2 를 생성 모델과 별개 판정기로 (I-12) | §6 | B-30 |

**그 사이 31개 작업의 코드가 미검증 가정 위에 쌓인다.** 가정이 틀리면 되돌리는 범위가 31개다.

§12 는 수평 순서다 — 스키마 5개 → 인증 6개 → AI 8개 → 엔진. 각 층은 완결되지만 **어느 시점에도
"돌아가는 것"이 없어 가정 오류가 드러날 계기가 없다.**

부수 문제 둘. 작업당 오버헤드(64개 × 이슈+브랜치+PR+30분 대기+CI 왕복)와 `CLAUDE.md` 104KB
(매 세션 30~40k 토큰이 로드되는데 §12·§13 은 해당 작업에서만 필요하다).

## 결정

세 가지를 함께 정한다.

### 1. 수직 슬라이스로 재배열 — B-32 까지 10개

순서는 `docs/tasks.md` 의 "MVP 수직 슬라이스" 절에 기록했다. **§12 의 작업 정의는 하나도 바뀌지 않았다 —
바뀐 것은 순서뿐이고, 제외한 작업은 취소가 아니라 연기이며 각각 복귀 조건을 적었다.**

포함: `play` 스토어 / `play_session`·`turn`·`game_state_snapshot` / **`FixedStoryProvider`(최우선)** /
B-26~29 / B-31 / B-32 / 시드 축소판 / B-47.
제외: B-06, B-07·08·10·11, B-12~17, B-22·23.

**`FixedStoryProvider` 를 B-22 보다 먼저 만든다.** 실 AI 없이 파이프라인을 무한 반복할 수 있고
비용·지연·비결정성이 없다. **B-44 는 테스트 산출물이 아니라 개발 도구다**(#27).

**규칙 위반 여부** — I-12 는 위반이 아니다. 규칙 기반 판정기도 **생성 모델과 별개의 판정기**이며,
모델 기반 L2(B-30)는 나중에 얹는다. §0.2 의 스텁 금지도 위반이 아니다 — **스텁이 아니라 축소된 실물**이고
미구현 경로는 `UnsupportedOperationException` 을 던진다. §10.1 중 1·2·3·4·6·11 은 이 슬라이스에서 살아난다.

**`dev` 프로파일의 고정 `playerRef` 는 편의가 아니라 인증 우회다.** `prod` 에서 활성화 불가를
테스트로 강제한다 — B-47 이 `prod` 에서 404 여야 하는 것과 같은 이유이고, 그보다 위험하다.

### 2. 스토어 배선을 팩터리로 — 등록 대상은 4개 유지

`StoreDataSources` 를 신설해 **풀 구성·검증·마이그레이션 배선을 스토어 수와 무관한 한 곳**으로 모았다.
`DataSourceConfiguration` 의 메서드들은 "어느 스토어가 존재하는가"만 선언한다.

**발의의 "지금 play 하나만 등록"은 기각했다.** 근거 셋.

**(a) 발의의 전제가 사실과 달랐다.**

- "EMF 4벌" — **EMF 는 지금 0벌이다.** B-05-1(#20)이 미착수라 JPA 자동설정을 제외해 두었다.
- "통합 테스트 27.8초" — **이미 정정된 수치다**(#29). WSL 툴체인이 `/mnt/c` 를 읽던 조합의 값이고,
  현재 구성에서는 7.73초다.

**(b) 실측 이득이 0.4초다.**

| 구간 | 시간 |
|---|---|
| 컨텍스트 기동 전체 | 7.73s |
| 컨테이너 3개 | 3.34s |
| **DataSource 4개 + Flyway 4세트** | **0.49s** |

**(c) 조건부 등록이 이 프로젝트의 두 관례와 구조적으로 충돌한다.**

`@ConditionalOnProperty` 는 설정 클래스 파싱 시점에 조건을 평가하며 `${VAR}` 를 해석한다. 그런데
§7.3 은 템플릿에 플레이스홀더만 두라고 하고, §7.2 는 테스트 설정 yml 대신
`DynamicPropertyRegistrar` 로 값을 나중에 주입하라고 한다. **조건 평가 시점에는 둘 다 값이 없다.**
`BeanDefinitionRegistryPostProcessor` 로 옮겨도 같다 — 더 이르다.

실제로 두 방식을 모두 구현해 돌려봤고, 각각 다음 지점에서 깨졌다.

```
Could not resolve placeholder 'IDENTITY_DB_URL' in value "${IDENTITY_DB_URL}"
app.datasource.identity.url 이 currentSchema=identity 로 끝나는 값을 갖지 않는다
```

**잃는 것도 있다.** 등록을 1벌로 줄이면 `StoreSeparationTests` 의 **12조합 계정 권한 검증**과
크로스 스키마 FK 검증이 대상을 잃는다. 이건 §5.3 을 애플리케이션 계층에서 지키는 유일한 장치다.

**따라서 발의의 목적("1벌이든 4벌이든 코드가 같아야 한다")은 팩터리로 달성하고, 등록 수는 4로 둔다.**
`docker/postgres/init` 의 스키마 4개 + 계정 4개도 그대로다(발의와 동일) — 크로스 스키마 접근은
DB 권한 오류로 먼저 터지며, 이것이 1차 방어선이고 이미 작동 중이다.

### 3. 작업당 오버헤드 축소 (§8.9 확장) 와 문서 분할

- **수직 슬라이스 하나 = 이슈 하나.** §8.1 의 예외이며 근거가 이 ADR 이다. **PR 400줄 제한은 유지** —
  이슈 단위를 키운 만큼 실질적 크기 제어가 그쪽으로 옮겨간다.
- **30분 셀프 리뷰 간격을 스코프별 차등.** `ai` · `safety` · `play/engine` 유지, `config` · `infra` ·
  스캐폴딩 면제.
- **면제하지 않는 것: "에이전트 산출물 diff 전수 확인".** 대기 시간이 아니라 읽는 행위이고
  실패 비용이 가장 크다.
- **푸시 전 로컬 게이트** `scripts/preflight.sh`. **CI 의 대체가 아니라 예고다** — 머지 차단의 근거는
  여전히 CI 이고, `--no-verify` 로 우회 가능한 것을 신뢰 근거로 삼지 않는다.
- **`CLAUDE.md` 분할** — §12 → `docs/tasks.md`, §13 → `docs/corrections.md`. **이동만 했다.**
  §15 충돌 우선순위의 `CLAUDE.md §13` 을 `docs/corrections.md` 로 정정했고, §13-12 의 내부 문서
  참조는 그대로다. 문서 버전 v1.1.

## 결과 (되돌리기 비용 포함)

| 결정 | 되돌리기 비용 |
|---|---|
| 1 순서 재배열 | **낮음** — 순서일 뿐이고 §12 의 작업 정의는 그대로다 |
| 2 팩터리 | **낮음** — 스토어별 `@Bean` 이 팩터리를 호출할 뿐이다 |
| 3 §8.9 · 문서 분할 | **낮음** — 분할은 이동이고, 조정은 문단 하나다 |

### 복귀 조건

| 대상 | 조건 |
|---|---|
| **제외한 B-xx 전부** | `docs/tasks.md` 의 "제외한 작업과 복귀 조건" 표에 각각 명시했다 |
| **`dev` 인증 우회** | **B-12 착수 시 제거한다.** 그전까지 `prod` 활성화 차단 테스트가 반드시 살아 있어야 한다 |
| **`FixedStoryProvider`** | 제거하지 않는다. B-44 의 산출물로 남고 §10.2 의 역할을 이어받는다 |
| **§8.9 조정** | **팀원이 합류하는 시점에 승인 리뷰와 함께 원복한다.** §8.9 의 기존 문장과 같은 조건이다 |
| **스토어 4벌** | 유지가 기본이다. 줄이려면 (a) 실측 이득과 (b) `StoreSeparationTests` 대체 수단을 함께 제시한다 |

### 이 결정이 위험한 지점

**슬라이스가 "돌아가니까 됐다"로 끝나는 것.** 제외한 작업은 연기이지 취소가 아니다. `docs/tasks.md` 의
복귀 조건 표가 그 기록이며, **표가 갱신되지 않으면 이 ADR 은 그냥 범위 축소가 된다.**

`dev` 인증 우회가 가장 위험하다. 편의가 자리를 잡으면 제거할 이유가 약해진다. 그래서 복귀 조건을
"B-12 착수 시"라는 **작업 시점**에 묶었고, `prod` 차단을 테스트로 강제한다.

## 절대 완화하지 않는 것

시크릿 스캔 · S-11(공개 레포) · I-3(페이로드 화이트리스트) · 세이프티 이슈 P0.
위 결정은 전부 되돌릴 수 있는 것만 건드린다. 이 넷은 실패가 되돌려지지 않으므로 범위 밖이다.
