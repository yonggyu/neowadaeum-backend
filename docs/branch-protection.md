# 브랜치 보호 설정

> 대상 레포: `neowadaeum-backend`
> 근거: CLAUDE.md §8.2 (브랜치 모델), §8.5 (PR 규칙), §8.9 (1인 개발 조정)
> 최종 갱신: B-04

이 문서는 **GitHub 설정의 사본**이다. 설정을 바꾸면 이 문서를 함께 고친다. 둘이 어긋나면 다음 사람은 어느 쪽이 의도인지 알 수 없다.

> **S-11 — 이 레포는 공개다.** 이 문서에 운영 도메인·IP·계정 체계·조직 구조를 적지 않는다. 여기 담는 것은 브랜치 보호 규칙 그 자체뿐이다.

---

## 1. 설정값

| 브랜치 | PR 필수 | 승인 리뷰 | status check | force push | 삭제 |
|---|---|---|---|---|---|
| `main` | O | **끔** | 필수 (아래 3종) | 금지 | 금지 |
| `dev` | O | **끔** | 필수 (아래 3종) | 금지 | 금지 |
| `backend` | O | **끔** | 필수 (아래 3종) | 금지 | 금지 |

추가 설정 3가지.

| 설정 | 값 | 이유 |
|---|---|---|
| Require branches to be up to date before merging | **끔** | 켜면 `backend` 가 움직일 때마다 열린 PR 을 전부 재기반해야 한다. §8.9 표에 없는 항목이므로 켜지 않는 것이 기본이다 |
| Do not allow bypassing the above settings (관리자에게도 적용) | **켬** | 1인 개발에서 관리자 예외를 두면 규칙이 없는 것과 같다. 자기 자신이 유일한 우회 경로가 된다 |
| Automatically delete head branches (레포 설정) | **켬** | 머지된 PR 의 브랜치가 자동 삭제된다. `feat/#3-package-structure` 처럼 머지 후 남은 브랜치를 손으로 치우는 일이 반복되지 않는다 |

`feat/*` · `fix/*` · `chore/*` · `docs/*` · `test/*` 는 보호하지 않는다. 수명이 3일을 넘지 않는 작업 브랜치이며(§8.1), force push 를 허용한다. 다만 다른 사람이 그 브랜치를 보고 있으면 `--force-with-lease` 를 쓴다.

## 2. 필수 status check

`.github/workflows/ci.yml` 의 잡 이름 3개를 그대로 등록한다.

| 체크 이름 | 하는 일 |
|---|---|
| `build` | `./gradlew build -x test` |
| `test` | `./gradlew test` (Testcontainers 포함) |
| `gitleaks` | 전체 커밋 이력 시크릿 스캔 |

위 세 문자열은 `ci.yml` 에서 옮겨 적은 것이 아니라 **실제 실행 결과의 체크 이름을 그대로 복사한 것**이다. GitHub 는 `jobs.<id>.name` 이 있으면 job id 가 아니라 그 값을 체크 이름으로 쓴다. 둘이 다른데 job id 를 등록하면 한 글자 차이로 `Waiting for status to be reported` 에 영구히 걸린다.

확인 방법:

```bash
gh api "repos/<owner>/<repo>/commits/<sha>/check-runs" -q '.check_runs[] | .name + "  [" + .app.slug + "]"'
```

**이름이 계약이다.** `ci.yml` 의 `jobs.<id>.name` 을 바꾸면 GitHub 는 "그런 체크가 아직 오지 않았다"가 아니라 **그 체크를 요구하지 않게** 되어, 보호가 조용히 헐거워진다. 잡 이름을 바꿀 때는 이 문서와 세 브랜치의 설정을 함께 고친다.

### 필수로 지정하지 않는 체크

| 체크 이름 | 출처 | 필수로 걸지 않는 이유 |
|---|---|---|
| `CodeQL` | 레포 설정의 **code scanning default setup** (java-kotlin, default query suite). `ci.yml` 이 아니다 | §12 B-04 의 산출물이 아니다. 우리가 규칙을 소유하지 않는 도구로 머지를 막으면, 규칙이 바뀌었을 때 근거 없는 차단이 된다 |
| `Analyze (java-kotlin)` | 위 default setup 이 생성하는 워크플로 잡 | 위와 같다 |
| `workflow-scripts` (예정) | B-04-2 | 아직 존재하지 않는다. **B-04-2 완료 후 필수 목록에 추가한다** |

CodeQL 결과는 계속 본다. 다만 **보는 것과 막는 것은 다르다.** 필수로 걸려면 먼저 우리가 그 규칙을 소유해야 한다.

### `gitleaks` 체크의 범위

`fetch-depth: 0` 으로 레포의 **모든 브랜치**를 가져와 스캔한다. PR 의 커밋만 보는 것이 아니다.

- 어느 브랜치에 시크릿이 있으면 **무관한 PR 까지 전부 실패한다.** 의도한 동작이다 — 공개 레포에서는 브랜치도 공개이므로, 어디에 있든 유출은 유출이다
- 해소 방법은 체크를 끄거나 우회하는 것이 아니라 **그 브랜치를 없애는 것**이다. 이미 푸시된 자격 증명이라면 삭제보다 **로테이션이 먼저다** (§7.1-4)
- 검증·실험용 브랜치를 오래 두지 않는다. B-04 의 시크릿 스캔 실증도 확인 직후 브랜치를 삭제했다

### 실제 유출이 들어갔을 때의 순서

`fetch-depth: 0` 이므로 gitleaks 는 모든 브랜치·전체 히스토리를 본다. 실제 시크릿이 한 번 들어가면 **그 뒤 모든 PR 이 영구히 실패한다.** 순서는 다음과 같다.

1. **자격 증명 로테이션** (§7.1-4). 커밋을 되돌려도 유출은 취소되지 않는다. 이것이 항상 먼저다
2. 로테이션 완료 기록을 남긴다
3. `.gitleaksignore` 에 fingerprint 를 등록하는 PR 을 **별도로** 연다
4. 그 PR 본문에 (2) 의 기록을 링크한다. **링크 없는 fingerprint 등록은 반려한다** — 스캐너를 조용히 재우는 것과 구분되지 않기 때문이다

히스토리 재작성은 기본 선택지가 아니다. 모든 클론을 깨뜨리면서 유출을 취소하지도 못한다.

> 이 절은 순서만 고정한 스텁이다. 최종 위치는 **B-64 운영 런북**이다. 실제 사례·키 형태·운영 계정 체계는 여기에도 런북에도 적지 않는다 (S-11).

### 실증을 재현할 때 주의

B-04 의 "시크릿 심어 스캔 실패 확인" 을 다시 해야 할 때 걸리는 함정 둘이다.

- **값에 `FAKE` · `DO-NOT-USE` 같은 단어를 넣으면 탐지되지 않는다.** gitleaks 가 스톱워드 허용목록으로 건너뛴다. 가짜임은 **파일명과 변수명으로 선언**하고, 값은 어떤 서비스의 형식도 흉내 내지 않은 **엔트로피만 있는 무작위 문자열**을 쓴다
- **이 레포는 secret scanning push protection 이 켜져 있다.** 공급자 패턴(예: 클라우드 액세스 키 형식)을 쓰면 푸시 자체가 막혀 검증이 성립하지 않는다

실증용 브랜치는 확인 즉시 닫고 삭제한다. 남겨 두면 위 성질 때문에 무관한 PR 이 전부 빨개진다.

`strict`(머지 전 최신 base 반영 요구)는 켜지 않는다. 1인 개발에서는 PR 마다 재실행 대기가 길어지는 비용이 더 크다. 대신 §8.1 의 "3일 이상 살아 있는 브랜치는 매일 base 를 받는다"로 대신한다.

## 3. 승인 리뷰를 끈 이유

GitHub 는 **본인 PR 의 자가 승인을 허용하지 않는다.** 1인 개발 체제(§8.9)에서 승인 리뷰를 필수로 걸면 본인이 본인 작업에 막혀 아무것도 머지할 수 없다.

**완화가 아니라 대체다.** 승인 리뷰가 빠진 자리는 §8.9 의 세 장치가 메운다.

1. **시간 간격 셀프 리뷰** — PR 을 연 뒤 최소 30분, 가능하면 다음 날 diff 를 처음부터 끝까지 읽는다
2. **CI 필수 status check** — 위 3종. 이것이 승인 리뷰를 뺀 자리의 주된 대체물이다
3. **에이전트 산출물 전수 확인** — Claude Code 가 작성한 PR 은 사람이 diff 전체를 읽는다

### 되돌리는 조건

**팀원이 합류하는 시점에 승인 리뷰를 다시 켠다.** 최소 1인 승인이 기본값이며, 그때 §8.9 절과 이 절을 함께 삭제한다. 자가 승인 제약이 사라지는 순간 이 예외의 근거도 사라진다.

## 5. 확인 방법

설정이 실제로 켜져 있는지는 다음으로 본다.

```bash
for b in main dev backend; do
  gh api "repos/<owner>/<repo>/branches/$b/protection" \
    -q '{checks: .required_status_checks.contexts, reviews: .required_pull_request_reviews, force_push: .allow_force_pushes.enabled}'
done
```

`checks` 가 `["build","test","gitleaks"]` 이고 `force_push` 가 `false` 여야 한다.

## 6. 부트스트랩 예외의 종료

§8.8 은 B-01 ~ B-04 구간에 한해 이슈·브랜치·PR 흐름의 예외를 두었다. **B-04 가 끝나는 순간, 즉 위 필수 체크가 세 브랜치에 켜지는 시점에 이 예외는 종료된다.** 이후 어떤 작업도 이슈·브랜치·PR 을 건너뛰지 않는다.
