# 유출 대응

> **이미 나간 자격 증명은 삭제가 아니라 로테이션이다** (§7.1).
> 지우는 것은 흔적을 지우는 일이고, 유출을 되돌리지 않는다.

## 무엇이 유출인가

| 대상 | 어디에 있는가 | 나갔다면 |
|---|---|---|
| API 키 · DB 비밀번호 · JWT 서명 키 · TOTP 시크릿 | `.env` (레포에 없다) | **로테이션** |
| 프롬프트·응답 원문 | `ai_call_log` (promptlog 스토어) | 접근 감사 확인 (R12.3) |
| 회원 식별정보 | identity 스토어에만. 소셜 식별자·이메일은 **해시만** (§13-11) | 범위 판정 |
| `player_ref` | 비-Identity 스토어 전부 | **그 자체로는 회원정보가 아니다** (§2.1, I-3) |

**이메일·이름 원문은 어디에도 없다.** 그것이 §13-11 의 결정이며, 유출 범위 판정의 출발점이다.

## 즉시 (분 단위)

**1. 무엇이 나갔는지 특정한다.** 추정으로 로테이션 범위를 넓히면 서비스가 멈춘다.

**2. 자격 증명이면 로테이션한다.**

```
ANTHROPIC_API_KEY / OPENAI_API_KEY      provider 콘솔에서 폐기 후 재발급
POSTGRES_* · *_DB_PASSWORD              스키마별 계정이 넷이다 (§5.3)
GOOGLE_OAUTH_CLIENT_SECRET              소셜 로그인
JWT_SECRET                              ★ 아래
ADMIN_TOTP_SECRET_KEY                   ★ 아래
```

- **`JWT_SECRET` 을 갈면 발급된 토큰이 전부 죽는다.** 서명 키는 하나이고 액세스(30분)·
  리프레시(30일) 모두 그것으로 검증된다 — 갈면 **전원 강제 로그아웃**이다. 그것이 의도라면
  (토큰 자체가 유출됐다면) 맞는 조치이고, 아니라면 다른 값부터 본다.
- **`ADMIN_TOTP_SECRET_KEY` 는 서명 키와 별개다** — 서명 키는 위조를, 이 키는 저장된 TOTP 가
  **읽히는 것**을 막는다. 하나를 간다고 다른 하나를 함께 갈 이유가 없다.
- **TOTP 키를 갈면 등록된 2FA 가 전부 무효가 된다.** 관리자가 재등록할 때까지 **관리자 경로가
  통째로 닫힌다** (S-4). 갈기 전에 재등록 절차를 준비한다.

**3. 새 값으로 재기동한다.** 이미지는 그대로다 — **값은 이미지에 없다** (S-2). 환경변수만 바꾼다.

## 그다음 (시간 단위)

**4. 노출 경로를 막는다.**

- 공개 커밋에 들어갔다면 **git 이력은 되돌릴 수 없다.** 포크·아카이브·스크래퍼에 남는다 (S-11).
  그래서 "일단 지우고 나중에" 라는 선택지가 없다 — 3번의 로테이션이 유일한 대응이다.
- CI 는 내장 `GITHUB_TOKEN` 외의 자격 증명을 쓰지 않는다 (§7.2). 워크플로에 다른 시크릿이
  들어가 있다면 그것부터 확인한다.

**5. 원문 접근 여부를 확인한다.**

`ai_call_log` 와 `story_draft.payload` 는 접근 통제 대상이며, **읽는 경로는 감사 기록을 남긴다**
(R12.3, B-41). 유출 의심 구간의 `access_audit_log` 를 본다 — 보관 3년 (S-10).

**6. 로그를 확인한다 — 없는 것이 맞다.**

애플리케이션 로그에는 프롬프트 원문·응답 원문·API 키·토큰·이메일이 **남지 않는다** (S-3).
남아 있다면 그것 자체가 결함이며 별도 이슈다.

## 회원정보가 포함된 경우

**7. 범위를 판정한다.** 비-Identity 스토어에서 나온 것은 `player_ref` 뿐이다 (I-3).
**매핑이 없으면 그것은 누구도 가리키지 않는 UUID 다** — 매핑은 identity 에만 있다.

두 스토어의 데이터가 **함께** 나갔을 때만 회원 특정이 성립한다. 그것이 스토어를 나눈 이유다.

**8. AI 페이로드는 별도로 본다.** 페이로드에 회원 식별정보를 담는 것은 금지이며
(I-3, R12.1), 직렬화 직전 화이트리스트 검증이 위반 시 요청을 중단한다. **구조가 막고 있으므로
"AI 로 나갔을 수 있다"는 가정은 검증 없이 세우지 않는다** — `GeneratedTurnContractTests` 가
그 목록을 고정한다.

## 하지 말아야 할 것

- **키를 지우고 끝내지 않는다.** 삭제는 대응이 아니다 (§7.1).
- **재현 절차를 공개 채널에 적지 않는다** (S-11). 미수정 취약점의 재현 경로·정규화를 뚫는 표기·
  운영 도메인과 계정 체계를 이슈·PR·커밋에 남기지 않는다.
- **유출된 값을 로그·이슈·PR 에 붙여 넣지 않는다.** 확인용이라도 마찬가지다 — 이 레포는 공개다.
- **파기 배치를 손으로 돌려 흔적을 지우지 않는다.** 파기는 보관 기간이 부르는 일이고 (R12.4),
  감사 로그는 사후 추적의 근거다 (S-10). **지우면 무슨 일이 있었는지 설명할 수 없게 된다.**
- **스키마 경계를 임시로 넘지 않는다.** 조사 편의로 크로스 스키마 조회를 열면, 유출 대응이
  **새 유출 경로를 만드는 일**이 된다.

## 사후

- 로테이션한 값의 **이전 값이 어디에 남아 있었는지**를 정리한다 — 이미지, CI, 백업, 로컬 `.env`.
- 접근 감사(`access_audit_log`)와 관리자 감사(`admin_audit_log`)는 3년 보관된다 (S-10).
  파기 배치가 그 주기를 지킨다 (B-61) — **그 전에 지우지 않는다.**
