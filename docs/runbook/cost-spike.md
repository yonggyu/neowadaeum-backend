# 비용 폭주

> **본문은 매 턴 AI 가 만든다.** 비용은 사고가 아니라 **정상 동작의 부산물**이며, 그래서 상한이 없으면
> 폭주는 예외가 아니라 시간문제다.

## 징후

| 지표 | 무엇을 본다 |
|---|---|
| `ai.call.cost.micro{provider,model,purpose}` | **어느 용도가 쓰는가** |
| `ai.call.tokens{purpose,direction}` | 입력이 늘었나 출력이 늘었나 |
| `ai.call{purpose}` | 호출 **횟수**가 늘었나 |
| `play.turn.outcome` | 실패가 늘면 재요청이 늘고, 재요청은 비용이다 |

## 먼저 갈라야 할 세 가지

**1. 호출이 늘었는가, 호출 하나가 커졌는가.**

- `ai.call` 횟수는 그대로인데 `ai.call.tokens{direction=in}` 이 늘었다 → **컨텍스트가 커졌다.** 4번으로.
- 횟수가 늘었다 → 2번으로.

**2. 어느 `purpose` 인가.**

| purpose | 늘어나는 이유 |
|---|---|
| `turn` | 플레이가 늘었다 · 재요청이 늘었다 |
| `safety` | 턴 수를 따라간다. **여기만 늘면 재요청이 도는 것이다** |
| `summary` | 세션이 길어졌다 |
| `outline` | UGC 작성이 늘었다 |

**용도별 모델이 나뉘어 있다** (R3.6) — 요약·검수·아웃라인이 턴 생성 모델을 쓰고 있다면
그것 자체가 원인이다. `ai.providers.<이름>.models.*` 를 확인한다.

**3. 사람이 늘었는가, 한 사람이 많이 쓰는가.**

한 계정이 폭주시키는 경우 상한이 이미 있다 — 걸리고 있는지 확인한다.

## 조치 — 이미 있는 상한

**턴 생성** (§15, B-38). 세 종류의 429 가 코드로 구분된다.

```
app.rate-limit.turn-per-minute        분당      → RATE_LIMITED
app.rate-limit.turn-per-day           계정당 일일 → QUOTA_EXCEEDED
app.rate-limit.auth-per-minute-per-ip 인증 경로 (IP 기준, S-8)
app.rate-limit.report-per-minute-per-ip 신고 (IP 기준)
```

**UGC** (B-60). 한 계정이 플랫폼 비용을 정하지 않게 한다.

```
app.ugc.outline-per-day      아웃라인 생성
app.ugc.previews-per-day     미리보기 — 한 번이 임시 작품 하나와 AI 호출 셋이다
app.ugc.stories-per-author   계정당 작품 수
```

**컨텍스트 예산** (§13-2, B-20). 프롬프트에 싣는 양을 줄이면 입력 토큰이 준다.

```
ai.prompt.recent-turns.verbatim       원문으로 싣는 최근 턴 수
ai.prompt.recent-turns.in-prompt      프롬프트에 싣는 턴 수
ai.prompt.recent-turns.summary-merge  이보다 오래되면 요약에 병합
```

**줄이면 이야기의 일관성이 떨어진다.** 비용과 품질을 맞바꾸는 손잡이이므로, 값을 바꾸면
**바꿨다는 사실을 기록한다** — 나중에 "왜 문체가 달라졌나"의 답이 여기 있다.

## 재요청이 도는 경우

스키마 위반 시 재요청이 일어난다 (R3.3). 구조화 출력을 보고하지 않는 어댑터는 재요청이 더 잦다.

- `ai.call{purpose=turn}` 횟수가 `play.turn.outcome` 총합보다 뚜렷이 크면 **턴 하나에 호출이 여러 번**이다.
- 타임아웃은 **재요청까지 포함한 생성 전체의 상한**이므로 (§13-19), 첫 호출이 예산 대부분을 쓰면
  재요청은 걸리지도 않는다 — 그 경우 비용이 아니라 실패로 나타난다.

## 하지 말아야 할 것

- **확률을 도입하지 않는다.** 확률 소멸·배수 지급·가챠로 비용을 조절하는 구현을 넣지 않는다 (I-16).
  재화는 정액 소모만이며, 무료 재화도 같다.
- **상한을 사용자별로 몰래 다르게 두지 않는다.** 한도는 계정 기준으로 균일해야 하고,
  다르게 두는 순간 그것은 요금제이지 상한이 아니다.
- **`ai.provider.timeout-ms` 를 줄여 비용을 아끼려 하지 않는다.** 짧은 타임아웃은 실패를 늘리고,
  실패는 재시도를 부르며, **재시도가 더 비싸다.**
- **`ai_call_log` 를 지워 저장 비용을 줄이지 않는다.** 보관 기간은 약관에 적힌 값이고 (R12.4),
  파기 배치가 그 주기로 지운다. 손으로 지우면 고지와 실제가 어긋난다.

## 사후

- 비용의 실제 내역은 `ai_call_log` 에 있다 (보관 90일). 지표는 집계일 뿐이다.
- 상한을 바꿨다면 **바꾼 값과 이유를 남긴다.** §15 의 값은 B-46 실측 뒤 조정하기로 한 값이며,
  근거 없이 움직이면 다음 사람이 같은 논의를 반복한다.
